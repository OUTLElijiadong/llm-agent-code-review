# 生产韧性与人机协同：对齐

## 原始需求

读取服务器生产状态，获取最新生产版本，检查现有检查逻辑，完善各类报错和回退处理机制。非关键错误不能把系统完全堵死，同时要保留与人的交互和人工接管入口。

## 已核验项目事实

- 生产主机：`root@81.70.251.90`，应用目录 `/opt/code-review`。
- 对齐时生产提交：`5bc2f4b7b264388f50636e90391e9cdb2580cbc6`，语义版本 `3.7.0`；生产 Git 树干净。
- `cr_backend`、`cr_frontend`、`cr_mysql`、`cr_redis`、`cr_clamav` 健康，`/healthz` 与 `/readyz` 公网返回正常。
- Alembic 当前版本与单头均为 `045_skill_asset_user_grant`，最近备份 gzip 与 SHA-256 校验通过。
- 当前 `ops-check.sh` 因磁盘使用率 87% 超过 85% 阈值退出 1；该容量告警与业务健康不是同一等级。
- `prism-ops-check.service` 仍引用旧发布目录；当前发布目录的脚本内容已核对一致，但服务路径漂移会让后续发布无法可靠接管。

最终发布前又发现并纳入同一任务范围的调度缺口：默认 `sandbox_heartbeat` 使用 `interval@30s`，原解析器只接受分钟单位，导致心跳任务被跳过。该表达式已通过失败用例复现，并补充秒级解析后发布。

独立生产复核还发现 FlyTrap 进程虽然保持 `active`，但到 `42.194.238.178:8443` 的心跳、事件上报和同步持续超时；旧巡检只读取事件日志，无法区分“本地采集可用”和“上游同步失败”，并会把包含 `remote` 字段的运维 JSON 误计为攻击事件。该缺口已通过失败用例复现并纳入本次范围。

## 边界确认

### 本次纳入

1. 运维巡检改为 `ok / degraded / error` 三态，并区分可继续的容量压力与必须阻断的容器、备份、迁移、HTTPS 关键故障。
2. 统一错误响应保留请求编号、是否可重试和下一步动作；生产环境仍不泄露内部堆栈和字段路径。
3. Agent 对话、追问、Responses 流和团队操作在失败时保留可读原因、重试/重新提问/新建会话等人工恢复入口。
4. 修复 systemd 运维检查单元的发布目录漂移，补充测试、部署记录、公网验收和回退证据。
5. FlyTrap 巡检同时验证本地进程、最近上游错误和同步信号；上游故障保留本地事件与持久队列、标记可重试降级、生成管理员告警和人工恢复动作，不把运维日志误计为攻击。

### 本次不纳入

- 不放宽认证、授权、恶意代码拦截、数据完整性、审批和破坏性操作的阻断条件。
- 不删除旧发布目录、历史备份或遗留状态文件；清理只允许在核对保护清单后执行。
- 不更换模型供应商、数据库结构或现有 Agent 协议版本。

## 需求理解

系统已有统一 `AppError`、Axios 拦截器、错误卡片、Responses 审批/人工输入和 Agent 团队重试能力。本次重点是把这些能力连成一致的恢复闭环，并修复现有“容量告警等同业务失败”和“追问过期被泛化成重试失败”的断点。

## 疑问澄清及决策

| 优先级 | 问题 | 决策 |
| --- | --- | --- |
| P0 | 生产操作授权范围 | 用户已明确“读取服务器生产状态后，给你完整权限”；允许在备份、回退和验收可证的前提下发布与修复。 |
| P0 | 哪些错误可以继续 | 资源接近阈值、单个非关键 Agent 步骤、外部暂时不可用属于 `degraded`/可重试；认证、权限、审批、恶意文件、迁移不一致和关键健康检查仍阻断。 |
| P1 | 追问过期如何恢复 | 不重复提交已失效的 `clarify_id`；保留原因，并将原问题预填为新一轮提问，等待人确认后再发送。 |
| P1 | 运维告警退出码 | `ok` 与 `degraded` 均退出 0，只有 `error` 退出 1；JSON 必须让人和自动化都能看懂继续条件和动作。 |
| P1 | FlyTrap 上游超时如何处置 | 本地日志可读且进程存活时保留结果并设为 `degraded`、`can_continue=true`；上游连通性由人核查，恢复后的成功信号自动解除集成告警。 |

## 对齐结论

以生产已核验提交为基线，先通过失败测试固定三态巡检、错误元数据和追问恢复契约，再实现代码；所有关键阻断保持 fail-closed，非关键故障提供继续、重试、回退或人工接管路径。
