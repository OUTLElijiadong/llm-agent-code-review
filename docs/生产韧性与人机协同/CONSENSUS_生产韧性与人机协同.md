# 生产韧性与人机协同：共识

## 明确需求

在生产版本 `5bc2f4b7` 上完成可观测、可降级、可恢复的错误处理闭环：巡检不能因单一容量压力把业务状态误判为全面失败；应用错误要能定位和判断是否可重试；Agent 失败要给人留下明确的下一步操作。

## 验收标准

1. 磁盘/内存达到告警阈值但未达到临界阈值时，`ops-check.sh` 输出 `status=degraded`、退出 0，并包含动作建议。
2. 容器、备份完整性/新鲜度、Alembic 多头或 HTTPS 关键失败时，输出 `status=error`、退出 1，且不伪装为可继续。
3. 巡检 JSON 每个检查包含 `status`，顶层包含 `can_continue`、`summary` 和人工动作集合；旧 `ok` 字段保持兼容。
4. 生产应用错误响应包含 `request_id`、`retryable` 和 `next_action`，但不回显生产堆栈或校验字段路径。
5. Agent/追问界面不把后端结构化错误覆盖为泛化文案；追问过期可见原因，能预填原问题并由人确认重新发送。
6. systemd 运维检查单元指向稳定的当前部署目录，定时检查在 `degraded` 时不进入 failed 状态。
7. 后端、前端、部署脚本测试通过；生产备份、部署、健康/就绪、HTTPS、Agent 关键交互均有实际证据；失败时可回退到本次前一版本。

## 技术方案

- 运维巡检：资源类检查使用告警/临界双阈值，关键依赖保持错误态；统一计算 `status` 与退出码。
- 错误契约：`AppError` 增加 `retryable` 与 `next_action` 默认值，异常处理器统一注入请求编号；未捕获错误给出安全的人工支持指引。
- 前端：扩展响应类型和可读错误解析，Agent 错误卡片显示请求编号/动作；Clarify 41001 走“原问题预填 + 人工确认”恢复。
- 发布：沿用现有备份、Compose、Alembic、systemd 和回退脚本，不引入新服务或数据库迁移。

## 技术约束

- 认证、授权、审批、恶意代码、破坏性写操作和数据库迁移不一致必须阻断。
- 生产错误不泄露内部堆栈、SQL、字段路径或凭据。
- 保持 `schema_version=1` 与 `ok` 字段兼容，新增字段只增不删。
- API key 和生产凭据不进入代码、文档或提交。

## 未决项

无阻塞性未决项。容量临界阈值采用默认磁盘 95%、内存 98%，并支持环境变量覆盖。
