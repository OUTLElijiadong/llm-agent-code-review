# 路由兼容修复验收

已修复 HTTPS 权限验收脚本在 FastAPI 0.139.0 下只发现三条路由却校验通过的问题。冻结实现没有修改业务权限、数据库、账号或生产环境。两版框架各26项回归全部通过，完整313条方法/路径、依赖顺序、源码位置与旧完整计划逐行相同；匿名可执行299格、无权限可执行239格，没有把原未发送的格子改成通过。

## 原因和准确复现

本地原环境是 Python3.9.6、FastAPI0.128.8、Starlette0.49.3；生产锁文件使用 FastAPI0.139.0。官方0.137.0将包含的路由改为树结构，0.137.2提供 `iter_route_contexts()` 供原先遍历平表的工具使用。旧脚本只对顶层 `APIRoute` 取值，因此0.139只留下healthz、readyz、metrics三个直接定义的端点，绑定来源也从49个缩为10个，旧校验仍通过。来源：[官方版本说明](https://fastapi.tiangolo.com/release-notes/#01370)、[0.139路由实现](https://github.com/fastapi/fastapi/blob/0.139.0/fastapi/routing.py)。

实际在独立 `/tmp/prism-fastapi-0139-env` 中用Python3.11.15按仓库 `requirements-dev.lock` 安装93个锁定依赖，未升级或改写现有venv。完整读取该实际包的RouteContext、包含上下文合并、有效依赖构造与遍历实现。生成计划不调用OpenAPI、不启动lifespan、依赖函数或端点。

旧实现已归档。准确红测分别是0.139路由数量/小计划2项失败、旧平表环境完整性篡改7项失败。首轮曾有一个对三行列表取第11行的测试夹具错误，其XML另存，未当作准确应用缺陷。修复后两运行时一致转绿。

## 实现与完整性门禁

- 有官方遍历API时读取有效上下文的path、methods、endpoint和dependant，保留父router、include_router、路由本身以及参数依赖的完整顺序；旧平表直接使用APIRoute，不自行拼前缀或重建依赖。
- schema2绑定验收脚本、requirements.lock和应用来源。313方法路径/41端点文件为已审基线下限，同时检查关键路径、重复项和完整行摘要。执行前重建全部路由、排除条目、中间件和来源逐值比对；删行、改依赖后再重算普通摘要也不能通过。直接调用Runner也在登录前执行门禁。
- 原已审只读依赖白名单保持；未知父级依赖会令两个角色都blocked。OpenAPI仅被测试设为禁止调用，未用于替代授权证据。
- 主代理独审发现第一版仍会跳过普通Starlette业务Route，已用真实业务Route和伪造文档函数名称两个反例准确复现。现在仅FastAPI.setup中四个内建文档函数的真实代码对象、模块与源码文件身份完全一致时允许排除；其他HTTP非APIRoute、未知树节点及Mount明确拒绝，不静默漏路由。
- 当前确有一个业务WebSocket：`/api/ws/discuss/{session_id}`。它在计划中明确列为not_tested，绑定 `app/api/v1/ws_discussion.py`，不建立连接。四个内建文档端点也明确列出排除原因；不把HTTP矩阵称作WebSocket验收。

两版冻结计划均为313条HTTP业务方法路径、41个端点文件、52个绑定来源。相对原49来源增加验收脚本、锁文件和已明确排除的WebSocket源码。完整业务行与原313计划没有变化，新增的52来源SHA及5条排除项也在两版之间完全一致。
