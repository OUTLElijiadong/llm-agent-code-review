# 前端资源发布竞态复核

## 已复现原因

2026-09-12 本轮生产发布日志记录：构建 `62fe4f32dfeb4e8153ad14d1bbe4f44f4df867e0` 后，前端启动紧接资源同步出现 `cp: can't open '/assets/./SecurityCenter-DHDsx0cc.css': File exists`，发布以 `stage=frontend_assets` 失败，随后应用回滚至 `c0e4e2ab270273808171da5518e77c9742d64eb2`、3.9.0。此结论来自根任务保存日志，不代表子任务执行过生产变更。

原顺序为 `compose up -d frontend` → 独立容器 `cp -a`。`up -d` 返回时入口脚本仍可执行自身 `cp -a`，两者写同一 assets 卷。独立本地容器为 `prism-frontend:local`、Alpine 3.21.3、BusyBox 1.37.0；无网络、无生产挂载，合成 5000 个文件。8 个复制进程同步起跑，首轮 8 个进程均失败，出现相同 `can't open ... File exists`，也出现并发路径删除后的元数据写入失败。未使用故障替身制造 cp 错误。初次两个进程无同步起跑的 30 轮未观察到冲突，因此未把自然低并发复现描述为必现。

复现脚本和输出在 `证据/前端资源并发复制复现.sh`、`证据/前端资源并发复制复现.txt`。可以通过已有本地 Alpine 前端镜像和 `docker run --rm --network none --entrypoint sh -v <脚本绝对路径>:/repro.sh:ro prism-frontend:local /repro.sh` 重现。并发压力复现带调度概率，不作为日常必现测试门禁。

## 最小修复

只调整发布事务顺序为前端构建 → assets 同步成功 → 前端启动 → 健康/HTTPS 冒烟。完整复制成功之后才切换 index，移除本次脚本自身制造的并发写入。未忽略 cp 返回码，没有修改保留窗、入口脚本和回滚脚本，也未添加跳过门禁的开关。部署维护锁继续约束标准发布事务；不支持绕开维护流程人为并发运行单独资源同步。

新增发布故障矩阵断言：资源同步失败不得启动目标前端；前端健康失败场景必须先有同步记录再有启动记录，原错误码、旧发布账本、应用回滚和数据库不降级断言继续保留。旧代码红测在 assets 场景真实执行脚本后失败。

`deploy/tests/test_frontend_assets.sh` 在本地已有镜像的独立容器运行真实入口脚本，验证同步后再启动、嵌套文件完整、窗口内旧哈希时间不变、过期文件删除、当前文件更新时间、再次启动与旧镜像回滚文件兼容，以及非法保留天数/缺失镜像资源保持退出码 64/66。该测试没有挂载生产卷或拉取镜像。
