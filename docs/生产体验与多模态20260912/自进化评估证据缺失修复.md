# 自进化评估证据缺失修复

日期：2026年9月12日。来源：主代理真实管理员界面发现唯一提案闸门列“未评估”、状态“闸门通过”，审批按钮仍可点击；未实际审批。以下是本地修复与测试结论，尚不等于生产验收完成。

## 复现与既有合同

`eval_gate.py` 明确无可用黄金集不得通过，`evolution_service.py` 明确先评估再生效。旧审批方法仅检查 status=eval_passed；历史记录若缺 eval_score，也会调用 `_apply_proposal` 修改规则。前端同样仅按 status 放行，而且把字符串 passed="true" 当成通过。

本地给真实测试数据库种入 9 组缺失或非法评估分数（空值、空串、坏 JSON、数组、null、空对象、passed=false、passed="true"、passed=1）；旧代码全部未拒绝，9 项红测。前端挂载 6 组无效分数全部红测；已有正向评估恢复用例通过。

## 最小修复

- 默认审批先保留原状态门禁，再复用既有 JSON 解析函数，要求分数字典 passed 必须是布尔 true。否则返回“评估证据缺失，请重新评估”，不调用规则写入，不更改历史提案状态、审核人或评分。
- 前端同一严格布尔判断；有 eval_passed 状态但无有效分数时，显示缺失证据说明、“待重新评估”展示状态并禁用审批。保留重新评估入口；重新取得通过证据后按钮恢复。显示修正不修改数据库历史 status。
- 内部既有 require_eval=False 兼容参数保留，代码搜索未发现调用者；公开审批 API 不接收此参数，不允许客户端绕过默认门禁。未增加迁移或重写历史数据。
- 原禁用／回滚测试原先直接伪造 eval_passed 无评分；改为先调用真实 evaluate_proposal（离线 reviewer、测试黄金集），确保正向流程证据完整。

本次校验的是服务已保存的明确通过结论，不对历史评分做签名验证，也不重定义黄金集算法、稳定性指标或审批业务。
