## 数据口径

- 平均代码评分仍为当前账号可见、非删除项目中成功审查任务的算术均值。没有成功审查显示“—”，真实零分保留 0.0；本轮没有重写历史 score。
- 审查进度为实际 processed_files / total_files，不将等待/未知时长伪造为百分比；任务列表与首页共用相同数据库事实。
- Agent 面板只显示本人运行/等待状态，不把目录数量当作进程数量，不猜 Agent 百分比。
- 风险/类型窗口按现有来源事实读取；未分级保留。累计不等于最近 N 天。首页进度面板保留既有最多 10 条审查、5 条 Agent 的展示上限，后续全量运行列表与跨会话定位需主任务验收，不应将可见卡片数宣称全系统执行数。
- 本轮没有修改历史 task11/team5、task35/team12 或孤儿账本状态，也没有读取生产私密内容。

## 补充：项目列表与工作台文件量

主任务真实界面发现工作台 630 份文件，而部分项目卡片显示数千 files。本组源码核验发现：列表原 file_count 优先活跃 CodeFile 数，若为 0 则回退 active ProjectSourceArchive.file_count；工作台仅统计前者。没有证据证明是历史软删除漏同步，不能直接将整包成员数改成 0。

本轮保留兼容 file_count 与归档历史元数据；列表和详情显式返回 active_file_count 与 archive_file_count，卡片展示“代码库文件/归档文件”。工作台显示“代码库文件”，并在同卡说明另有多少整包归档文件；可见项目包括可见的归档项目，故原“活跃项目”改为“可见项目”。统计报告同样标明来源。

独立数据用例创建 1 个有效入库文件、1 个已删除文件、另一个项目 4276 个归档成员，验证 summary=1+4276 两个分项，列表/详情对应一致，原归档 file_count 未变。此为隔离测试，不冒充生产数据库重计数。生产 630 与各归档项目的精确对账仍由主任务只读验证。

旧权限矩阵另行运行：FastAPI 0.128.8、325 条路由、311 条认证路由、243 条声明权限路由，1009/1009 通过。但 route_inventory 直接遍历 app.routes；没有验证 FastAPI 0.139 嵌套路由枚举，不可将本结果当全版本/生产全按钮验收。


## 追加核验：代码评分与测试评分分离

复核发现旧 `get_summary` 只按成功状态聚合全部评分，沙箱100分和渗透测试评分会混入“平均代码评分”。新增红测复现混合集与纯沙箱都没有独立代码评分样本数，前端也把纯测试或旧接口当作有效代码评分。已改成明确 `quick/standard/security/performance/full` 代码审查类型、成功状态及非空0—100分的范围，同时返回 `code_review_count`；总成功任务仍包含测试，名称与说明已明确。

前端使用实际代码评分样本数，缺失样本数或无样本时显示“— / 暂无代码评分样本”，有效代码0分仍显示0并保留风险提示。近期任务和下载报告区分代码评分、测试评分、类型未确认的历史评分；无分数显示“未提供”。后端最近任务明确返回 `review_type`，不把未知历史类型默认改成standard。不会改写历史任务分数与状态。

新增混合集含有效代码0分、沙箱100分、渗透100分、未知历史100分、非法101分，结果总任务5、有效代码样本1、代码均分0；纯沙箱为样本0。Dashboard组件最终61项通过，工作台后端8项及安全增量9项通过，另核缓存回归。当前模型列为非空且默认0，因此无法仅从旧记录默认0分判断过去是否真正计算过；本修复只承诺明确类型、成功状态、有效持久化分数的统计口径，不补造历史评分来源。
