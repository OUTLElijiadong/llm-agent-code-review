## 变更控制

- 生产Python锁只改变cryptography版本与官方分发hash；先用旧版本约束重解全部生产依赖，确认没有其它包升级，再替换该包解析区块。requirements范围改为 `>=50.0.1,<51.0.0`。
- 开发锁同样只升级cryptography；独立新环境发现开发锁原先漏了5个requirements已声明的生产包：bleach、libarchive-c、maxminddb、psutil、webencodings。补入生产锁现有版本和hash，无其它包升级；既有async-timeout保留。
- 前端先仅升级DOMPurify与nanoid，确认其它版本不变。随后按父代理追加授权升级Vitest及coverage-v8与必要传递依赖。没有升级Vite或其它业务组件。精确增删版本见 `证据/依赖锁差异.json`。
- 只unlink隔离工作树的node_modules符号链接，未删除或修改旧仓库目标；两次npm ci均在隔离目录实际安装。
- Vitest4兼容只调整 `test.poolOptions.forks.execArgv` 为 `test.execArgv`，保留jsdom存储初始化修复；BaseChart测试中Mock类型明确为可调用函数，未删改断言。
- 新增Markdown安全回归2例：安全标记保留、恶意原生标记/脚本链接不可执行、无权限链接过滤与代码示例保留。

## 开发Python锁补审遗留（未冒领清零）

生产Python锁审计0不代表开发锁0。追加开发锁审计返回7条源记录，按漏洞ID去重为4项，涉及3个仅开发包：black24.10.0（修复26.3.1）、pytest8.4.2（修复9.0.3）、pip26.1.2（修复26.2）。同一漏洞的重复来源未当作多个独立缺陷。原始结果在 `证据/依赖-pip-dev-audit-after.json`。已回报根代理；未在正在全量测试的3.11环境中擅自跨pytest主版本升级。

具体边界：Black公告涉及受攻击者控制的 `--python-cell-magics` 与GitHub Action `use_pyproject` 版本来源；pytest公告涉及UNIX本地临时目录；pip公告涉及恶意包索引的双重编码URL。当前生产requirements.lock不包含这3个开发包；生产镜像自带的系统pip不属于该锁审计范围，需要镜像级检查，不能据此声称容器全软件无漏洞。

## 实际发布入口只读核验

当前仓库 `deploy/deploy.sh` source `deploy/lib/common.sh`，在236—237行执行 `compose build backend`，随后执行目标镜像迁移、切换、健康与冒烟；266行构建frontend。`common.sh` 的 `compose()` 仅原样调用 `docker compose "$@"`，所以实际构建文件由Compose最终合并配置决定。基础 `deploy/docker-compose.yml` 的backend context为`../backend`、dockerfile为`Dockerfile`，frontend为`../frontend/Dockerfile`。默认路径会安装完整新锁，但服务器Compose override和COMPOSE_FILE仍可覆盖，须核最终有效值。

本轮后端应指向 `backend/Dockerfile`；`Dockerfile.runtime`、`deploy/Dockerfile.fast`、`deploy/Dockerfile.responses-overlay` 均不能仅凭应用COPY证明crypto升级。前端使用完整Dockerfile，或根代理确认新dist后的既有runtime发布方案，不复用旧dist。

在服务器目标SHA干净检出的deploy子目录，沿用原环境和Compose文件链，只输出构建位置与镜像标识，避免打印完整展开的环境配置：

```bash
docker compose config --format json | python3 -c 'import json,sys; d=json.load(sys.stdin); print(json.dumps({n:{"image":d["services"][n].get("image"),"context":d["services"][n].get("build",{}).get("context"),"dockerfile":d["services"][n].get("build",{}).get("dockerfile")} for n in ("backend","frontend")},ensure_ascii=False,indent=2))'
```

若生产原override选择runtime，追加一个仅改变构建选路的临时Compose文件到**现有完整COMPOSE_FILE链末尾**，不能替换掉生产挂载、网络和资源配置：

```yaml
services:
  backend:
    build:
      dockerfile: Dockerfile
      args:
        PIP_INDEX_URL: https://pypi.org/simple
  frontend:
    build:
      dockerfile: Dockerfile
      args:
        NPM_CONFIG_REGISTRY: https://registry.npmjs.org
```

保留context相对第一份Compose文件的解析规则。再次核backend绝对context指向目标SHA检出的backend目录、dockerfile为Dockerfile，再使用 `./deploy.sh all --revision <完整SHA>`。完整Git bundle导入、checkout、现有环境链由根代理处理；本子没有修改发布逻辑或执行生产发布。

部署后沿用同一Compose配置链验收：

```bash
docker compose exec -T backend python -c 'import cryptography,platform,os; from PIL import __version__ as pillow; assert cryptography.__version__ == "50.0.1"; assert pillow == "12.3.0"; print({"python":platform.python_version(),"cryptography":cryptography.__version__,"pillow":pillow,"release":os.environ.get("APP_RELEASE"),"version":os.environ.get("APP_VERSION")})'
docker compose exec -T backend python -m pip check
```

切换前也可针对已构建目标镜像执行 `docker run --rm --entrypoint python prism-backend:<完整SHA> -c 'import cryptography; assert cryptography.__version__ == "50.0.1"; print(cryptography.__version__)'`，先验证依赖再进入既有发布事务。版本输出不能替代备份恢复验证、Alembic、health/ready与公网真实页面验收。
