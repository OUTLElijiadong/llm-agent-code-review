# 审查详情错误语义与失败恢复

## 对齐与复现

本子任务核验 `/reviews/162` 出现“项目不存在”的原因，只修改审查详情与问题列表两个读取接口，以及审查详情页的失败恢复。主任务已提供知识库 `hard_gate=ready` 收据 `20260908-043653-5695123a36`。没有访问生产、触发模型、修改历史任务状态或迁移数据库。

完整读取相关路由、审查读取服务、项目访问门禁、异常响应封装、前端 HTTP 客户端、详情组件与既有测试。`/reviews/:id` 确实加载 `ReviewTaskDetail`，请求 `/api/review/tasks/:id`，没有误跳项目路由。原服务在任务缺失/已删除时返回“审查任务不存在”，在任务存在但父项目不可见、已删除、隔离或缺失时，透传项目门禁的“项目不存在”。前端只读取错误的 `message`，故照样展示该文案。这还使两种 404 的消息不同，可被用来区分任务记录是否存在。

使用真实 JWT、真实 RBAC/资源门禁、真实路由和内存 SQLite，独立请求六种资源状态 × 两个读取接口，共12次，均404但返回两种文案。全部请求期间没有 INSERT/UPDATE/DELETE。原响应及服务源码 SHA 在 `证据/审查详情错误文案-修复前响应.json`。这些隔离复现本身不证明生产状态。主代理随后只读取证显示：任务162确实存在且status=failed，其父项目158存在但status=deleted；证据为`证据/任务162生产存在性只读核验.json`，事务read_only=1。故“任务不存在”不是该条生产记录的精确描述，统一不可访问404仍符合防枚举要求。

前端首次失败分支只有重新加载，返回按钮藏在成功分支中；重新加载又清除原错误、切换全页加载，使失败原因和返回入口暂时消失。已有任务随后因403/404失去访问权时，旧详情及源码仍沿用网络断线的缓存保留逻辑，也需撤掉。

## 有界实现

- 两个读取接口复用 `_require_readable_task`。不存在、已删除和不可见统一为HTTP404/40400：“审查任务不存在或当前账号无权访问”，并返回到审查记录列表/联系项目负责人的下一步提示。只转换项目门禁的 `NotFoundError`，不拦截认证、权限、基础服务或未知系统异常；原401、403、503契约保留。合法owner/reviewer仍可读取。
- 详情失败页展示原始业务原因、请求编号和下一步；提供“返回审查记录”。重试只GET原任务，不会再次发起审查。重试期间保留错误信息，禁用重复点击，返回仍可用；成功后清除旧编号。
- 首次/手动重载先确认详情读取成功，再读取问题列表，避免对不可访问任务发出第二个无意义请求。旧页面卸载或路由切换后，迟到详情不会启动问题请求或轮询。
- 401/403/404使当前任务不可访问时，清空本页缓存的任务、问题、文件、源码与弹窗，递增请求序号以丢弃迟到源码/问题；连接类错误仍明确展示“上次成功获取的数据”，保留既有手动重连行为。

独立审查另复现：任务详情200但问题接口403时旧问题仍可见。最终修复只清问题列表、总数、选中问题、抽屉及问题派生文件，保留详情接口仍授权的任务摘要/文件；递增代码序号拒绝迟到源码，并阻止失效问题的旧点击/已审回调复活缓存。503仍保留明确标注的旧问题；缓存已清时不再显示“已有内容为上次成功结果”。独立复核原反例1项由security代理修复后重跑通过。

共享错误组件、全局HTTP客户端、权限码、路由守卫、任务取消/删除、数据库与历史状态均未修改。新增按钮使源码交互节点清单发生变化，后续全站台账必须按最终源码重新导出，不能继续沿用旧610节点SHA。
