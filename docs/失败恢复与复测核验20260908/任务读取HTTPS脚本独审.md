原脚本存在两类可复现验收缺口：它直接构造 Runner，跳过其 main 中的用户名/角色标记预检；错误清单已发登录请求后才失败。另仅按业务码整除得到 HTTP 状态，以及只比较不同404信封是否相等，会把不正确的40102/40301或所有404都附带相同私有detail的响应判通过。

修复仅在 `证据/verify_task_access_https.py`：

- 登录前核对 marker=20260908、role_code=qa_permission_20260908、严格四别名及 qa_20260908_<别名> 用户名、唯一正整数ID（排除bool）、非空密码。随后继续由真实 Runner 登录核查返回ID/用户名/status=1/role=user、三账号专用20权限与无权限账号空角色空权限。
- 30个只读任务请求严格校验匿名40100、无权限40303、不可见/缺失40400；读取真实 AppError 文案、next_action、retryable=false。允许固定五个信封字段以及值为null的可选detail，拒绝非空detail和任何额外字段，避免把一致的泄露当成功。
- 请求编号须在响应头和正文中一致，且符合 observability 的安全编号格式；Nginx 可覆盖客户端编号，发送和返回编号分别保留。响应限制8192字节，仅保存状态、字节数、SHA和请求编号，正文、密码、JWT不落日志。每条明确失败，不以pending隐藏失败；无自动重放。
- 复用 Runner 的正常证书验证、禁环境代理、禁重定向、0600/NOFOLLOW凭据、独占输出日志；只发4次正常登录、8次自身角色/权限GET和30次任务GET。没有模型/审查写接口，输出用only_login_and_read_requests描述请求范围，不把常量0冒充数据库实际新增数。
- 模块导入不执行请求；保持原CLI的credentials/output参数，正式调用无需新增开关。固定生产站点没有增加任意外发地址入口。

隔离测试使用真实主应用ASGI、SQLite、bcrypt、JWT、RBAC与原Runner，只将urllib传输替换为本地TestClient；所有路径限制为正常登录、自身RBAC读取和任务GET。测试中用户名/密码皆专用本地夹具，不读取生产凭据。正向脚本完整执行42次请求，数据库审查任务和模型账本均为0；日志不含密码或access_token。六个反例覆盖三类身份预检以及私有detail/错误401码/错误403码。

证据准确红测为6失败/1通过，修后7项全过，Ruff通过。首次适配器误用urllib Request.method而非get_method产生的4失败/3通过保留为“首轮适配器错误”，不当应用缺陷。初次绿测采用开发模式，真实403会带调试detail，脚本按生产隐私合同正确拒绝；已单独保存“开发信封边界复现”，最终明确使用production异常handler，且确认每个故障注入到达对应401/403/404响应后被拒绝。最终XML无错误或跳过。详情与七个源文件SHA见 `证据/任务读取HTTPS脚本独审.json`；测试副本在同目录。

## 生产入口编号差异与脚本纠正

首版独审漏掉了 Nginx 覆盖客户端请求编号这一层，错误要求返回编号等于客户端 qa- 编号。这是验收脚本的合同错误，不能算作应用401/鉴权失败。生产首次脚本结果保留在 `证据/生产任务读取错误专项原始结果.json`：四次正常登录及八次角色/权限GET共12通过，首个匿名任务GET返回正确HTTP401，却因返回编号与发送编号不同被脚本拒绝。原日志只有正文SHA，没有保存或读取原正文。后续按已核实 AppError 的公开固定401信封及返回的边缘编号重建预期JSON字节，145字节与SHA256均与原日志完全一致，独立证明该次响应的头/体使用同一边缘编号；见 `证据/原匿名401公开信封独立哈希比对.json`。

重新读取实际 `frontend/nginx.conf.template`（本仓不存在 deploy/nginx.conf）确认 /api/ 等代理显式 `proxy_set_header X-Request-Id $request_id`。后端 observability 接收此可信边缘编号，错误handler与中间件把同一编号写入正文/响应头。因此正确公共合同是合法的服务器编号在响应头与正文中一致，而不是必须沿用客户端编号。
