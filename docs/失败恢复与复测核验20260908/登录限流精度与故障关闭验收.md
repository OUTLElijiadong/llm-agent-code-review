# 登录限流精度与故障关闭验收

## 范围与结论

本轮主任务提供知识库准入收据 `20260908-043653-5695123a36`。用户报告“第六次错误受限后，正确密码立即登录成功”，本子任务先进行隔离复现，保留原先确认的安全合同：同一来源 IP、同一固定窗口内没有准入名额时，正确密码也不能绕过。没有使用已禁用 QA 账号，没有对生产进行错误密码循环或 Redis 写入。公开生产仅匿名 HEAD 读取登录页安全响应头，见另一份安全建议核验。

复现区分了三件事，不能把它们当成同一个生产原因：

1. 固定窗口从第一次计数开始，而不是从第六次拒绝重新开始。隔离真实 FastAPI、SQLite 和 bcrypt 中，五错发生在第 0/2/4/6/8 秒，第 10 秒第六次请求返回 429/50，10.01 秒正确密码仍 429/50，认证函数只调用过五次。59.90 秒的拒绝剩余 1 秒，60.01 秒正确密码成功，相隔 0.11 秒但已跨原窗口，这是原合同允许的恢复。
2. Redis 原 Lua 使用整秒 TTL；剩余 404 毫秒时 TTL=0，被误替换为完整 60 秒；某些准入/结算路径还会重新 EXPIRE 60 秒。隔离真实 Redis 已复现。实际限流剩余时间与提示不一致，已修复。
3. 配置 Redis 时，旧实现故障后粘性降级进程内影子计数。暖实例可能保留旧失败数，冷实例却没有共享历史而直接准入。隔离故障注入真实 HTTP 显示正确密码返回 200，认证成功后结算故障也会返回 JWT。这是可复现缺陷，但没有证据证明生产用户所遇现象当时发生过 Redis 故障或跨 worker，不能据此认定生产事故原因。

## 最小实现合同

- 六个登录 Lua 脚本使用 PTTL，以 `ceil(ms/1000)` 返回至少 1 秒；只有实际存在但没有到期时间的 key（PTTL=-1）才建立原配置窗口。剩余亚秒、失败结算、预留释放不重启窗口。
- 仍使用原配置的 5 次、60 秒固定窗、可信代理来源识别与原子预留/结算。公网自带 X-Real-IP/X-Forwarded-For 不覆盖真实来源；不同真实来源仍各自计数。
- 仅配置 Redis 的 LoginFailureLimiter 在初始化、Lua、结果解析或 reset 故障时抛出 HTTP 503/50301，返回 Retry-After 和 retry_after_seconds。首次为 5 秒，退避中按向上取整报告剩余时间，不重复探测；到期通过原客户端连接池或重新初始化重试。继续读取原 Redis 桶，不以本地空桶或 reset 提供新名额。
- 每实例的锁串行化重探测，连续故障每 5 秒至多一次探测。各实例分别退避，但都不降级放行。未配置 Redis 的开发模式保持内存行为，普通 GET 及已有有效会话不受此登录保护影响。
- 准入前故障不执行密码认证、不改会话版本。认证成功后结算故障返回 503，已生成 JWT 不出现在响应或审计中；auth_service 已提交的 token_version +1 不回写，审计明确“令牌未返回；会话版本已递增”。失败结算或释放失败保留共享预留，由原 TTL 到期，不伪造已完成结算。
- Login.vue 保留 503 具体原因，显示可重试倒计时并只允许用户手动重试；既有 HTTP 拦截器、429、登录错密 401 与普通业务 401 合同未改。倒计时不是授权凭据，服务端仍再次检查。
- 连接日志只记异常类型，不输出 Redis URL、异常原文或凭据。未引入新 schema、JWT/CSP 架构或密码政策变更。

## 集成和回退边界

本修复改变的是配置 Redis 故障时登录返回 503 的安全合同，恢复 Redis 后原共享桶继续生效；已存在的会话不会仅因 Redis 故障被主动清空。一次认证已经提交后若结算失败，旧会话可能因原单设备版本递增而失效，必须如实解释并等待服务恢复重新登录，不能声称事务已回滚。

没有数据库迁移；仍由主任务完成统一提交、完整 Git bundle 发布、发布版本核验。回退应用会重新引入旧限流缺陷，不能通过清空 Redis 桶、反向回写 token_version 或启用生产错密循环验证来规避。
