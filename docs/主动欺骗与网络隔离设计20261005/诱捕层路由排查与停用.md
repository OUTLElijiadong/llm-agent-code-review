# 诱捕层路由排查与停用（v4.0.57 → v4.0.63）

## 1. 结论

**诱捕层的"服务端与取证端"已经做完并在生产跑通；"把命中诱饵的请求稳定转发到诱捕容器"这一步，
六次尝试都没做成，现已主动停用整条路由，恢复原始 404/SPA 兜底行为。**

停用理由不是放弃，而是：已部署的中间态会给真实扫描器返回 **500**，等于主动告诉对方
"这条路径有异常"，比原来的 200 假首页**更容易被识破**。继续留着比停掉更差。

## 2. 逐次尝试与真实拦截

| 版本 | 现象 | 根因 | 处置 |
| --- | --- | --- | --- |
| v4.0.57 | 发布自动回滚 | `host not found in upstream "cr_decoy:8080"`，upstream 块静态解析，诱捕容器缺席时**前端整个起不来** | 改 `resolver 127.0.0.11` + 变量 `proxy_pass` |
| v4.0.58 | 预检拦截 | `nginx` 因 `access_log /var/log/prism-decoy/access.log` 目录不存在拒绝启动 | 镜像内预建目录 + `VOLUME`；`deploy.sh` 预建并放宽权限 |
| v4.0.59 | 预检拦截（人工失误） | 我为验证配置手动 `docker compose build frontend`，改写了生产镜像 tag，发布账本与运行状态脱钩 | 对齐账本 + 用已有 tag 重建前端容器，恢复自洽后发布成功 |
| v4.0.60 | 发布成功，但诱捕容器没起 | `deploy.sh` 缺 `compose up -d decoy`（镜像 tag 也没构建） | `deploy.sh` 增加显式拉起 + 提前构建诱捕镜像 |
| v4.0.60/61 | 诱饵路径 500 | `map` 用 `$request_uri` 判定，内部重写后它仍是原始路径 → 二次命中 → 内部重定向死循环 | 改 `map $uri` + 位置捕获 `$1`（仍未解决） |
| v4.0.62 | 诱饵路径仍 500 | 诱捕转发 location 只定义在 **80** 的 server 块里，https 请求在 443 的 server 中找不到它，继续落入 `location /` 再次命中 | 补独立 443 server 块（仍未解决） |
| v4.0.63 | **停用路由** | 剩余症结未定位：443 的 server 块里 `location = /__prism_decoy` 已存在且 `nginx -t` 通过，但运行时仍报 `rewrite or internal redirection cycle while processing "/__prism_decoy"` | 停用 include 与跳转，恢复 404/SPA 兜底 |

`nginx -t` 通过而运行时仍循环，说明问题在 **重写后的 location 匹配**，而不是语法；
下一步应把诱捕转发做成**独立的 location 前缀**（例如直接 `location ^~ /__prism_decoy/ { proxy_pass …; }`，
去掉 `rewrite`），或者干脆把诱捕入口放到**独立监听端口**（如仅内网可达的 8443 由诱捕容器直接对外应答，
主站完全不参与转发），从根上避开内部重写。

## 5. 重启用前必须满足的条件

1. 诱捕转发改走**独立监听端口**或**无 rewrite 的 location**，并在隔离环境先验证 443 命中路径；
2. 验证项：命中诱饵返回虚构内容（HTTP 200）、`decoy-log/access.log` 出现对应行、
   真 backend 日志对同一请求记录数为 0、诱捕容器内 `curl` 外网失败；
3. 端到端跑一遍真页面 9/9 与业务路径回归；
4. 全程保留回退点（`.releases/previous.env`）。
