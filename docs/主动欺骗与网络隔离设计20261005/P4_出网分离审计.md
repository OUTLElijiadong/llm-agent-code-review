# P4 出网分离：现状审计与阻塞（v4.0.71 时点）

## 1. 现状（只读实测结论）

```
网卡：eth0 = 10.2.0.16/22（**私网地址**），默认路由 via 10.2.0.1
公网地址：81.70.251.90 —— **不绑定在任何网卡上**（云侧 NAT / 弹性地址）
对外可见 IP：curl https://ipinfo.io/ip → 81.70.251.90（与业务入口 IP 相同）
出网 NAT：POSTROUTING 仅对 docker 网段做 MASQUERADE，宿主机自身走云侧公网出口
策略路由：ip rule 只有默认三条（local / main / default），未配置任何分流
平台主动出网目的地：api.deepseek.com（模型）、ipinfo.io / ip-api.com（威胁情报）、
                  dl.fedoraproject.org（EPEL，已临时使用后移除）、registry-1.docker.io（镜像拉取）
```

**结论：业务入口与出网共用同一个云侧公网地址，二者无法在宿主机内部分离。**

## 2. 因此 P4 的真正阻塞点是"第二个公网出口"

要做出"高风险出网走独立出口"，必须先在云侧拿到**第二个弹性公网地址**，宿主机才能用
`ip rule` + 独立路由表把指定目的/进程的出网绑到它。这一步在云控制台，宿主机内无解。

**需要管理员在云控制台执行的动作（列出即可，我不擅自操作云资源）：**

1. 为实例申请/绑定第二个弹性公网地址（EIP），记下它的地址与是否绑定到同一张网卡；
2. 若希望运维通道与业务入口彻底分离（设计文档 D3b），把 SSH(22) 只开在第二个 EIP 上，
   并从业务 IP 上摘掉 22 —— 这一步会改动**云安全组**，需单独窗口；
3. 把结果告诉我，我按下面第 4 节在宿主机落地策略路由与出网分流。

## 3. 在没有第二个出口前，能做的与不能做的

| 项目 | 现状 | 说明 |
| --- | --- | --- |
| 情报查询暴露服务器 IP | **存在** | `security_ip_trace` 查询 ipinfo.io 时，对端可见 81.70.251.90；目前没有收到限流或封禁，但这是对外信息面 |
| 模型 API 暴露服务器 IP | 存在 | DeepSeek 侧可见同一地址；迁移出网会改变源 IP，**可能触发供应商风控**，因此迁移前必须做迁移前后各 10 次真实调用对比 |
| 出网分流能力 | 未配置 | `ip rule` 无自定义表，`ip route` 无第二出口 |
| 宿主机内能做的替代 | 有限 | 可用代理容器改变**TCP 出口目的地**，但源 IP 仍是同一个云侧公网地址，达不到"分离"目的 |

## 4. 拿到第二个 EIP 后的落地步骤（我这边执行）

```bash
# 1) 新建独立路由表（假设第二出口网关为 <GW2>、地址 <EIP2>）
ip route add default via <GW2> dev eth0 table 100
ip rule add fwmark 0x2 table 100

# 2) 给高风险出网打标记（示例：情报/证书/更新；模型与通知渠道不动）
iptables -t mangle -A OUTPUT -m owner --uid-owner 0 -d 34.117.59.81 -j MARK --set-mark 0x2   # ipinfo.io
iptables -t mangle -A OUTPUT -d 208.95.112.1 -j MARK --set-mark 0x2                          # ip-api.com

# 3) 目的地址变更时更新规则；验证对端看到的源 IP 已变化
curl -sS https://ipinfo.io/ip    # 期望返回 <EIP2>，而不是 81.70.251.90

# 4) 模型与通知渠道：迁移前后各 10 次真实调用对比成功率（设计文档验收项 H2）
```

## 5. 方案边界（写清楚避免误解）

* 出网分离**不改变**任何对外的"行为"：不新增扫描、不回击、不影响授权渗透流水线；
* 它解决的是"对手反向拉黑我方出口会连带打掉业务入口"这一类风险，属于**韧性**改进；
* 在拿到第二个 EIP 之前，P4 保持在"已审计、待基础设施"状态，我不会用代理容器假装完成。
