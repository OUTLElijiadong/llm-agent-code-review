# 圆桌讨论群聊语义完善 - 对齐文档

## 原始需求

圆桌讨论应把全部代码审查子 Agent 放入同一个共享聊天群。Agent 能读取其他参会者和用户的完整发言，能自主选择发言或静音；发言时能明确选择赞同、否认、质疑、补充或保持中立；最后由一个总结 Agent 输出共识、分歧和处理建议。完成本地修改和验证后同步到服务器 `81.70.251.90`，确保线上完整运行。

## 项目现状

- 后端为 FastAPI，讨论入口为 `GET /api/discuss/start`，实时通道为 WebSocket。
- `DiscussionOrchestrator` 目前让选中的静态审查画像按顺序强制发言，每位 Agent 能看到此前 Agent 文本。
- `full` 组合当前只有安全、可靠性、性能、可维护性四个画像，通用质量 Agent 未进入圆桌。
- Prompt 已要求后发言者表态，但输出是无结构纯文本，系统无法可靠区分赞同、否认或其他立场。
- 当前不存在自主静音决策；每个 Agent 每轮必须生成 100-300 字。
- 用户插话会实时广播并提示下一位 Agent，但未进入编排器的完整 `all_turns`，主持总结和问题抽取不能保证包含用户原话。
- 生产服务器 `/opt/code-review` 的相关实现与本地一致，四个 Compose 容器运行中，Backend 健康和就绪检查通过。

## 边界确认

- “全部子 Agent”限定为代码审查域的五个子 Agent：通用质量、安全、可靠性、性能、可维护性。
- 主持/总结 Agent 独立于五个审查子 Agent，负责开场和最终总结，不参与普通观点投票。
- 项目管理、文件管理、仪表盘、报告导出等业务 Agent 不具备独立代码评审职责，不纳入圆桌参会集合。
- 保留现有 WebSocket、报告沉淀、暂停/继续/终止和用户插话能力。
- 不改数据库结构，不引入新的外部依赖，不修改模型密钥配置。

## 已解决疑问

1. 参会范围：采用五个代码审查子 Agent 全量参会，避免无关业务 Agent 产生低质量讨论和额外模型成本。
2. 静音语义：静音是 Agent 每轮自主决策，不等于连接断开；前端显示静音状态，但静音记录不进入问题抽取。
3. 立场语义：使用结构化枚举 `propose/agree/oppose/question/supplement/neutral`，其中 `oppose` 对应用户所说的“否认/不赞同”。
4. 总结责任：主持 Agent 汇总有效发言、用户插话、共识和仍未解决的分歧。
5. 部署方式：仅同步本任务白名单文件，先备份远端同名文件，重建 Backend/Frontend，再做容器和公网冒烟验证。

## 项目特性规范

- 兼容历史讨论帧：新增字段均有默认值，旧消息仍可渲染。
- 决策解析失败时降级为普通发言，不能让整场讨论中断。
- 模型调用失败与自主静音必须区分；调用失败仍标记失败，静音标记为成功决策。
- 共享上下文按时间顺序包含 Agent 发言、静音状态和用户插话。
- 所有新增 Python/TypeScript 函数均提供函数级注释，说明功能、参数和返回值。
