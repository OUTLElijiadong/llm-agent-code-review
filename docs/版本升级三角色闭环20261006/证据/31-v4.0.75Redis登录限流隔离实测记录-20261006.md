# v4.0.75 Redis 登录限流隔离实测记录

## 验收结论

2026-10-06（Asia/Taipei），在本机候选工作树以 Redis 7.4.11 执行三轮隔离集成测试，每轮 6 项通过，合计 18 项通过；另有 34 项限流及 Redis 不可用回归通过。三轮都记录了唯一运行编号、源文件哈希、Redis 配置和清理回执。该结果验证当前 `rate_limit.py` 的 Redis Lua 逻辑和 Unix URL 客户端创建路径；未连接生产 Redis、生产 API 或生产数据库。

## 复现和修复

- 首次尝试使用项目原有容器夹具时，因本机 Docker daemon 未运行而在测试前失败；没有连接生产 Redis。
- 随后从官方 Redis 7.4.11 发布源码归档构建临时二进制；本地归档 SHA256 为 `3c266ece0abd54ed3b1c912c6eb86b7508cf382cb690ee6649d3843f018f6357`。运行二进制报告版本 `7.4.11`、SHA256 为 `6c2239e0542b75b721594fab53a2dd7f931844f515b8c4808a056682eca78e18`。源码到二进制的构建命令输出未归档，因此版本/二进制哈希可核验，但构建过程不能由现存记录完整复现。
- 独立复核发现启动器未验证 TLS 端口、沿用完整父进程环境、没有记录版本/清理回执，也未验证 `Redis.from_url()` 的 Unix URL 建连。修复后又发现 socket 权限只有日志记录、未断言，且强制终止超时分支需避免清理仍被进程使用的目录。当前启动器与测试已使用白名单环境、发现 `backend/.env` 时拒绝运行、要求 Redis 7.x、启动时读取并断言 TCP/TLS 端口为 0、验证 socket `0700`、增加 Unix URL 工厂连接测试和 pytest 180 秒超时；进程无法退出时保留目录并报告 PID，不删除仍在使用的文件。正常清理路径已重复实测；极端“SIGKILL 后仍无法 wait”分支没有人为触发。
- 修复后的首次执行出现启动器清理断言条件写反：其中 6 个 pytest 用例通过，但启动器误报临时目录清理失败并返回非零。已修复断言并保留当次原始日志 [证据 23](23-v4.0.75隔离Redis登录限流实测-20261006.txt)。这属于测试启动器自身的验收问题，不是生产服务故障。
