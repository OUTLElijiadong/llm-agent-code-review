## 6. 风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
| --- | --- | --- | --- |
| DeepSeek 限流 / 不稳定 | 中 | 高 | 重试 + 缓存 + 截图兜底 |
| LLM 返回非 JSON | 中 | 中 | json_object 模式 + 二次清洗 + 单测覆盖 |
| 工作量超估 | 高 | 高 | 严格走 P0,P1/P2 砍掉(版本对比、批量状态、PDF) |
| Monaco 体积大首屏慢 | 中 | 低 | 路由懒加载 + 语言包按需 |
| MySQL LONGTEXT 影响列表 | 低 | 中 | 列表不 SELECT content,详情按需 |
| 答辩环境网络问题 | 低 | 高 | 预录演示视频 + 截图 |
| 论文与代码节奏不同步 | 中 | 中 | 边写边改,每周末同步一次 |
| 多 Agent 调用次数增加导致演示变慢 | 中 | 中 | 默认 standard 保持单代理;full 仅用于小文件或录屏 |

## 11. 高频答辩问题预备答案

| 提问 | 简答 |
| --- | --- |
| 你这个跟 SonarQube 有什么区别? | SonarQube 基于规则匹配,缺少语义理解和修复建议;本系统利用 DeepSeek 的自然语言理解,能给出修复方案和代码 |
| 为什么不接 GitHub? | 数据库直存是本系统核心定位,目标是本地教学/小团队场景,接 GitHub 会增加 OAuth/Webhook 等工程负担,对答辩演示无加分 |
| LLM 给的建议不准怎么办? | 通过强 Prompt 约束 + 8 维度规则 + 综合评分;问题闭环管理(忽略/已修复)让用户保留判断权;后续可加 RAG 引入团队规范 |
| 你的 Prompt 是怎么设计的? | 角色明确 + 维度分组 + JSON Schema 强约束 + few-shot 示例;`response_format=json_object` 强制返回合法 JSON |
| 长文件怎么处理? | 按函数/类边界分片,每片携带行号偏移;Service 收齐后还原绝对行号 |
| 安全方面做了什么? | bcrypt 密码、JWT 短期 token、CORS 白名单、文件白名单、SQL ORM 参数化、user_id 隔离 |
| 性能怎么评估? | 单文件审查 < 30s,列表接口 < 500ms;LONGTEXT 不入列表 SQL |
| 数据库选 MySQL 还是 PostgreSQL? | MySQL 8.0,LONGTEXT 上限 4GB 足够,部署简单 |
| 后续扩展计划? | 异步任务队列(Celery)、多 LLM、增量审查、团队协作;多 Agent 可继续扩展为代理投票和冲突合并 |
| 这个系统教学价值在哪? | 老师可让学生提交作业代码,系统自动审查并出报告,辅助批改与反馈 |

## 13. Git 分支与提交规范
