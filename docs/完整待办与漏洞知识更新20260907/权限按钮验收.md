## 隔离语义

当前数据模型没有独立组织字段。这里的跨域验证对应项目拥有者/项目成员关系与 Agent 账号所有权，不能宣称已测试一个不存在的组织实体。

| 请求场景 | 既有契约与实际结果 |
| --- | --- |
| 未认证请求 | 401 |
| 禁用账号、缺少 API 权限 | 403 |
| 普通管理员访问唯一超管接口 | 403 |
| 同项目 reviewer 读取项目、源码、成员、任务/问题 | 可读，HTTP 与内容回显通过 |
| 同项目 reviewer 即使拥有 file:edit 等 API 权限仍修改源码/项目/成员/问题/审查状态 | 403，数据库目标内容保持 |
| 有权限但访问其他项目资源 | 通常 404 防枚举；旧报告删除沿用 403 |
| 同项目成员访问别人的 Agent 团队/事件/消息/取消/重试/归档 | 404，团队原状态保持 |
| 审查记录/问题列表 | 项目 owner ∪ member 范围；外项目过滤不返回外部数据 |
| 报告列表/详情/导出 | 任务发起者或管理员；项目成员资格本身不授予别人的报告 |
| 用户 RBAC 自助查询 | 自己的角色/权限/菜单/范围可读；其他账号 403 |

普通 owner 的项目创建 → 文件创建 → 项目修改 → 源码改版 → 重命名 → 添加 reviewer → 新 HTTP 客户端读取 → 移除成员 → 原成员 404 → 版本 1/2 回显 → 删除文件/项目完成闭环。这证明 HTTP 客户端重建后的数据库持久性，不等同于生产进程/机器重启验收。

## 专用生产验收账号准备

`backend/scripts/prepare_permission_acceptance.py` 默认 dry-run，只接受显式 `--apply` 创建 4 个来源明确的普通账号及独立自定义角色。权限仅来自现有数据，不授予管理员、模型执行或服务器运维权限；`no_permission` 不绑定任何角色。随机密码只写入 `--credentials` 指定的 0600 文件，禁止将该文件纳入 Git 或本报告。

应在既有生产后端环境中先 dry-run，凭据放在受限备份目录；随后使用真实登录 API 获得会话，再经真实 API 创建 2 个验收项目和普通源码文件，不伪造成功任务或报告。`--disable` 逐个核对清单 id/username/role 后禁用专用账号并递增 token_version，保留审计关联。专用项目、账号和输出单独记来源清单，不能修改真实用户的权限来凑矩阵。
