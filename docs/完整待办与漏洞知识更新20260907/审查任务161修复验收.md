# 审查任务 161 计数与执行展示修复

## 生产复现

本项是审查任务 `review_task.id=161`，归属项目 157，与先前项目 161 字段取证不同。只读一致性事务确认其为 `sandbox_test/success`，`total_files=processed_files=1`，历史总数 16，四级计数均零，`coverage/model_name` 为空，没有 `ReviewIssue` 或输入快照记录。

生产报告的“问题清单”含四个三级发现标题，每个下面有“漏洞位置、vulnerable code、POC/复现、修复建议”四个项目符号字段。旧发布代码把这 16 个字段误算为发现数。结构证据仅保存节点类型、字段类别和长度，不保存正文。最终解析器在生产只读进程中处理实际报告，得到 4 个报告条目，4 个未分级。真实报告 SHA-256、运行 helper SHA、采集器 SHA、SQL SHA 和只读事务状态均绑定在 `证据/审查任务161真实报告解析核验.json`。

## 实现和历史边界

小型解析器仅处理“问题清单”章节，忽略代码围栏与其他章节。发现标题或顶层发现列表构成条目；字段行、带序号/加粗/内联值的字段子标题不单独计数。空章节、缺章节、无法识别的格式保留未知，只有明确“未发现确定性执行失败”等声明才表示零。严重度只采纳明示标签或严重度字段，不从描述猜测，更不代表漏洞已经确认。

任务详情、审查列表、报告列表与详情、领域 JSON 导出和已有仪表盘统计读取同一解析摘要。任务 161 在这些读取路径得到 4，数据库原 16、success、原 update_time、NULL coverage 和全部历史关联不变。未来主动生成/重新发布的沙箱报告复用解析器，保存条目与显式严重度摘要，避免新记录重现误计。

其他无法解析的旧沙箱报告保留旧计数作为历史记录，来源为 `legacy_task_snapshot`，并明确保存 `legacy_recorded_total`；页面不把它显示为确定条目数。没有全库历史回填或状态迁移。标准审查、圆桌与渗透报告的原计数和评分契约保持不变。

沙箱详情显示真实已完成状态及已处理范围 1 / 1，撤去不适用的大块模型/当前文件/分片未知占位。严重度未分级时不以四个零表示没有风险；页面明确“报告条目不代表已确认漏洞数”，没有结构化明细时引导查看原报告。沙箱报告页不显示没有依据的修复进度。独立互审指出测试得分 100 曾推导“低风险”，已在任务和报告页面修正为测试得分不代表安全风险、风险未评定，挂载回归覆盖。
