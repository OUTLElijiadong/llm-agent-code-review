# 登录冷却反馈验收

日期：2026-09-07。要求：第 6 次请求限流后明确显示剩余时间，等待结束恢复登录，保留正确密码也受冷却限制。

## 复现

原规则为每来源 IP 默认 60 秒内最多 5 个失败/处理中名额，第 6 次请求在密码验证前返回 429。窗口从首个请求起算，拒绝不重置窗口；获准后的成功认证才清零失败。本轮没有修改阈值、窗口、可信代理、Redis Lua 或并发预留协议。

本地真实 FastAPI auth 路由、密码哈希校验、SQLite 和可控限流时钟复现：第 0/2/4/6/8 秒五次错密均 401；第 10 秒第六次请求 429、Retry-After 为 50；第 30 秒正确密码仍 429、剩余 30 秒且认证调用总数仍为 5；第 60.01 秒正确密码成功签发 token。修复前 JSON 缺 `retry_after_seconds`，前端丢弃响应头且没有倒计时，专项明确失败后修复通过。

本地 Nginx 配置、生产模板及运行中 `cr_frontend nginx -T` 均无 `limit_req`；运行配置也无隐藏 Retry-After 或拦截应用错误的指令。`证据/登录限流Nginx只读核查.json` 记录运行配置 SHA-256 与有限相关行，没有向生产发送任何登录请求。

## 实现

- auth 限流响应说明当前剩余秒；业务异常处理器保留 Retry-After 头，并在生产 JSON 返回相同的 `retry_after_seconds`。
- HTTP 拦截器支持应用 JSON 及代理 HTML 429、带 Retry-After 的 503。响应头支持秒数/HTTP-date；有服务器 Date 时使用服务器相对时间避免本机时钟偏差。格式依据 [RFC 9110 §10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#name-retry-after)。无效或未报告的剩余时间不捏造成 60/90 秒。
- 登录页根据服务器秒数显示截止倒计时，按钮及直接提交 handler 均阻止冷却中重复请求，说明正确密码也不能提前通过。结束只恢复手动提交，不自动重试密码。
- 同一标签页刷新/重进保留截止时间；sessionStorage 只存截止毫秒，不存用户名/密码。卸载清理计时器，存储不可用仍能显示本次倒计时，最终准入由服务端控制。
- 登录错密由表单唯一提示，不清 Token、不作为已有会话失效跳转、不重复全局 toast；其他业务 401 的会话过期处理保留。表单校验、普通错误、角色首页、注册跳转不变。
