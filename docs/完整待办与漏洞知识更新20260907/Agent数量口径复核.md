# Agent 数量与活动状态口径复核

## 复现与范围

同一页面中的 5、19、17 原本指向不同集合。Agent 中心把可见列表称为“在岗”，态势又使用不经账号过滤的总目录；MetaGPT 则只适配内置执行器。这里修正可见集合和显示含义，没有把三个不同集合强行改成同一个数字。

| 集合 | 真实代码来源 | 当前语义 |
| --- | --- | --- |
| 内置运行执行器 | `AgentRegistry.list_runtime()`，由 `Orchestrator` 注册 | 当前源码注册 17 个 BaseAgent，包括编排器自身 |
| 全平台运行目录 | 内置执行器与启用、已发布的自定义 Agent 合并，按 code 去重 | 仅 admin/super_admin 使用全平台范围；数量随实际已发布目录变化 |
| 普通账号可见目录 | 本人调用记录关联的目录，排除内部管理 Agent；自定义项还需 `custom_agent:invoke` | 列表、分类计数、态势可见数统一从这一集合计算；没有调用记录时为 0 |
| MetaGPT 可适配目录 | 真实 RoleAdapter 通过内置注册表获取执行器 | 明确为“内置可适配 Agent”，接口增加兼容字段 `catalog_scope=builtin_registry`，不包含已发布自定义项 |
| 审查画像 | 旧审查画像配置及审查类型映射 | 一个执行器可以提供多个画像，画像数量不计作独立 Agent |

后端隔离测试真实构建 17 个内置执行器，另外两条已发布自定义目录为显式合成测试数据。再写入普通账号的 5 个内置及 1 个自定义调用记录，但不授予自定义调用权限，准确构造可见 5、总目录 19、MetaGPT 17。该合成数字用于复现，不是生产当前自定义 Agent 数量的断言。

修复前后端 6 条新增测试中有 5 条失败：4 条复现计数或账号活动归属错误，第 5 条因新声明的范围字段尚不存在失败；剩余历史状态保持测试原本通过。前端 4 条初始测试均为有效行为失败，后续新增迟到事件边界共 5 条。保留的修复前 XML 不能被解释为 5 个后端安全漏洞。

## 修改与边界

运行列表、分类汇总、态势使用同一服务端可见集合。前端分类与态势活动计数直接取已返回的列表，避免三个请求先后返回不同目录快照；真实 0 不再被 `||` 替换成全局目录数。只有热点、调用频谱和今日请求量使用各自的账本统计，按本人或管理员全平台范围读取。运行调用统计和热点优先使用明确的 `agent_label`，仅缺少该归因时兼容旧 model 名称推断。

独立审阅发现新增系统用量入口与旧兼容规则发生冲突：明确标注 `api_connection_test` 或 `embedding` 的调用若仍按模型名回退，会错误算成 `code_reviewer`。两个标签的独立红测均复现了虚假的可见 Agent。最终将明确但不在运行目录的标签跳过，保留仅缺 label 的历史回退；这些实际模型调用仍计入“今日模型请求”，没有因不属于运行 Agent 而丢失系统用量。

普通账号的活动状态只使用属于本人的事件；他人事件及无 user_id 的系统事件不被当作本人执行。管理员保持全平台范围。活动窗口沿用既有逻辑：最新执行/阻塞事件超过 90 秒回到非执行态，错误状态窗口 6 秒；前端拒绝无效时间和过期活动事件。自动同步有既有轮询延迟，文案因此明确“按最新快照中的近期事件计算并自动同步”。这不是进程存活或心跳在线证明。

兼容 API 字段 `online/working/idle` 仍保留，说明及界面分别改为“可见目录/近期执行/非执行态”。非执行态是当前可见集合中未处于执行状态的数量，可以包含阻塞或错误，不宣称空闲或离线。

本次只读取调用账本和运行事件，不执行模型调用，不更新历史审查任务、Agent 根任务、团队、工具执行或调用记录状态。测试中的账本插入均位于隔离测试数据库。
