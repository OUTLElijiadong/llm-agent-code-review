## 2. 启用过程中暴露并修掉的两个真实缺陷（都不是小问题）

### 缺陷 A：执行器白名单漏字段（v4.0.55 修）

保存时 API 返回 `available=false / errors=["动作 security_block_configure 包含未允许参数: ['auto_escalate']"]`。

根因：`ops_service.ACTION_PARAM_KEYS`（API 进程）与 `deploy/prism_ops_executor.ACTION_PARAM_KEYS`
（root 执行器）是**两份独立维护的白名单**，v4.0.53 只改了后端那份，执行器仍然拒绝该字段。
修复：执行器白名单补 `auto_escalate`，并加互引注释。

**新增契约回归** `backend/tests/unit/services/test_executor_backend_contract.py`：逐动作比较两侧
参数白名单、动作集合、只读集合，并锁定封禁时长上限两侧同为 3600。这类"两个进程各有一份名单"
的漂移以后会在 CI 里直接红。

### 缺陷 B：读取路径把开关覆盖成 false（v4.0.56 修）

账本已写入 `auto_escalate=true`，但 API 读出来是 `false`——用户会以为"我明明开了怎么没开"。

根因：`security_response_service._POLICY_KEYS` 漏了 `auto_escalate`，回执重建策略时该字段被
pydantic 默认值填成 `false`。修复：补键；同时把回执缺新键的情形改为**按保守默认值兜底**，
而不是 `KeyError` 直接变成"状态不可用"。新增两条回归：账本 true 必须回显 true；
旧账本缺键必须降级为 false 且整体仍可用。

> 这两条与 v4.0.54 那次一样，都是"新增策略字段时只改了一处"引发的。三次连在一起看，
> 结论很明确：**加字段 = 加白名单（后端）+ 加白名单（执行器）+ 加读取回显 + 加旧账本兼容 + 加回归**，
> 少一环就是线上事故。现在已经把前三环用契约测试锁住了。

## 3. 加码逻辑验证（在已部署代码上，用隔离账本，不碰生产集合）

```
账本策略: enabled=True auto_escalate=True duration=3600
第1次: duration=3600s escalated=False previous_24h=0
第2次: duration=3600s escalated=True  previous_24h=1
第3次: duration=3600s escalated=True  previous_24h=2
```

`escalated` 与 `previous_24h` 随重复次数正确置位；`duration_seconds` 固定为策略值 3600，
因为 3600 已经是硬上限（未开启加码时同样时长，开启后由 `ESCALATION_FACTOR=4` 的倍数在
3600 处封顶）。用例里 `status=failed / ipset_timeout=None` 是因为隔离账本用的是假 ipset 模拟器，
**生产 ipset 未被触碰**（核验时 `ipset save prism-sec-v4` 成员数 0）。
