# 最高管理员侧能力清单：现状、边界与解除方式

> 观察时间：2026-10-05 21:08—21:15 CST。对象：**最高管理员（唯一超级管理员 `admin`）**
> 与其管理面 Agent（JARVIS「最高管理员管理 Agent」）、安全中心、运维执行器。
> 本文只记录**当前代码与生产实测事实**，每条都给出文件位置；"能不能解除"分开写，不混为一谈。

## 一、最高管理员本来就已经拥有的能力（无需解锁）

| 能力 | 入口 | 约束 |
| --- | --- | --- |
| 服务器运维动作（44 个已登记动作：状态、备份、重启服务、写配置、systemd、docker、包管理、防火墙端口、系统账户、SSH 公钥） | 管理面 `admin_execute_operation` / 安全中心 | 仅唯一超管；`critical` 级动作需一次性审批；全部写 `OpsExecution` + 操作审计 |
| 安全中心（概览 / 事件 / 策略 / 自动封禁 / 溯源与响应） | `/admin/security-center`，55 处 `require_super_admin` 守卫之一 | 仅唯一超管；匿名 401、审查员与普通用户 403 |
| 限时单 IP 封禁与解封 | 自动封禁面板 | 默认策略关闭时仅监控；保护来源永不被处置 |
| 小菱全部业务工具 | 站内对话 | `_WRITE_TOOLS` 内写操作需二次确认；`_DANGER_TOOLS` 单独收紧 |

生产实测（2026-10-05）：宿主 `fail2ban`、`nmap`、`suricata`、`zeek`、`whois` **均未安装**，
`ipset` 已安装且 `prism-sec-v4/v6` 两个集合生效，封禁策略 `enabled=true`、`ai_anomaly_enabled=true`、
阈值 20/30、租约 900 秒、当前活动租约 0。

## 二、当前**存在**的限制（按性质分三类，逐条给出解除方式）

### A 类：可以合理解除的运维缺口（工程问题，不是权限问题）

| 编号 | 缺口 | 影响 | 解除方式 | 风险评估 |
| --- | --- | --- | --- | --- |
| A1 | 宿主未装 `fail2ban` | 登录爆破只能等"每分钟日志巡检 + 阈值"，最快也要几十秒到一分钟才处置 | `dnf install -y epel-release && dnf install -y fail2ban`，只启用 `sshd` jail，`bantime` 与现有 ipset 租约保持同一量级 | 低。与现有 `PRISM-SEC-IN` 链叠加，不改变默认策略 |
| A2 | 宿主未装 `whois` | 溯源缺少 `netname/orgname/route` 归属摘要（现只有 `ip-api`/反向 DNS） | `dnf install -y whois` | 极低，纯只读工具 |
| A3 | 宿主未装 `nmap` | 无法做本机端口自查的二次验证（现用 `ss -lntup` 已够） | 建议**不装**；确需装则只对 `127.0.0.1` 使用 | 中。装在生产宿主上易被误用于第三方地址 |
| A4 | 未装 `suricata` / `zeek` | 没有流量入侵检测与全量网络元数据审计 | 需要先在容器网络或宿主入口接镜像流量，并预留内存；建议低峰单独评估 | 高。资源占用与误报处置都需要单独设计 |
| A5 | `THREAT_INTEL_BASE_URL` 未显式配置 | 默认 `ip-api.com` 在生产出口出现过 12 秒超时（本轮实测 8.8.8.8 归因超时） | 生产 `.env` 显式配置可用的 HTTPS 情报端点 | 低。失败已按"不参与评分"降级 |
| A6 | 自动封禁保护白名单为空 | 依赖 root 固定保护来源与"当前管理员 IP"兜底 | 在安全中心填入管理员常用网段（IPv4 ≥/24） | 低。填入过宽网段反而会保护攻击者，需谨慎 |

### B 类：**不建议**解除的硬限制（解除即降安全性，且与既有约定冲突）

| 编号 | 限制 | 现状 | 为什么保留 |
| --- | --- | --- | --- |
| B1 | 模型不能自选封禁目标 | 候选由宿主规则引擎生成，只给小菱**脱敏候选编号**；`security_block_apply_anomalies` 重读日志后再校验 | 让模型直接持有"任意 IP 封禁"入口，等于把生产防火墙的写权限交给一次模型幻觉 |
| B2 | 不存在"主动反击 / 反向入侵" | 全库检索"反击"只出现 1 次，且原文写的是"**未验证或未实现**"（验收边界） | 对第三方主机发起回击属于对外攻击行为，与"只读红线""目标域必须明确"两条既有约定直接冲突 |
| B3 | 三个新溯源动作不进模型工具目录 | 已登记 `INTERNAL_SECURITY_ACTIONS`，并从 `TEAM_READ_ONLY_ACTIONS` 中剔除 | 监听面与主机拓扑信息不该出现在任何子 Agent 的可选动作里 |
| B4 | 无流量载荷捕获 | `payload_captured` 固定 `false`；只出 IP/端口/协议/状态/计数 | 抓包会把业务载荷（含用户数据）落到磁盘，与隐私禁写清单冲突 |
| B5 | 授权渗透双人门禁 | 申请人自批必须 403，须另一评审员/管理员批准时间窗 | 生产渗透的既有硬门；单方面解除会让"授权"退化为自我授权 |
| B6 | 内部安全动作不能在聊天里下发 | `INTERNAL_SECURITY_ACTIONS` 在 `agent_responses_service._execute_operation` 里直接拒绝 | 配置与解封必须走安全中心页面，保留操作者与原因 |

### C 类：环境性限制（现状事实，非平台设定）

- 生产 MySQL 只监听 `127.0.0.1:3307`，Redis/ClamAV 只在容器网络内 → 外部端口探测均为 closed，
  这是既有的服务收敛结果，不要为了"能扫到"而重新对外暴露。
- 云侧安全组与宿主 `YJ-FIREWALL-INPUT` 链共存；改动云安全组属平台外操作（此前记录为"暂不改 8888"）。
- 本地 `deploy/.env` 的生产配置停留在 `APP_VERSION=4.0.35`，与运行中的 4.0.50 不一致，
  仅影响 `deploy/.env` 直读脚本的显示，不影响容器实际环境变量。建议发布 v4.0.51 时一并校正。

## 三、本轮实际执行的能力变更

1. 安全中心新增「溯源与响应」分区：单来源溯源、防御面审计、流量元数据三张只读卡，
   `require_super_admin` 守卫，前端在 `available !== true` 时只出错误条与重试。
2. 宿主机新增三个只读动作，与既有 root 执行器同 socket、同鉴权、同账本；
   `ops_service` 层补参数校验（单 IP、1–72 小时窗口）。
3. 新增 `TEAM_READ_ONLY_ACTIONS`：内部安全动作**从**团队/网格只读清单里移除（收紧，不是放开）。
4. 未安装任何软件、未开启任何新端口、未对任何第三方地址发起请求、未改动封禁策略。
