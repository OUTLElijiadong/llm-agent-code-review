# 页面任务完成判定专项修复与复验

观察日期：2026-10-15，Asia/Taipei。本轮子代理只使用本地隔离 SQLite、真实注册的站点执行/核验服务和持久工具账本；业务 HTTP 边界使用固定响应替身，没有生产写入、浏览器点击、账号登录或收费模型调用。

根代理在生产真实点击中定位：原页面提交回执为 `completed=false / verification_status=pending`，后续原团队已执行并独立核验完成，父运行仍按最初回执阻止成功结论。本轮未独立重查生产日志，不将该任务上下文当成本轮生产验收。

## 复现和修复范围

原版在 6 个合法完成样本中均被 pending guard 拦截：用户端、管理员端分别读取正常大小和较大论坛结果，以及两端发布后同目标读回。初始红测为 **6 失败、38 通过**；通过的 38 项是应拒绝的隔离或证据不足场景。

完成判定改为检查同一轮原提交的持久证据链：

1. 当前运行、账号、调用 ID、工具及完整参数与 `AgentToolExecution` 相符，且该原提交账本明确绑定原团队 ID。
2. 原团队属于同账号、同 surface、同 session，真实状态为 completed；不接受另一团队或公共 `get_agent_team` 投影充当完成证据。
3. 自动创建的固定 execute/verify 图保持原输入、原依赖；执行和独立核验节点均完成，成员职责与 `agent:site_operator` 地址吻合。
4. 原业务执行结果对应同账号、同团队、同任务的成功工具账本；核验回执的能力、参数、请求、完整输出保持一致，服务端 page_action.phase 为 completed，账号与目标路由正确。
5. 有对应 GET 时要求真实读回回执，读取能力与目标匹配，GET 条目和分页一致；无 GET 的同步命令只沿用已有 `synchronous_api_receipt_only` 口径，不冒充页面状态验收。

管理员逐调用的写入证据同样根据上述原团队证据临时升级判定。原提交回执仍保持 pending 的历史事实，不回写为成功，不发起新的业务 API、不重复提交团队，也不取消历史失败数据。团队 trace_id 由创建服务生成独立 team_* 标识，不能假设它等于父 run_id；原运行通过提交账本的 request_id/run_id/call_id 绑定。

新增的解除路径在首次实现中还有一个本地边界错误：同 call_id 的冲突重复 output 可借用另一条核验证据。扩展红测 **1 失败**复现后，增加冲突调用/输出去信任。这是本轮实现复验发现并已修正的缺陷，未确认它曾在生产发生。

## 独立复核后再次修复（2026-10-15）

上面的 109 项是第一阶段本地记录。独立复核随后提供 7 个新增场景，初版修复仍有 **6 失败、1 通过**，本代理重新执行原独立用例确认同样结果后继续修复；没有把先前局部通过当成最终完成。

已确认并修正的本地边界：

- 管理员新一轮明确只读时，旧 pin 的 pending 账本仍影响答复。管理写调用与输出证据统一限定最新 user 轮次；只清除独立完整的否定写入子句，不清除同句或后续真实删除要求。
- Python 的 `True == 1 == 1.0` 使原 task 参数或读回快照类型变化被当作相等。原调用、固定 task 输入、原执行回执与独立读回快照改用精确 JSON 比较；API 已依法规范化的字段与原请求之间沿用站点核验已有语义。两端原参数/任务都是 1.0、原 API 输出与读回都是整数 1 的合法规范化样本通过。
- 公共 checkpoint 标记 completed=true 时，原 team 仍 queued 可被跳过。所有本轮 capability 完成声明都必须有对应可信原调用账本；排队团队不再由公开标志解除。确属主会话同步 API 的回执额外核对当前账号、surface、session 的运行元数据，只查询必要字段。
- “没有失败”被旧失败识别误判，可压住后面的真实完成声明；“不能说操作失败”还跨标点压住后一句的成功检测。针对已复现有限语料剔除否定失败短语、限制成功否定前缀跨标点，并识别明确“任务执行失败，未能完成业务操作”。真实失败、诚实等待和仅客户端观察仍能如实答复。
