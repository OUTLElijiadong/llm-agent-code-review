# 04 · 数据库设计文档

> 本文给出完整的数据库设计:ER 关系、表结构、字段说明、索引、约束、初始数据。所有 DDL 可直接执行(MySQL 8.0)。

## 1. 数据库总览

- **数据库名**:`code_review`
- **字符集**:`utf8mb4`
- **排序规则**:`utf8mb4_unicode_ci`
- **存储引擎**:`InnoDB`
- **表前缀**:无
- **主键策略**:`BIGINT AUTO_INCREMENT`,字段名统一 `id`
- **公共字段**:`create_time DATETIME`, `update_time DATETIME`(关键表),`status` 软删除
- **命名风格**:全小写下划线;表名单数(`user` 而非 `users`)

## 2. ER 关系图(文字版)

```
┌─────────┐ 1     n ┌─────────┐ 1   n ┌────────────┐
│  user   │────────▶│ project │──────▶│ code_file  │
└─────────┘         └─────────┘       └────────────┘
     │                  │                     │ 1
     │                  │                     │
     │                  │                     ▼ n
     │                  │              ┌────────────┐
     │                  │              │code_version│
     │                  │              └────────────┘
     │                  │
     │ 1                ▼ 1
     │           ┌──────────────┐
     │      n    │ review_task  │ n  1 ┌──────────────┐
     ├──────────▶│              │◀──────┤review_rule  │ (规则 m:n,通过 task_rule 关联或直接快照)
     │           └──────────────┘       └──────────────┘
     │                  │
     │                  │ 1
     │                  ▼ n
     │           ┌──────────────┐         ┌─────────────┐
     │           │ review_issue │         │ ai_call_log │ 1 ─── 1 review_task / chunk
     │           └──────────────┘         └─────────────┘
     │
     │ 1              n                    ┌──────────────┐
     ├───────────────────────────────────▶│  audit_log   │ (user 操作审计)
     │                                    └──────────────┘
     │ 1                                       n
     └───────────────────────────────────────▶  (user_id 出现在多张表中,做归属过滤)
```

主要关系:
- `user 1:n project`:一个用户多个项目
- `project 1:n code_file`:一个项目多个代码文件
- `code_file 1:n code_version`:一个文件多个历史版本
- `project 1:n review_task`:一个项目可多次审查
- `review_task n:m code_file`:一次审查可覆盖多个文件，通过 `review_task_file` 持久化关联
- `review_task 1:n review_issue`:一次审查产出多个问题
- `review_task 1:n ai_call_log`:一次审查产生多次 LLM 调用
- `review_rule n:1 user`:每条规则归属一个用户(管理员维护全局规则的 user_id=NULL 或 1)
- `user 1:n audit_log`:一个用户产生多条审计日志(系统操作为 NULL)

### 3.2 用户表 `user`

```sql
CREATE TABLE IF NOT EXISTS user (
    id           BIGINT       NOT NULL AUTO_INCREMENT COMMENT '主键',
    username     VARCHAR(50)  NOT NULL                COMMENT '用户名',
    password     VARCHAR(255) NOT NULL                COMMENT 'bcrypt 加密',
    email        VARCHAR(100) DEFAULT NULL            COMMENT '邮箱',
    nickname     VARCHAR(50)  DEFAULT NULL            COMMENT '昵称',
    role         VARCHAR(20)  NOT NULL DEFAULT 'user' COMMENT 'admin/user/reviewer',
    status       TINYINT      NOT NULL DEFAULT 1      COMMENT '1=启用,0=禁用',
    last_login   DATETIME     DEFAULT NULL            COMMENT '最后登录时间',
    create_time  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_username (username),
    KEY idx_status (status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表';
```

### 3.7.1 审查任务文件关联表 `review_task_file`

```sql
CREATE TABLE IF NOT EXISTS review_task_file (
    id           BIGINT   NOT NULL AUTO_INCREMENT,
    task_id      BIGINT   NOT NULL,
    file_id      BIGINT   NOT NULL,
    create_time  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_task_file (task_id, file_id),
    KEY idx_task (task_id),
    KEY idx_file (file_id)
```

用途:
- 持久化一次审查覆盖的全部文件，避免报告、圆桌讨论和任务详情只能依赖单文件字段或临时上下文。
- 多文件审查写入任务时同步写入关联；删除合成任务或文件时按 `task_id/file_id` 精确清理关联。

## 4. 索引设计与查询模式

### 4.1 高频查询与对应索引

| 查询场景 | SQL 示意 | 命中索引 |
| --- | --- | --- |
| 用户列表自己的项目 | `WHERE user_id=? AND status='active' ORDER BY create_time DESC` | `idx_user_status` + `idx_create_time` |
| 项目下的代码文件 | `WHERE project_id=? AND status='active'` | `idx_project_status` |
| 文件历史版本 | `WHERE file_id=? ORDER BY version_no DESC` | `uk_file_version` |
| 审查任务文件集合 | `WHERE task_id=?` 或 `WHERE file_id=?` | `idx_task` / `idx_file` |
| 用户审查记录 | `WHERE user_id=? ORDER BY create_time DESC LIMIT 20` | `idx_user_create` |
| 任务问题列表(按严重程度) | `WHERE task_id=? AND severity='严重'` | `idx_task_severity` |
| 任务未修复问题 | `WHERE task_id=? AND status='unfixed'` | `idx_task_status` |
| 仪表盘问题类型聚合 | `WHERE user_id 范围 GROUP BY issue_type` | 走 `idx_task_severity`+回表 |

### 4.2 不建索引的字段

- 所有 `LONGTEXT` 字段(`content`, `response`, `prompt`, `fixed_code`)
- `description / suggestion / summary` 等长文本

### 4.3 反范式与冗余

| 字段 | 来源 | 原因 |
| --- | --- | --- |
| `review_issue.file_name` | `code_file.file_name` 冗余 | 报告导出/列表无需 JOIN |
| `review_task.total_issues / severe_issues / ...` | `review_issue` 聚合 | 列表展示避免 GROUP BY |
| `review_task.rules_snapshot` | `review_rule` 快照 | 审查后规则被修改时仍可还原现场 |

冗余字段在 Service 层由"写 issue 后增量更新"维护,避免 trigger。

## 5. 约束与一致性

### 5.1 外键策略

为了演示与维护方便,**逻辑外键**约束在应用层做,**物理外键**不创建。理由:

- 软删除场景下物理外键容易锁冲突
- Alembic 迁移更平滑
- 本地系统并发低,无强一致性压力

如需更严格,可在 `init.sql` 末尾追加:

```sql
-- ALTER TABLE project ADD CONSTRAINT fk_project_user FOREIGN KEY (user_id) REFERENCES user(id);
-- ALTER TABLE code_file ADD CONSTRAINT fk_file_project FOREIGN KEY (project_id) REFERENCES project(id);
-- ...
```

### 5.2 事务边界

| 操作 | 事务范围 |
| --- | --- |
| 注册 | 单条 INSERT,不需要 |
| 上传代码 | `INSERT code_file + INSERT code_version` 一个事务 |
| 保存代码(更新) | `UPDATE code_file + INSERT code_version + UPDATE version_no` 一个事务 |
| 单文件审查写问题 | 一个文件一次提交;每写一批 issues 后 commit |
| 任务收尾 | 计算统计字段并更新 `review_task` 一个事务 |

## 8. 字段字典(关键字段速查)

### 8.1 `review_task.status`

| 值 | 含义 |
| --- | --- |
| `pending` | 任务已创建,尚未开始执行 |
| `running` | 正在调用 LLM |
| `success` | 全部成功结束 |
| `failed` | 整体失败(如所有文件都报错) |
| `cancelled` | 用户主动取消 |

### 8.2 `review_issue.severity`

| 值 | 含义 | 评分扣分(参考) |
| --- | --- | --- |
| `严重` | 安全漏洞、严重崩溃风险 | -15 |
| `高` | 明显逻辑错误、性能瓶颈 | -8 |
| `中` | 规范、可维护性 | -3 |
| `低` | 风格、注释 | -1 |

综合评分 = max(0, 100 - Σ 各问题扣分),上限 100,下限 0。

### 8.3 `review_issue.issue_type`

字符串枚举(对应 8 条内置规则):

```
代码规范 / 潜在Bug / 安全漏洞 / 性能问题 / 异常处理 / 命名规范 / 可维护性 / 注释完整性 / 其他
```

### 8.4 `review_issue.status`

| 值 | 含义 |
| --- | --- |
| `unfixed` | 未修复(默认) |
| `fixed` | 已修复 |
| `ignored` | 已忽略,不计入下次报告 |
| `pending_review` | 待复查 |
