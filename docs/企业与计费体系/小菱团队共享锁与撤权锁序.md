# 小菱团队共享锁与撤权锁序

## 本轮修复

企业小菱计费归属在小组会话校验中只读取小组状态，但旧实现先由团队路径持有小组共享锁，随后 `billing_group.capture` 再请求同一小组排他锁。隔离 MySQL 8.0.45、REPEATABLE READ 下，两个同组 v1 团队通过真实 `_lock_live_context(lock_company=False)` 同时执行时，复现共享锁升级导致 MySQL 1213。已将 `capture` 的小组行读取改为共享当前读，企业成员和小组成员仍保留原有排他当前读；小组停用仍需等待共享锁，未扩大成员的写权限。

该红测使用合成的 v1 小组运行记录；当前正常新建小组运行仍为 v0，不能据此声称正常小组运行已走入 v1。相关真实 team/run/task 构造、角色快照与额度部分测试桩及其边界见 `backend/tests/test_mysql_enterprise_group_shared_lock.py`。

隔离 MySQL 回归：11 项通过、3 项严格 xfail；另外 SQLite 归属/版本/迁移组合 15 项通过。MySQL 测试覆盖：两名同组成员 v1 同时进入真实团队运行上下文、成员移除和小组禁用先后、旧 RR 快照、跨企业拒绝、关闭 v1 开关；原有无组/公司群、独立成员共享读和小组状态变更等待也一并验证。锁等待使用 `performance_schema` 实测。测试额度/订阅和部分角色快照有桩；未调用真实供应商，也未对生产做负载或权限验收。

## 实测未解决问题

1. **已解决同企业独立成员发送被企业排他锁串行的问题**：`_live_role_snapshot` 现以企业行共享当前读校验并持有企业状态；企业停用、角色/成员变更和退款仍须排他锁，因此仍会等待在途受保护操作。隔离 MySQL 用 `performance_schema` 验证两个独立成员可以同时通过团队授权；原 `strict xfail` 已删除并转为必须通过的回归。`send_guard` 仍会持有运行、成员/小组、团队/任务授权行直到同步 provider callable 返回；本地实测未覆盖生产负载、超长连接或取消延迟。
2. **历史死锁根因已由下方团队锁序局部修复**：旧实现先锁成员/小组、后锁企业，而 `remove_group_member` 先锁企业、再锁成员，正常 v0 记录下曾在 MySQL RR 复现 1213；单独提前企业锁又会与 parent run/runtime recovery 形成锁环。当前 `_lock_live_context` 和 `cancel_team` 采用 parent run→runtime state→enterprise→member/group→team/task 顺序，相关正反竞争已由隔离 MySQL 验证。

### 团队锁序的局部修复（本地）

`_lock_live_context` 和 `cancel_team` 现按 parent run→runtime state→enterprise→member/group→team/task 获取相关行。真实角色快照使用企业行共享当前读；发送期间组织写入仍被阻挡，不同成员的发送读可并行。其他显式以 `lock_company=True` 进入的短事务仍会持企业排他锁。修改不代表退款与供应商发送已形成完整资金互斥。

隔离 MySQL 先红后绿的真实入口测试见 `backend/tests/test_mysql_enterprise_team_lock_order_repair.py`：撤权先取得企业锁时团队拒绝、团队和取消争用父运行、真实 `retry_run` 与团队运行两种锁先后顺序按原状态拒绝或继续；团队持锁先行时，移组、企业停用、真实账号停用服务、小组停用分别等待，提交后下一次团队授权拒绝。真实退出登录服务也等待用户行；但历史 v0 团队按账号当前状态及角色授权，退出后 token_version 变化不会单独阻止其后台执行，不能将其描述为退出即停止任务。角色快照使用真实实现，订阅及额度检查使用测试桩；退款及真实供应商不在这些新增测试的覆盖范围中。此前两项只复现旧锁序的 strict xfail 已由上述正反回归替代；原先仅用于说明“提前企业锁但不先锁运行会死锁”的历史探针未作为现行实现的验收。

此前阶段 MySQL 选择性组合和 SQLite 服务结果均为历史快照，不能与下方新复验累加；按当时的筛选未运行测试也不算覆盖。

独立复核另在一次性 MySQL 8.0.45 上验证：真实角色快照下，成员撤权先提交则旧团队事务拒绝，团队先持锁时撤权等待企业行、随后按序完成；按 `_claim_new_invocation` 的真实 `run→state→enterprise` 锁定前缀模拟两种先后均无 1213；旧快照下父运行已取消、企业已暂停均拒绝。与团队归属/预览测试合并为 **14 项通过、1 项 strict xfail**。这些独立样本中的 claim 是真实锁定前缀，并非完整重试 HTTP；额度和订阅检查使用桩，未验证供应商发送或退款互斥。其同企业串行 xfail 已由共享企业锁改造后的新回归取代；临时探针 `/tmp/prism_unified_lock_independent.py` 的旧阶段结果仅保留为历史证据，独占容器已删除。

锁序仍需覆盖支付订单/退款/钱包及沙箱；企业共享行读只阻止企业状态/权限写入越过在途操作，不证明资金与供应商副作用原子互斥。实际退款可在企业授权锁期间进入处理中，故企业行本身不能证明退款与发送互斥。相关证据见 `test_mysql_company_shared_lock_does_not_fence_real_subscription_refund` 及未来周期退款探针；退款互斥原型不等于已接入。

## 交付与门禁

本地已修复小组行锁升级、团队锁序反转和团队授权持企业排他锁导致的不同成员串行；剩余关键风险是其他路径潜在锁序、退款互斥和真实供应商整链。应继续验证退款与发送、上游断连/取消、成员撤权、企业停用、项目/会话跨租户、重复请求及锁等待两个先后顺序；现有运行 v0 与新 v1 的行为都需覆盖。真正安全方案需要使用真实模型传输或本地受控 HTTP、真实账本与退款事务，而不是仅替换角色或订阅判断为桩。

在上述竞争安全、负载容量和退款互斥未闭合前，不得开放相关计费归属功能或以健康检查替代真实业务验收；`_CROSS_SCOPE_ATTRIBUTION_VERIFIED` 应维持关闭。
