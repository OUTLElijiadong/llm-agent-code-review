# 小菱团队共享锁与撤权锁序

## 本轮修复

企业小菱计费归属在小组会话校验中只读取小组状态，但旧实现先由团队路径持有小组共享锁，随后 `billing_group.capture` 再请求同一小组排他锁。隔离 MySQL 8.0.45、REPEATABLE READ 下，两个同组 v1 团队通过真实 `_lock_live_context(lock_company=False)` 同时执行时，复现共享锁升级导致 MySQL 1213。已将 `capture` 的小组行读取改为共享当前读，企业成员和小组成员仍保留原有排他当前读；小组停用仍需等待共享锁，未扩大成员的写权限。

该红测使用合成的 v1 小组运行记录；当前正常新建小组运行仍为 v0，不能据此声称正常小组运行已走入 v1。相关真实 team/run/task 构造、角色快照与额度部分测试桩及其边界见 `backend/tests/test_mysql_enterprise_group_shared_lock.py`。

隔离 MySQL 回归：11 项通过、3 项严格 xfail；另外 SQLite 归属/版本/迁移组合 15 项通过。MySQL 测试覆盖：两名同组成员 v1 同时进入真实团队运行上下文、成员移除和小组禁用先后、旧 RR 快照、跨企业拒绝、关闭 v1 开关；原有无组/公司群、独立成员共享读和小组状态变更等待也一并验证。锁等待使用 `performance_schema` 实测。测试额度/订阅和部分角色快照有桩；未调用真实供应商，也未对生产做负载或权限验收。

## 实测未解决问题

1. 真实团队 `_lock_live_context(lock_company=False)` 在 `_live_role_snapshot` 内仍取得企业 X 锁，不同成员的不同团队会等待企业行。strict xfail `test_live_team_authorization_does_not_serialize_independent_members` 只接受已观测 `enterprise` 行等待的专用异常；其他失败不被隐藏。受测试链路的发送守卫会持事务等待上游，故该锁的真实持有时长需实际整链验证。
2. 原真实团队先锁成员/小组、后锁企业；真实 `remove_group_member` 先锁企业、再锁成员。在正常 v0 小组记录上，隔离 MySQL 实测 MySQL 1213。另经 monkeypatch 验证，仅将企业锁提前会与 `run/state→enterprise` 的恢复路径形成新的锁环。

### 团队锁序的局部修复（本地，待独立复核）

`_lock_live_context` 和 `cancel_team` 现按 parent run→runtime state→enterprise→member/group→team/task 获取相关行。企业 X 锁未删除：原来 `_live_role_snapshot` 就会在团队事务中取得该锁，现在只是放到成员行之前；因此同企业串行仍然存在，新的归属付费门禁仍关闭。修改也不代表退款与供应商发送已形成互斥。

隔离 MySQL 先红后绿的真实入口测试见 `backend/tests/test_mysql_enterprise_team_lock_order_repair.py`：撤权先取得企业锁时团队拒绝、团队和取消争用父运行、真实 `retry_run` 与团队运行两种锁先后顺序按原状态拒绝或继续；团队持锁先行时，移组、企业停用、真实账号停用服务、小组停用分别等待，提交后下一次团队授权拒绝。真实退出登录服务也等待用户行；但历史 v0 团队按账号当前状态及角色授权，退出后 token_version 变化不会单独阻止其后台执行，不能将其描述为退出即停止任务。角色快照使用真实实现，订阅及额度检查使用测试桩；退款及真实供应商不在这些新增测试的覆盖范围中。此前两项只复现旧锁序的 strict xfail 已由上述正反回归替代；原先仅用于说明“提前企业锁但不先锁运行会死锁”的历史探针未作为现行实现的验收。

本地最终阶段组合：隔离 MySQL 与团队、聊天权限和退款检查相关的指定用例 **40 项通过、1 项 strict xfail、88 项按筛选未运行**，企业账户及团队相关 SQLite 服务 **113 项通过**，目标 Ruff 和 `git diff --check` 通过。另一次完整包含所有发送锁探针的组合为 **34 项通过、1 项 strict xfail**（该次早于增加真实退出登录对照）；临时容器已停止。两组包含重叠用例，不能相加作为不重复的测试总量。尚需独立代码复核和最终后端全量。

独立复核另在一次性 MySQL 8.0.45 上验证：真实角色快照下，成员撤权先提交则旧团队事务拒绝，团队先持锁时撤权等待企业行、随后按序完成；按 `_claim_new_invocation` 的真实 `run→state→enterprise` 锁定前缀模拟两种先后均无 1213；旧快照下父运行已取消、企业已暂停均拒绝。与团队归属/预览测试合并为 **14 项通过、1 项 strict xfail**。这些独立样本中的 claim 是真实锁定前缀，并非完整重试 HTTP；额度和订阅检查使用桩，未验证供应商发送或退款互斥。真实同企业不同团队仍受企业 X 锁串行，不能把该 xfail 当通过。测试使用临时探针 `/tmp/prism_unified_lock_independent.py`，独占容器已删除。

剩余串行 xfail 使用 `strict=True` 和具体异常类型；未建立隔离库、种子错误、未观测预期锁、等待超时或其他异常不能被当成预期问题。锁序仍需覆盖支付订单/退款/钱包及沙箱；不得仅将企业锁改为共享读或无锁。实际退款可在企业共享锁期间进入处理中，故企业行本身不能证明退款与发送互斥。其已复现实验证据见 `test_mysql_company_shared_lock_does_not_fence_real_subscription_refund` 及未来周期退款探针；退款互斥原型不等于已接入。

## 交付与门禁

本轮本地修复了重复读取时的小组锁升级和上列两个已复现团队锁序反转；企业锁串行、其他路径的潜在锁序、退款互斥和真实供应商整链仍未解决。应继续验证退款与发送、上游断连/取消、成员撤权、企业停用、项目/会话跨租户、重复请求及锁等待两个先后顺序；现有运行 v0 与新 v1 的行为都需覆盖。真正安全方案需要使用真实模型传输或本地受控 HTTP、真实账本与退款事务，而不是仅替换角色或订阅判断为桩。

在上述竞争安全、负载容量和退款互斥未闭合前，不得开放相关计费归属功能或以健康检查替代真实业务验收；`_CROSS_SCOPE_ATTRIBUTION_VERIFIED` 应维持关闭。
