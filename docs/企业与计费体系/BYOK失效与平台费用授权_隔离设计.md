# BYOK 失效与平台费用授权：隔离设计

状态：设计草稿，尚未实现、迁移或上线。当前生产状态不在本文件中推断。适用范围是用户自带模型密钥失效后平台托管模型可能产生的费用；平台管理员成本中心与个人、企业钱包各有独立成本主体，不得互相代扣。

## 现有路径和已复现事实

- `user_api_config` 每用户至多一行，`is_active` 只有布尔值，不记录停用原因或用户对后续费用的选择。
- `api_config_service.get_config` 和 `api_resolver.resolve_api_config` 在解密失败时都会把已配置行设为 inactive 并提交；后者只查询 active 行。隔离红测证明：在自动停用后再次解析，或先读取配置再首次解析，`billing_credential_source` 可由 `fallback` 丢失为 `system`。此证据不证明线上发生扣费。
- 用户通过 `DELETE /api-config` 主动删除行，现有接口承诺恢复系统默认；没有自定义行的用户同样使用系统默认。两种选择不能被当作系统自动停用。已有 inactive 历史行可能来自其他路径，无法仅凭布尔值恢复真实原因。
- `PUT /api-config` 保存并启用新的用户配置。视觉请求当前可从用户配置切换为平台配置；其他审查、个人 Agent 和 Responses 等路径也调用 resolver。设计必须覆盖所有实际发包入口，不能仅修管理员单页。
- 全局配置解析失效有自己的 `billing_eligible` 回退信号；它不是用户主动选择，也不能用普通用户的 BYOK 状态覆盖。配置解密、轮换及读取可能提交会话，需专门处理事务归属。

## 目标状态与业务语义

持久记录“系统自动停用/状态未知导致的费用归属待用户确认”与普通来源选择分开。它只能决定能否继续选择平台托管调用，不能替代现有真实钱包、管理员成本中心、费率、额度、组织权限、发送所有权或服务端审批。自带 Key 的有效调用仍按其实际凭据来源走原有路径。

建议以用户稳定身份建立独立持久策略记录，不依赖可能被用户删除的配置行；字段至少包括状态（正常、故障待确认、历史未知待确认）、变更代次、来源配置版本、变更时间和有限原因码。不得保存明文密钥或其低熵摘要。用户配置本身增加乐观并发版本；所有发包侧以当前读获取对应策略及最终凭据身份，再由正确财务主体执行原有门。字段及最终表结构需在迁移设计审查后确定，这里不是可运行迁移。

| 情况 | 来源与平台付费处理 |
| --- | --- |
| 历史上没有自定义配置行 | 保留既有系统默认选择；仍执行原钱包、权限和费率门，不新增凭空的购买或扣费授权。 |
| 当前有效自带 Key | 按实际用户凭据处理；不得把平台成本主体伪装成用户 Key。 |
| 系统确认有效配置解密失败、校验失败或轮换持久化失败 | 在同一受控事务中，以配置版本条件写入故障待确认，并停用对应旧版本；平台托管付费发送前拒绝或进入明确选择。不能只把 `is_active` 改为 false。 |
| 用户主动删除现有自定义配置 | 保持删除配置并恢复系统默认的既有动作；同一受控事务记录用户明确选择了系统来源。**该来源选择不等于接受新价格、同意扣费或授予新的财务权限**，仍须执行实际费用、预算、权限和必要的确认流程。不能将后台清理、错误路径或伪造请求当成用户选择。 |
| 历史 inactive 行 | 标记历史未知，不猜测其被停用的原因。遇到需要平台托管付费的请求时在发包前请求明确选择；不影响无付费风险的只读页面。历史未知不等于已经产生欠费。 |
| 用户保存新 Key | 原子记录新配置版本；**保存成功不等于供应商已验证 Key 有效**。是否清除旧故障标志须依据已定义的用户选择与实际调用来源，不能把新 Key 的保存等同于同意平台付费。用户主动发起的第三方网络测试与保存互相独立，其结果不能替代保存事务或权限校验。 |
| 视觉、模型回退或子 Agent 从用户 Key 切到平台 Key | 对实际最终来源再次校验用户选择与正确成本主体；不能从原用户 Key 推断平台付费已授权。系统主动回退失败关闭，除非该次或约定范围内的选择明确且仍有效。 |

前端只在确需选择时明确展示实际成本主体和动作：修复个人 Key，或选择使用平台配置。个人/企业/平台费用的实际承担者由服务端基于当前会话和权限确定；浏览器传入的主体或价格不可信。对于平台管理员系统运营预算，现有平台职责可以决定其合规流程，但不能静默使用管理员个人余额。

## 原子性与并发

先定义全路径一致的锁序，至少覆盖稳定用户策略、配置版本、运行所有权、成本主体/预算与 attempt。必须以独立事务边界说明哪个操作提交，不能在调用者会话里意外提交其他待修改对象；读取接口现有自动停用属于状态变更，需迁移到统一服务并保留兼容响应。

读取、解密发生在并发写入之前时，使用旧配置版本的解密失败结果不得停用或覆盖另一个请求刚保存的新 Key。条件更新失败须重新读取并重新判断，不得复用旧明文、旧原因、旧审批或旧费用授权。用户删除、重新配置、确认平台来源、后台轮换与发包在提交前必须校验同一代次；异常、撤权、配置发生变化、提交不确定时拒绝未发送请求。已发送或无法确定是否发送的请求继续保留原有冻结，不能借来源变更释放或自动重发。

独立后台/恢复 worker、缓存的 `ApiConfig`、子 Agent 配置复制和平台视觉替换，都必须在最终发送前执行同一受保护校验；只在 resolver 最初读取时校验无法防止后续并发更改。消费者必须兼容系统配置或用户配置不存在，不能把配置来源作为身份认证。

## 迁移、兼容与验证门

本分支以 `121_billing_model_evidence` 为基线；另有公开 WIP revision `122_assistant_call_owner`。正式修复须使用不冲突的新 revision，明确保留原 122 的身份和唯一 head/合流顺序。121 状态下 revision 看似未变也不能排除部分 MySQL DDL；发布与回滚必须检查真实结构、迁移标记与镜像兼容。不得重写现有 revision 或以 `stamp` 假装迁移成功。

增量迁移不得修改或删除原密钥；历史 inactive 行只能归类 `unknown`，没有行与 inactive 行必须区分。上线须先证明所有旧 worker、配置读写者和缓存无法绕过新门；不兼容旧镜像不得在新策略存在时继续写入。对 DDL 中断、双写窗口、回滚、数据库备份及完整隔离恢复分别验证；源表与策略的对账不能单凭行数。保留原 API 对主动删除的行为，新增澄清必须不暗中创建账单。

至少覆盖：有效用户 Key、无自定义配置、用户主动删除、已知故障停用、历史未知 inactive、配置页先读、连续运行、全局配置失效、视觉替换、管理员/企业/个人三种主体、权限撤销、删除/保存与发送竞争、Key 轮换、旧 worker、双会话 MySQL 重复读与进程重启。校验无授权时 HTTP 前零发送、零预占；已发送/未知维持冻结。主机级/供应商故障以及真实账户和账单验收需独立记录；模拟通过不能解除销售和生产门。

并发验收需单列：不同会话和进程读取并更改同一用户策略；旧配置的解密失败与新 Key 保存竞争，两种提交顺序均不得停用或覆盖新版本；用户撤销来源选择或财务授权后，新请求在 HTTP 前零预占、零发送。此前已提交的测试只有 SQLite 的来源选择基线，不覆盖这些并发与撤权条件。
