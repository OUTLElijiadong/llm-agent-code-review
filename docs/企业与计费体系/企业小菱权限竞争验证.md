# 企业小菱权限竞争验证（2026-11-08）

## 问题和修复

MySQL 的 REPEATABLE READ 事务若先读取了账本等数据，再等待企业锁，普通读取仍沿用旧快照。原实现可能在会话历史发言人的企业角色、组关系或账号状态变化后，继续使用旧优先级并发布过期结果。

继续执行和最终发布时，服务端先锁企业行，再按用户 ID 稳定排序锁定并读取会话涉及的账号、企业成员及小组成员，最后与运行时保存的权限摘要比较。组织权限更改沿用企业行在前的锁序；账号禁用与相应账号行锁互斥。权限变化时不执行后续工具，并抑制结果；发布先取得锁时，后来的变更等待该事务结束。

## 隔离验证

- 使用独立一次性 MySQL 8.0.45 空库，执行正式初始脚本和全部本地迁移后测试；未使用生产数据。
- 4 个撤权先完成的发布用例先复现旧答案被发布，再验证修复后均被抑制：移出小组、移出企业、企业角色降级、账号禁用。另 4 个工具执行入口用例验证旧快照不能继续执行。
- 4 个发布先完成的反向竞争用例通过 `performance_schema.data_lock_waits` 确认后续权限变更实际等待锁，再依次完成。共 **12 项通过**，重复运行通过。账单状态和订阅检查使用测试桩，模型和真实渠道未调用。
- 企业小菱及关联服务定向 SQLite 测试 **51 项通过**；修改文件 Ruff 通过。未进行真实浏览器、多账号生产和真实模型验收。

自然语言冲突是否存在，以及同级冲突时模型是否调用澄清工具，仍依赖模型理解；当前不能把提示词当成确定性语义仲裁的证明。新消息高权限覆盖旧运行的服务端检查也有明确触发条件，不覆盖所有未 @ 小菱 的消息。
