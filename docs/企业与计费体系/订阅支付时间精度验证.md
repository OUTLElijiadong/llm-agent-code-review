# 订阅支付时间精度验证

## 范围与现象

本次只涉及当前任务工作树的企业席位和审查员月度订阅；没有部署生产、连接真实商户或改写历史订单、周期和账本。

隔离 MySQL 8.0.45 中，`billing_subscription_period.starts_at` 为 `DATETIME(0)`。支付时刻微秒达到 500000 时，数据库默认会将周期起点四舍五入到下一秒；立即发放时，当前锁读刷新出较晚的起点，而服务仍用原始微秒支付时间比较，因而误判周期尚未开始。跨 UTC 日末会变成下一日。真实业务路径是否在线上触发、后台周期调度是否后来补发，本次未验证。

## 修改与边界

- 创建新订阅或在过期后重新锚定时，将新周期的 UTC 锚点和起点向下规范到整秒，再据此计算月度结束边界；及时发放不再受 MySQL 舍入影响。这种新锚点相对精确支付时刻最多提前不足一秒，数据库精度和月周期的可见语义明确一致。
- 原始 `paid_at` 仍用于支付记录赋值、激活的当前时间和已有订阅宽限期比较；不把周期起点当作支付凭证，不更改历史订单、周期或账本。SQLite 能保存原始微秒；既有 MySQL `DATETIME(0)` 的支付记录本身仍按数据库规则保存到秒，本次未修改支付证据表精度，不能声称其保存了原始微秒。
- 已有续费紧接前一期结束时继续沿用既有起点和锚点；不迁移或推断旧记录。真实支付验证、账务对账和生产数据副本中的历史缺发修复须另行核验，不能只因新代码正确而自动补发。

## 验证

- 测试先行：隔离 MySQL 原始代码 **5 失败、3 通过**，其中首次支付 `500000`、`900000` 微秒下的审查员与企业周期均未立即发放；重启订阅的起点同样舍入到了下一秒。修改后 [MySQL 精度测试](../../backend/tests/test_mysql_subscription_payment_precision.py) **8 项通过**：覆盖 499999/500000/900000 微秒、跨秒跨日、两种订阅、重复通知、未来续期及其生效时间、宽限期后重启和外层事务回滚。测试走真实服务和账本，但传入合成的已验证交易结果，没有调用支付渠道。
- [SQLite 精度测试](../../backend/tests/unit/services/test_subscription_payment_precision.py) **4 项通过**，覆盖 UTC 与东八区入参、两种订阅、保留 SQLite 付款记录微秒、锚点和月度边界以及即时额度；既有支付与订阅运行时组合 **95 项通过**。
- 一次性 MySQL 中，既有周期激活回滚/并发、双渠道重复支付通知、关闭与支付竞争 **5 项通过**。第一次该组合运行的临时库没有启用 `performance_schema`，导致其中锁等待观察测试失败；重新建立开启该功能的空库后重跑通过。支付验签使用测试替身，不代表真实渠道验收。
- 相关 Ruff 通过。全部后端最终回归、真实商户及生产验收仍待完成；独立审查结果见下节。

## 独立复核

- 另一代理在单独的一次性 MySQL 8.0.45 空库完成基线与当前迁移后，重新运行原精度专项 **8 项通过**。另写独立隔离测试 **8 项通过**：宽限期结束前 1 微秒、恰好结束及后 1 微秒分别在 UTC 与东八区输入下验证；覆盖原周期不变、当前权益、相同通知只发放一次、不同流水冲突拒绝，以及分数秒付款后退款审核时的周期、积分批次到期与冻结关系。测试只通过合成的已验证交易对象调用服务，没有请求支付渠道。
- 独立 SQLite 宽限期边界 **6 项通过**，原 SQLite 付款精度和订阅规则组合 **5 项通过**。临时验证代码位于 `/tmp/test_mysql_prism_precision_independent.py` 和 `/tmp/test_prism_subscription_precision_independent.py`，不属于正式测试套件；临时 MySQL 容器已停止。
- 未发现本次时间规范化的新缺陷。精确处理时间向下取整意味着新周期及到期时间最多提前不足 1 秒；MySQL 的既有付款与验证时间列仍为 `DATETIME(0)`，不保存原微秒。此次测试未核验生产历史缺发数量、真实渠道支付通知、生产数据库或真实退款到账，不能据此视为生产验收。
