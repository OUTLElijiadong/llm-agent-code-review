# 个人渗透执行证据的间隙锁验证

验证时间：2026-11-09（Asia/Taipei）。验证对象是隔离工作树的 111 持久执行证据代码；本地迁移唯一 head 为 `112_quota_history_index`。`_DURABLE_PENTEST_STAGING` 固定关闭，本记录不表示新路径已开放或旧路径已解决。

## 已验证事实

使用独占、无持久挂载的一次性 MySQL 8.0.45，默认 InnoDB `REPEATABLE READ`，从空库执行项目初始化 SQL、种子和完整迁移链。账号、项目、委托及活动均为合成数据；锁等待以 `performance_schema.data_lock_waits` 和对应线程 ID 核验。测试结束后只停止并删除本次容器。

1. **不同项目的活动插入等待。**事务 A 持有本委托与执行行锁，对没有未决活动的执行调用 `_drain_if_recorded_facts_complete` 并保持事务；事务 B 对另一项目、另一执行调用真实 `prepare_activity`。B 在 `pentest_execution_activity.uq_pentest_execution_activity_key` 请求 `X,INSERT_INTENTION`，等待该索引 `supremum pseudo-record` 上的 X 锁；A 回滚后 B 成功。这一隔离探针未完整模拟调用方额外持有的项目锁，但确认该方法的缺行查询可造成跨执行插入等待。
2. **不同项目的新执行插入等待。**事务 A 对仅有 draft 委托、尚无执行记录的项目调用真实 `project_execution_evidence` 并保持事务；事务 B 为另一项目调用 `create_execution`。B 在 `pentest_execution.uq_pentest_execution_generation` 的 `X,INSERT_INTENTION` 等待 `supremum pseudo-record` 上的 X 锁；A 回滚后 B 成功。
3. **同一执行的互斥有必要。**事务 A 按 Project → Engagement → Execution 的顺序持锁，将终态且无未决活动的执行排空；事务 B 为同一执行调用 `prepare_activity`，实际等待 Project 主键行 X 锁。A 提交后 B 按当前执行状态被拒绝，未创建活动。该正向测试 **1 项通过**。
4. **普通旧快照不能作为空活动证明。**事务 A 先建立“无活动”的一致性快照，事务 B 创建并标记 dispatched 活动后提交；A 再依次锁定当前父行时，普通查询仍返回空，而 `_drain_if_recorded_facts_complete` 的当前锁定读发现已提交的活动并拒绝 drained。该测试 **1 项通过**。因此不能直接将当前锁定查询替换为普通 RR 查询。

前两项以“无关项目不应等待”为断言，均在隔离测试中失败；锁等待证明了可用性争用，**不证明已发生死锁、生产负载问题或跨租户数据泄露**。

## 受限候选及边界

独立测试把相关 Session 从第一条 SQL 开始限定为 `READ COMMITTED`：上述两个跨项目插入均不再等待，**2 项通过**；同执行排空与新活动仍在项目主键行互斥，**1 项通过**。这些只是最小事务实验，不证明真实 worker、账号与项目授权、钱包/退款锁序、绑定、连接池复位或跨进程恢复的整体安全。不得据此全站切换隔离级别，也不能在已经执行查询的事务中途安全地假设切换成功。

另一个可研究方向是在已锁定执行父行上维护未决活动的持久计数或引用，并为所有活动创建、状态转换与历史回填提供同事务约束；该方向尚无实现与验证，必须先证明所有写入口、异常回滚、旧数据和数据库外键一致性，不能仅依赖应用约定。

当前保留现有锁定当前读及其安全语义；跨项目等待作为未解决性能问题记录。测试探针位于本机临时文件 `/tmp/prism_activity_gap_probe.py`，不是仓库内持久测试，也不能替代真实生产负载、真实供应商、沙箱或浏览器验收。
