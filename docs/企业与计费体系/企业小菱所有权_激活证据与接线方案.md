# 企业小菱所有权：激活前证据与接线方案

## 当前边界

本文只描述后续工程，不授权启用。独立工作树在 `7ea0c995` 上加入 122 基础表和默认关闭的内部 primitive；现有运行、checkpoint、Search/Fetch、账本和用户接口都还没有接入 owner。即使数据库迁移成功，也不得将其视为同代重入已解决。

旧 worker 不认识新表，也可能已经提交发送标记并停在网络发送前。新代码、数据库代次、租约到期、环境变量、镜像标签或人工口头确认，都不能单独证明旧进程不会迟到发送。外部写入者和已发送请求必须在明确隔离或继续冻结的前提下处理。

## 可自主实现的自动证据

以下均要以**当前目标环境**实测并输出带时间、发布 SHA、镜像 ID、迁移 revision、检查结果及失败原因的机器可读收据；任何查询失败、对象未识别、范围不完整或执行中途变化均为不通过。记录只包含脱敏标识，不记录凭据、owner 明文和用户内容。

1. **数据库与代码身份**：证明目标库唯一 head 是 122，三张 owner 表的列类型、二进制唯一键、检查约束、外键及模型 attempt 不可更改触发器完整；对实际运行镜像而非本地文件核对不可变镜像 ID、源码指纹、运行时版本与 owner 协议版本。现有 121 计费证据兼容探针只证明其固定模块指纹，不证明新 owner 协议；122 必须增加独立探针及篡改负测。现有数据库/迁移图异常、部分迁移、schema 比对失败均拒绝启用。
2. **已知运行实例**：枚举部署编排中所有后端副本、独立队列 worker、定时任务及宿主机服务的进程标识、启动时间、可执行文件/镜像 ID 和启动命令，交叉比对实际网络连接、数据库会话、任务租约与注册实例。先停止所有已知旧版本写入者，再复查编排与进程；发现未知实例、无法读取的命令或旧实例自动重启，拒绝通过。`deploy/deploy.sh` 的 `--confirm-no-external-chat-writers` 是人为声明；`stop_chat_authority_writers` 的 Compose 范围不能证明外部写入者消失，不能直接当作 122 的自动证明。
3. **数据库写入口**：在有权限且不暴露密钥的情况下列出 MySQL 当前连接、账号来源及事务状态，关联到上一步已识别进程；核对应用外账号、外部定时脚本、面板任务及其他服务。需要从网络和数据库权限两端隔离旧凭据，并确认存量会话也已断开；如果多个新旧进程共用无法区分的凭据、存在不能识别的连接、权限不足以看到完整写入范围，自动门应拒绝。进程 PID 和会话 ID 可重用，必须组合机器/容器身份、启动时间、连接建立时间和实际握手版本，不能仅凭一个数字判定。
4. **冻结与对账清单**：先停止新运行领取/外呼、旧写入及触发器入口，再对账本和 owner 做一致快照：枚举 Search/Fetch 与模型的 reserved、unknown、发送标记、已结算但缺结果、未到期租约，以及与这些记录关联的旧运行。输出分类与只读核对结果，不在探针中释放、结算、重试或伪造未发送证据；计费键保持现有格式。旧运行未持有可信 owner 时不自动补发令牌、不用超时推断安全，保留原有账本事实及双人对账流程。
5. **外发隔离和网络事实**：验证已识别旧执行环境的供应商出口被阻断、旧进程已终止且不能由守护服务重启；对于无法强制隔离的第三方 worker/凭据，自动门拒绝。网络连接消失或过了若干秒不等于供应商未接收；提交标记后即使无连接或无响应也保持未知冻结，直到可信供应商证据和既有双人复核可判定。数据库事务提交异常同样可能已提交，必须重新读取真实标记及账单，不得依据异常直接释放。
6. **故障演练与退出**：在独立环境验证停写前后实例/连接清单再次一致，模拟旧进程重启、未知数据库账号、探针超时、半迁移、旧镜像回滚、备份与隔离恢复失败，所有不确定分支不激活并保留冻结。启用后的回滚目标也必须证明能识别 122 owner 与冻结语义；否则停止相关 writer、维持 122 及账本原状、前向修复。122 的 Alembic `downgrade` 明确拒绝，备份恢复须另行隔离演练，不是自动降级。

可自动采集不等于一定能自动证明：没有足够进程、网络和数据库可见性，或无法限制外部凭据时，只能报告具体缺口并保持关闭。不得把配置开关设为开启当作这些证据。

## 不启用条件下的接线设计

### 运行领取与证据

- 在队列、审批、澄清、追问和显式重试各自的现有 `run → state` 锁定领取事务内，检查当前权限、旧状态和未决账本后递增 generation，并在同一事务创建唯一 run owner。`claim_run` 现阶段只认领**已给定的**代次，它不执行上述业务检查或递增，也不能证明旧进程已停；不得直接在历史活跃代次调用。不能先提交 generation 再另开事务领取 owner。
- 每次 driver 独立生成随机凭据，凭据仅在当前进程私有内存传递；不进入 checkpoint、模型上下文、API、日志或事件。数据库只保留摘要；从数据库读取摘要不能构造明文凭据。事务提交前不得启动模型/工具；若提交结果不确定，不重复发起，以新的只读会话查证并停止，不靠重试猜测成功或失败。
- 在 `EnterpriseAssistantCheckpointStore` 的 create/claim/save 以及 `_build_runtime`、`_result_for_runtime`、`_finalize_runtime` 和后台异常收敛中，在各自事务的同一行锁下同时检查 generation 和 run owner；缺 owner 的历史运行不自动获得新凭据。发生非 owner 信号时不得把它转成普通工具错误、可重试状态或聊天消息。

### 每次工具调用与账本

- 每次具体 Search/Fetch 调用用独立工具凭据进行原子首领，调用标识以精确 UTF-8 字节摘要唯一，并复核原始有界字节以检测摘要冲突；参数按现有 `validate_arguments` 规范化后只保存 SHA-256，绑定企业、会话、发起人、冻结组、企业钱包、工具及原有账单键。新的 run owner 不因代次增加而自动重新领取历史同一调用。是否允许基于明确证据建立新的业务调用，应复用双人核账结果，并另行定义不可重放旧请求的合同。
- 在 `enterprise_assistant_runtime_service._execute_search_fetch` 的首次已有预占检查，以及 `billing_search_fetch_service.execute_tool` 的预占/发送标记/返回结果/结算的每个独立事务中校验正确 run owner 和 tool owner。不得只在发送前验一次：`_persist_unknown`、`_finish_unknown`、`_finalize_result` 的异常与恢复路径也可能改账本，失权者必须无写退出；只有被授权的独立恢复流程才可在相同锁序中处理不确定账单。
- 设计并证明完整锁序。基础 `claim_tool` 与 `assert_tool_owner` 现改为在短事务内取得钱包排他锁，`claim_tool` 在插入带钱包外键的记录前加锁；仅修复了下文实测的基础组合，未证明真实账本和对账的完整锁序。仍须对空键索引 gap lock、跨企业/跨钱包并发、重复请求和回调/退款/对账 writer 分别测试，不能仅凭局部锁修改接线。
- 网络发送标记与 HTTP 发包无法组成原子事务。标记可能已提交或旧进程可能迟到发送时，唯一安全默认是停止自动重发并冻结；新 owner、超时、重新部署或无响应都不是“未发送”证据。已成功结果、账单结算及可重放结果必须按现有事务一致保存。

### 非 owner 信号

- 定义专门的内部控制信号及严格边界，不把它包装成 `ToolExecutionResult.failure`。当前 `DeepSeekResponsesRuntime._execute_tool` 的宽泛 `except Exception` 会把异常转换为普通错误，之后 `_process_calls` 会追加 transcript 并 `save`；必须让该信号穿透整个 driver，且不追加输出、不调用模型、不保存共享 checkpoint。
- 检查 `approve`、`resume_clarification`、`answer`、`retry`、队列以及 transport/完成守卫的所有宽泛异常。`execute_queued_run` 当前通用 handler 会更新状态和消息，必须在它之前显式处理该信号；不能用 `BaseException` 逃避正常 finally、连接释放或取消语义。HTTP 响应只能返回当前账号有权观察的安全状态，不暴露 owner/其他会话内容。
- 对非 owner 的只读观察需验证无数据库写入、无账本预占/释放/unknown 变更、无 checkpoint、消息和后续供应商请求。不能用通用失败结果或根据 lease 到期自动接管来代替该合同。

## 分阶段验证与阻断

- **阶段 A：基础，已完成但关闭。** 加表、凭据摘要和受限 claim/assert；MySQL 单一领取、旧数据不动及 SQLite 实际并发/回滚测试。它尚不提供完整的 run/工具 fencing，也不证明旧 worker 已隔离。
- **阶段 B：领取和 checkpoint。** 五个入口分别进行双进程领取、旧 owner 回写、取消与重试竞态；在 SQLite 和真实 MySQL 同时验证事务回滚、旧 RR 快照、lease 到期及调用方事务所有权。
- **阶段 C：工具与账本。** 使用真实 executor 和假供应商，分别暂停在预占前后、标记提交前后、网络发送前后、结算及 checkpoint 保存前；验证非 owner 零写入、HTTP 最多一次、标记提交不确定时冻结，以及不同企业/不同调用并发。再对外部供应商提供的计费及退款合同单独验收。
- **阶段 D：部署和恢复。** 分别验证旧版本混跑阻断、无权枚举时拒绝、外部账号无法隔离时拒绝、数据库/标记提交不确定时拒绝和旧镜像回滚拒绝；执行数据库备份、独立恢复和全量迁移演练。通过后才可提出单独启用评估，不在本阶段打开开关。

## 非持有者中止信号的当前范围

当前只在测试中注入 `NonOwnerAbort`；它尚未连接真实 owner 领取、校验、发送或结算，不构成已启用的所有权保护。已覆盖企业 `_build_runtime` 使用的 `NativeResponsesTransport`、企业工具执行器、Search/Fetch 与团队计费的部分异常和取消传播；其他 Responses 网关、个人工具、其他工具链和其账本路径均未覆盖，不能推定符合无写契约。将来扩展任何网关或工具之前，先对该路径独立复现、补充异常与取消竞态测试，并完成涉及账本、检查点和消息发布的事务内 owner fence。

已测的部分同轮取消与失权不会由旧执行者写入 unknown；普通取消仍按原规则冻结不确定结果。独立复现确认：轮询任务在普通取消后的清理中才抛出失权信号时，Native transport 可能已先写入 unknown；传播信号无法撤销先前写入。后续必须在每次账本状态转换的同一事务里验证 owner，并以此复现场景作为阻断验收，不能仅凭 transport 捕获信号保证安全。旧 worker 和已发请求的隔离证据未就绪前，保持基础开关关闭，禁止自动释放或重新发送可能已发出的请求。

复现用例为 `backend/tests/unit/services/test_non_owner_abort.py::test_late_non_owner_during_cancel_cleanup_must_not_write_unknown`，目前标记为严格预期失败（`xfail(strict=True)`）；执行 `python -m pytest -q --no-cov backend/tests/unit/services/test_non_owner_abort.py -k late_non_owner -rxX` 可查看该阻断。修复后应移除预期失败标记并要求通过，再执行真实 MySQL 竞争验证；测试变成意外通过会使严格模式报错，不能直接据此宣布安全。

本地回归证据：企业 Native transport、运行时取消、团队 guard 与账本等组合测试 318 项通过；其中普通父协程取消后模型不得继续发送的回归，先复现失败再修复。在独立空 MySQL 完整迁移链上，团队注册 guard 的标记前/后注入中止及既有截止时间共 4 项通过。供应商发送由测试替身表示，上述结果不证明真实 owner 接线、进程隔离或供应商并发安全。

## 模型 attempt 的事务围栏：待实施契约

当前流式路径中，`billing_runtime_gate.begin_attempt` 在预占事务中执行 `attempt_guard`；`before_stream_send` 在发送前另开事务；`unknown_attempt` 和 `finish_attempt` 又分别另开事务直接调用账本。`enterprise_assistant_runtime_service._billing_scope` 的 `on_reserved` 设置恢复标记，该标记不能统一证明模型 provider 是否收到请求。同步模型调用还经过 `billing_metered_call` 的正常结算、超时和通用异常处理，团队 guard 的结算与释放分别在 `enterprise_agent_team_dispatcher`、`enterprise_agent_team_runtime_service`；Search/Fetch 则在自身服务及企业工具恢复分支更新。人工对账有专门的授权、复核和恢复路径，不能误套普通执行者凭据，也不能绕开其双人复核。

当前 122 还包含默认关闭的模型 attempt 基础表，但没有建立经过可信 checkpoint 和真实预占事务验证的模型 attempt 绑定。仅用请求键前缀、现有 generation、回调是否触发，或让被调用方提供一个未验证的 guard，都不能证明同代重复者无权操作。未来必须先设计并证明：

1. 在新一代领取同一事务原子创建 run owner；用持久检查点中的不可变模型轮次身份和实际预占记录建立一对一 attempt 绑定，持久化随机 owner 凭据摘要、企业及付款范围和必要的不可变摘要。不同执行者不能取得或重建对方凭据；重启/同代重放不得生成新的等价 attempt。不得保存原始提示词、密钥或 owner 明文。
2. 区分**发送权限检查**与**账务结果所有权检查**：撤权、取消或租约到期应禁止新发送，正常取消已发出或发送状态不明的请求仍须保留 unknown 的现有体验。当前正常取消也会停止运行并递增 generation，不能直接复用会因 `stop_requested` 或 generation 变化失败的 `assert_run_owner`，否则会改变取消语义。候选方案是由取消方在其授权事务中同步撤销精确 attempt 的 owner 并将可能已发出的预占标记为 unknown，旧执行者之后零写；必须先证明与发送标记及现有锁序原子且没有死锁，不能直接当成已选定实现。代次接管、owner 不匹配、不可验证绑定时旧执行者不得写账，保留待核对预占；不能因为租约到期推断未发出。
3. 在每次 unknown、结算、释放、结果和检查点发布的**同一数据库事务**读取并锁住可信绑定后再写入；包含流式及同步、团队、Search/Fetch 与异常恢复。人工复核使用独立授权入口和可审计接管契约，不读取或伪造运行时凭据。任何提交结果不确定或可能已发送的请求均不得自动释放或重发。
4. 落定并跨路径验证锁序：候选为运行 → 运行状态 → run/attempt owner → 企业及授权上下文 → 钱包 → 预占及其明细；现有对账有预占 → 钱包路径，不能在未解决反序前采用该顺序。必须逐条审计与 MySQL 屏障测试后调整。基础工具入口已避免自身先持钱包共享锁再升级，但调用者可能在进入前持有其他锁，仍需验证整个调用链；不得自行提交调用者事务或无限等待。
5. 在独立 MySQL 上验证并发领取、不同模型轮次/付款人绑定冲突、owner 更换前后 unknown/settle 竞争两种顺序、取消与失权同时发生、提交结果不确定、正常取消仍进入 unknown、旧 worker/旧运行拒绝，以及人工复核不能被执行者围栏误伤。严格 xfail 必须转为真实通过后移除标记；同时验证无真实身份变化时不会错误把普通取消识别为失权。

上述是待完成的接线契约，当前已有默认关闭的模型 attempt 基础表，但没有可信模型轮次或账本状态转换的事务内 owner 围栏；不能激活或宣称迟到失权问题已修复。

## 模型 attempt 绑定基础：轮次身份仍阻断接线

122 工作树正在验证独立模型 attempt 绑定记录，默认保持关闭且没有连接实际模型、账本状态转换或恢复入口。该基础只允许同一 SQLAlchemy Session 中**尚未 flush 的新预占对象**与独立 owner 摘要和调用者提供的 `round:` 加 32 位小写十六进制标识一同提交。未 flush 不证明该对象来自可信预占流程，不能证明额度、钱包批次、费率、发送状态或 checkpoint 有效；现有 `ledger.reserve` 会在内部 flush，该基础不能直接接到生产预占。关联不能授予发包、结算、释放、取消或自动恢复权限。

**轮次身份尚未建立可信来源。**当前 `RunCheckpoint.rounds` 在恢复等路径中会重置为 0，不是跨恢复的稳定身份。基础接口没有校验模型轮次 ID 与持久检查点之间的关系；拒绝非不透明字符串只是阻止误把提示词当作标识持久化，不能证明两个不同 ID 不是同一次模型外呼。未来必须先在同一受保护的 checkpoint/领取事务中创建并保存不可变模型轮次 ID，证明崩溃恢复、同代重入和显式重试分别使用正确的旧/新 ID 后，再评估接线。严禁仅凭这个表或 round 摘要开放调用、宣称重入安全或移除迟到失权的严格 xfail。

基础验证记录：SQLite 模型绑定用例覆盖重复轮次与代次、计费身份篡改、旧/已 flush 预占拒绝、外层回滚、数据库不可更新和删除；真实 MySQL 一次性隔离库完整迁移后通过并发单领、不可修改及旧数据迁移测试，并另验证 owner 断言持锁时代次变更等待、旧 RR 快照不能继续使用旧代次。数据库唯一性冲突导致的 flush 错误要求调用者回滚整个外层事务；不得捕获后继续提交。数据库里现有预占或用户历史信息未被回填 owner。以上不是计费成功、持久 checkpoint 信任、老执行器隔离或生产验收证据；现有迟到失权负例仍严格预期失败。

## 发布和接线阻断补充

- MySQL 迁移 122 的建表和触发器为非原子 DDL；途中失败可能留下部分结构而 Alembic revision 仍为 121。现有部署探针没有 122 半迁移或触发器完整性门，故即使基础功能关闭也不能据此发布。须实现独立 schema/revision/触发器门，并在隔离库对每个故障点注入失败、验证拒绝启动及前向恢复。
- 模型 owner 不可更改/删除触发器及外键 `RESTRICT` 对历史记录保留、归档和数据清理有影响；须先制定保留策略，完成含 owner 行的 mysqldump、隔离恢复、验证及安全清理演练。当前未发现或主张已破坏生产数据。
- 真实 `ledger.reserve` 创建预占的 Python ORM 对象在 flush 前，其 `billable_kind` 和 `usage_state` 默认均为 `None`；基础 claim 目前要求显式 `model`/`pending`，且现有 reserve 会立即 flush。因此仅把 hook 移至 flush 前仍不能接线；须先修改并验证可信 reserve 工厂、默认值、钱包批次及额度的同事务契约。测试使用真实 reserve 构造路径与替身账本依赖重现此边界。
- 一次性 MySQL 8 完整迁移链上的针对性竞态已验证：同一 run 的不同轮次复用同一预占请求键时，reservation flush 报 1062；在异常退出外层事务后，额外的 tool owner、钱包版本变更和新预占均未提交，原预占和模型 owner 保留。调用者必须整体回滚，不能捕获后继续提交。
- 同一企业钱包的两个不同 run 在各自同一事务内先调用 `claim_tool` 获得钱包共享锁，再并发调用 `claim_model_attempt` 申请钱包排他锁，独立 MySQL 双连接屏障**已复现 1213 死锁**：一方事务回滚，另一方提交。这是实际的接线阻断，不代表现有生产功能已触发或已发生数据损坏；在设计并验证一致锁序之前，禁止组合接线或放开功能。两项验证均未连接真实供应商或生产账本。

基础层后续修复：`claim_tool` 在写入 owner 及其外键之前取得钱包排他锁，`assert_tool_owner` 也使用排他锁，避免本组合发生共享锁升级。设计要求调用者及时提交短数据库事务，不得持锁等待供应商网络；当前基础函数不拥有外层事务生命周期，不能强制保证调用者遵守，接线前须另行验证。若同 Session 有本运行、相关 owner、钱包或预占的未刷新修改，基础函数会拒绝，避免 `populate_existing` 覆盖调用方数据；拒绝不会自行提交或回滚。调用者在进入前已持有的锁、其他待 flush 修改、真实 reserve 的批次/限额、取消、人工对账和退款的锁序仍需单独证明，功能继续关闭。

对应回归先在原共享锁实现上失败，再对独立 MySQL 8 重跑通过：相同钱包的两个 run 无论先 claim 或先 assert，第二事务均等待第一事务结束后完成；不同企业钱包的两个事务通过双连接屏障并行完成，未引入全局串行。这些都是关闭的基础接口及模拟预占测试，不包括持锁网络调用，也不能代表生产链路的全路径锁序已验证。

基础 `claim_run` 和 `assert_run_owner` 同样拒绝当前运行及其关联 owner 的未刷新变更，避免刷新丢失调用方状态。未来接入新代次时，必须在持有运行和状态锁的同一事务先 flush 代次和状态，再创建 owner，最后统一提交；flush 不是提交，后续失败应回滚两者。现有队列、审批及通用领取路径各自已有 flush，但实际接入点、其他未刷新数据和完整锁序尚需逐一验证；不得因为基础用例通过就激活。
