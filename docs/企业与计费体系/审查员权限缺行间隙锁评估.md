# 审查员权限缺行间隙锁评估

## 当前状态

当前单连接权限栅栏保持启用；本文件仅记录隔离复现与候选方案，不是生产修改方案或验收通过证明。不能以普通快照查询直接替换当前锁定读，否则可能在退款已提交后错误放行。此处问题是已复现的跨账号等待，尚未证明死锁、生产负载影响或等待超过真实业务事务时长。

## 隔离证据

一次性 MySQL 8.0.45、REPEATABLE READ、从空库迁移至当时唯一 head、两个独立付费审查员：

1. A 执行真实 `check_paid_permission_fenced` 并保持事务，双方订单均无退款；B 对自己的另一订单执行真实 `request_refund`。`performance_schema.data_lock_waits` 显示 B 的 `billing_refund.uq_billing_refund_order` `X,INSERT_INTENTION` 等待 `supremum pseudo-record`；A 提交后 B 完成。探针 `/tmp/prism_refund_gap_lock_probe.py`，1 项通过。
2. 同样 A 持事务时，管理员为另一账号执行真实 `set_permanent`。B 等待 `billing_permanent_reviewer.uq_billing_permanent_reviewer_user` 的 `X,INSERT_INTENTION`，A 提交后完成。探针 `/tmp/prism_permanent_gap_lock_probe.py`，1 项通过。
3. 对缺失退款使用 `FOR SHARE SKIP LOCKED` 仍持退款索引间隙锁，不能消除该等待。探针 `/tmp/prism_refund_gap_skip_probe.py`，1 项通过。
4. A 先建立没有退款的旧快照；B 在真实服务中创建并批准退款、提交后，A 的普通快照查询仍看不到退款，而现有当前锁定栅栏正确拒绝。探针 `/tmp/prism_refund_snapshot_absence_probe.py`，1 项通过。故不能使用普通快照先查退款主键、找不到时直接当无退款。

以上探针使用合成账号、合成费率和一次性空库，完成后各临时容器均已停止并删除；不代表生产性能或业务验收。

## 已确认的应用路径与局限

应用源码中业务退款行的唯一构造点为 `billing_checkout_service.request_refund`，该路径先取得对应 `BillingOrder` 的 `FOR UPDATE` 锁，再创建退款；退款状态变更使用 `_lock_refund_and_order`，先锁订单后锁退款。查单认领单独更新令牌和时间，不代表退款金额状态的变化。源码搜索不等于证明生产不存在运维 SQL、旧进程或未来新增写入口；迁移及切换时必须另行核对。

永久权益的 `set_permanent` 当前先锁用户钱包，再锁永久权益行，之后调用方同步用户角色。现有栅栏锁付款证据后锁用户和 RBAC；任何方案必须核对所有支付、订阅、永久权益、角色分配、工作室和审批写路径的完整锁序。事务持有锁期间不能再次向已满的同一个连接池借连接，否则此前已复现池饥饿。

## 可选方案及不能省略的约束

### 每笔订单保存退款引用

可研究在订单中增加可空退款引用，历史按 `order_no` 一对一回填；当前锁定订单后可用引用按退款主键当前读，正常无退款不查缺失键。必须证明引用与订单一对一、所属订单匹配、旧记录完整回填、错误或缺行失败关闭；退款创建、删除及任何改绑只能在持订单锁的同一事务维护。旧进程或直接插入若未维护引用，NULL 会被误当无退款，因此必须实现数据库级一致性保障，或在变更前清点并停止全部旧写入进程，且确保不再有绕过路径。单独增加字段并仅修改一个 Python 插入入口不安全。

此方案只针对退款缺行，不解决永久权益缺行。为永久权益再加引用可能引入 `User`、钱包和永久权益的倒序锁；不能未经验证把 `User` 行先锁后查权益。不得以级联删除丢失退款、账本或审计证据。

### 每账号权益版本协调行

可研究为每账号预先建立唯一的权益协调行，使用同一事务维护单调版本。受保护操作先在原快照中读取协调版本和相关付费证据，再按已知主键锁定当前协调行；版本变化或协调行缺失时失败关闭并提示重试，版本一致时在持锁期间按锁后时间校验周期。这样不需在正常路径锁定缺失退款或永久权益键，但前提是**所有**会影响审查员付费权益的订单、退款、支付事件、周期、永久授权及恢复写入，在同一事务以统一锁序更新协调版本；角色、权限和 JWT 仍要单独当前读并持锁。

协调行必须在历史用户迁移中完整回填，新用户创建必须同事务创建；读快照发现缺行时只拒绝，不以缺行锁代替。不能用新连接池读取来绕过锁，也不能仅依赖应用内存。迁移期间旧 worker 若仍可写且不更新版本，会导致失效，需可靠切换保障或经验证的数据库级版本维护。自然到期、宽限期、跨多个付费周期、永久权益、未提交写入、回滚、整数溢出、管理员和内部调用都必须有明确语义。

### 指定业务事务使用 READ COMMITTED

一次性 MySQL 中，以依赖注入方式让受保护业务的同一个 Session 从认证首次查询起使用 `READ COMMITTED`：缺退款和缺永久权益的跨账号插入均不再等待；真实个人/远测授权的退款先行拒绝、写入先行锁等待及永久权益共 6 项通过；Studio、个人及远测 JWT 撤销先后和真实 HTTP/JWT 共 9 项、项目绑定先后 2 项、不同审查员及角色权限撤销 3 项通过。分别见 `/tmp/prism_refund_rc_gap_probe.py`、`/tmp/prism_permanent_rc_gap_probe.py`、`/tmp/prism_refund_rc_authority_probe.py`、`/tmp/prism_rc_scoped_review_probe.py`。这些隔离测试不证明所有业务在此隔离级别下正确。

单连接池测试 `/tmp/prism_rc_pool_reset_probe.py` 确认：SQLAlchemy 的 RC 连接归还后，以相同 MySQL CONNECTION_ID 重新借用可恢复服务端默认 `REPEATABLE READ`；首次 SQL 已建立事务后再设置隔离级别会抛出 `InvalidRequestError`。真实 `get_db` 必须在认证及任何依赖的第一条 SQL 之前精确选择事务隔离级别，且认证、角色判断、锁定授权与业务写入共享同一 Session；不能把已认证的 RR Session 中途改成 RC，不能未经验证把所有请求或后台任务全局切换，也不能以持锁后借用第二个连接替代。普通读取的可见性变化、引擎回退、真实路由选择和依赖缓存、异常/断线后的池复位、其他写入口及不变量，均需逐条核对并以真实路由回归验证。

上述方案均尚未实现、未独立审查，也未选型；不得把协调版本、订单引用、超时或 lease 作为无证据的业务完成证明。本阶段保留现有 RR 方案，不扩散路由级隔离选择。

## 先决测试与发布门禁

- 真实 MySQL RR：退款创建/批准先提交后旧事务必须拒绝；受保护写先持有效授权时，同一订单退款等待，提交后按序执行。跨账号无退款插入和永久权益授予不应被 unrelated 缺行阻塞。
- 迁移用真实历史副本核对一对一关系、NULL、孤儿、错单、重复、全部已付款周期；分别验证新用户、旧数据、直接旧写入、事务回滚和部署切换。不能修造或丢弃历史事实。
- 签名查单、金额、退款生命周期、订阅创建/发放/续费/过期、永久权益授撤、账号禁用、角色绑定和权限撤销均验证两种并发顺序；正确恢复永久审查员，不能开放未付费权限。
- 缩小连接池验证不存在二次借连接饥饿；查询计划和 `performance_schema` 验证锁定的具体行/索引；同时测试缺失、异常和多账号并发。SQLite 结果不作为 MySQL 锁证明。
- 本地全量测试之后仍需真实商户沙箱、生产数据副本迁移及恢复、多账号浏览器、旧 worker 清点及灰度实际业务验收；销售代码锁保持关闭。
