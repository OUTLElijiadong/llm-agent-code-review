# 平台模型调用所有权：设计与红测

## 状态与范围

本设计只针对管理员使用平台托管模型时的成本 attempt。现有平台成本基础默认关闭、独立 metadata、没有迁移或生产调用方。本阶段不连接 Responses、后台恢复、真实供应商或平台预算配置，不修改模型白名单。下文是待实现和验收的合同，不代表现有系统已具备这些能力。

## 现有调用链与不能复用的原因

`agent_response_run` 用用户、`surface` 和 `session_key` 限定运行，`version` 是检查点版本，不是已实现的执行者代次。SSE 入口的计费上下文只包围该请求；后台恢复在独立线程、独立数据库会话中直接调用 `resume`，不能依赖前台上下文自动传播。`NativeResponsesTransport` 先预占并调用发送前钩子，随后在实际 HTTP 调用处通过 `prepare_deepseek_responses_payload` 转换请求；现有预占不能证明最终发送的是同一个 payload。它的 `finally` 调用未知结果处理，失权与取消竞态需要覆盖。

`DatabaseCheckpointStore.save` 当前会直接提交其共享会话，创建检查点与后续写入均如此；`cancel` 另锁定真实运行并写入停止意图。不能把所有权和预占临时放入该会话，再假设提交只影响本组件；必须明确事务所有权，并复核检查点保存与停止意图的锁序。`AgentResponsesService._runtime` 可能解析用户自带 Key，视觉分支也可能改用平台配置，实际成本归属必须从最终可信配置判断，不能只看管理员 surface。

企业所有权实验绑定企业运行、企业会话、租约代次以及企业钱包；这些事实在平台管理员 Responses 运行中并不存在。不能虚构企业、钱包或用检查点版本冒充租约代次。平台需要自己的运行与 attempt 身份；可参考企业方案的摘要、锁及负向测试方法，但不能直接复用其作用域或宣称企业分支已接入本分支。

## 待实现合同

1. 服务端从已认证请求或合法恢复任务加载真实运行，校验账号仍有效、仍为平台管理员、运行 `surface=admin` 且用户/会话匹配。前端传入 surface、attempt key 或用户 ID 都不能单独证明身份。后台恢复必须重新建立同等可信上下文；运行所属、权限、停用状态在锁定的当前读中复核。
2. 持久运行所有者与每个模型 attempt 所有者分开。凭证由服务端每次领取产生足够随机字节，只存摘要，日志、响应和 checkpoint 不保存原值；原子唯一领取，其他同账号执行者没有凭证不能完成任何 owner 专属写入。真实运行和 attempt、模型、提供方、凭证来源、冻结预算和最终 payload 摘要不可变。各标识须用字节一致的比较及唯一约束，不能依赖 MySQL 默认不区分大小写的字符串排序规则。哈希不是对低熵敏感内容的保密保证。
3. 执行者失权后，不得写 attempt、费用、checkpoint、最终消息或重新外呼；信号不能被通用异常、`finally` 或取消清理转成普通失败和账本写入。取消方必须在同一事务中围栏旧执行者并按已知状态冻结对应预占；不得替调用方提交、回滚其已有事务。
4. 发送前在最终 payload 构造完成后、真实 HTTP 发送前校验已认证的所有权、运行状态、预算和费率。发送标记与相应所有权验证必须原子提交；提交结果不确定也冻结。**提交标记与外部网络发送不可能仅靠数据库事务原子化**：旧执行者在标记提交后仍可能迟到发包。未证明旧进程及其出口已隔离前，不能按未发送释放，也不能自动重发或让其他执行者接管该 attempt。
5. `reserved` / `unknown` 都维持预算冻结。超时、丢失响应、取消、失权或进程崩溃不构成释放证明；需要单独的可信对账/授权状态机。真实 provider 结果、账本结算、最终回复和 checkpoint 均须同事务检查各自实际 owner；不得仅以 request key 前缀、账号相同或 lease 超时推断所有权。

建议后续在最终迁移中分别建立运行执行所有权记录（真实运行主键、单调代次、凭证摘要和有效状态）与 attempt 执行所有权记录（真实 attempt、运行及代次、独立凭证摘要、最终请求摘要、发送阶段）。唯一约束必须使同一逻辑 attempt 只能有一位执行者。运行创建/领取与 owner 的首次落库需要同一可信事务，并明确老运行/旧 worker 的隔离证明；将 owner 事后附着到现存运行不能证明没有其他执行者。一个模型轮次的稳定逻辑标识也须在检查点中持久化并与 attempt 原子绑定；单纯每次恢复生成随机 key 会让重复运行产生新 attempt。表结构和锁序在未完成跨路径验证前只作为设计候选，不生成迁移。

权限撤销与发送也只能在明确的序列化点界定：撤权先于发送标记提交时应拒绝；标记先提交后撤权不能仅凭数据库状态保证请求尚未离开进程，该 attempt 必须保持冻结，迟到结果和最终输出仍须验证对应的处置权。不能把“发送前再查一次”描述成撤权后绝无发包的证明。

## 锁、接入及上线依赖

不得在当前分支假设最终锁序。接入前必须逐条验证用户/RBAC、运行、成本中心、费率、预算、attempt、owner、检查点及取消路径的统一全局锁序；特别检测用户权限撤销、预算启停、并发恢复、外部写入者与已有事务持锁造成的环。SQLite 需在首次读取前取得写事务并验证旧快照；MySQL 使用独立连接和有界屏障验证。只改变会话超时必须保证连接池状态恢复，不能偷偷提交或回滚调用方事务。

启动门还包括：基线 121 与并行 122 合并后保持唯一迁移 head；已发送/unknown 账单与旧运行盘点；可验证地隔离旧 worker、恢复线程和外部写入者；经审核的真实平台预算与提供商账号费率；变更后备份恢复、真实账号及业务验收。无任何一项证明均保持关闭。预算表由其他写入者绕过中心锁时，目前不能证明预算唯一性。

## 红测与验收拆分

- **已复现并保守封闭的红测**：独立执行者即使不提供 owner，只要拿到同一管理员和 attempt key，原 `mark_unknown` 就能改写仍在途 attempt。已让此入口在基础开关开启时也无条件拒绝，原预占保持 `reserved`；此前红测应转绿。测试仅针对关闭且未接线的基础，不代表线上发生。此封闭没有实现 owner、取消围栏或合法 unknown 处理，仍禁止接线。
- **待补真实链路红测**：同账号跨进程同时领取；管理员降权/停用与发送竞争；取消在发送前、标记提交前后及 `finally` 竞争；后台恢复和前台重复领取；最终 payload/提供方快照变化；旧执行者在新所有者之后写费用/检查点/结果；异常或提交不确定时保持冻结。必须分别记录普通取消与失权取消，不能因为防失权而允许正常取消后的请求继续发送。
- **隔离基础**：先验证不可伪造的独立运行/attempt 领取、锁后身份校验和同事务财务围栏；不接真实发送。旧运行或旧 worker 无法证明隔离时一律拒绝初始化新 owner。
- **后续完整接线**：贯穿 SSE 与后台恢复、Native transport 和所有异常/取消边界，对真实 MySQL 并发、崩溃/网络断点、外部写入及真实浏览器多账号逐项验证。完成前不得把局部基础称作完整无写或生产恢复。

本轮红测先在隔离 SQLite 文件库使用 `NullPool` 和独立连接复现“不提供 owner 仍能调用成功”，再完成封闭；复测平台基础 **35 项通过**，包括调用者待写降权未被提交或刷新。真实 MySQL owner 竞争、已持锁会话、发送及恢复端到端均未验证；同账号竞争实际生产发生与否也没有证据。

## 隔离双 owner 原子阶段

新增实验在未注册应用 metadata 的独立表中分别记录 run owner 和 attempt owner。仅可在同一事务中新建真实 `AgentResponseRun` 与其 owner；不提供对已有运行的领取或代次接管。模型成本预占与 attempt owner 在同一调用方事务中建立，凭据分别随机生成，数据库仅保存将类型、运行主键、代次及 attempt 主键纳入的摘要。任何一次状态写都重新锁定当前管理员角色、运行和 owner；取消在同事务内记录停止意图、递增运行版本和 owner 代次，并把尚为 reserved 的尝试保守转为 unknown、保持预算冻结。重复 unknown 不扣费或释放。旧版 `mark_unknown` 入口仍一律拒绝。

该能力仅是离线实验：`AgentResponseRun` 跨 metadata 引用只是逻辑检查，没有数据库外键；运行删除后以相同主键重建时，现有约束不能保证旧身份与新身份隔离。激活前必须验证外键、不可变身份与归档生命周期。传入的 actor/session 并未在本模块证明来自真实认证；没有合法已结算状态、账单处理、真实发送、外呼结果、检查点写入的 owner 围栏，也没有安全接管。管理员被停用后，原账号及其他管理员均不能通过实验取消接口完成代停，此时预占保持冻结，必须设计独立受权代停/恢复路径。凭据是能力令牌，并不能区分被复制的同一凭据；模型轮次尚无与 checkpoint 原子绑定的稳定逻辑标识，换用新的 attempt key 不能视为安全重放。提交成功后确认丢失的模拟只验证同一个 key 的重复预占受阻，不能证明 HTTP 未发送或证明可自动恢复。

独立复核已实际复现同主键重建后旧 secret 仍能预占，现有严格 `xfail` 持续记录该未解决缺口。必须由正式迁移提供真实数据库 FK、运行不可变身份与防删除重建/归档合同，并测试历史数据和旧进程隔离；仅比较时间戳、当前 run 字段或本实验逻辑引用不足以作为修复。保持默认关闭。

本轮 SQLite 两文件 **60 项通过、1 项严格 xfail**，覆盖双连接同 key 竞争、权限撤销、跨管理员和会话错配、generation 变更、调用方脏事务、回滚、取消/unknown 竞争与确认丢失模拟；损坏、含重复字段、非有限数值和状态含糊的检查点失败关闭。MySQL 8.0 一次性隔离容器的随机标记空库执行基础与扩展竞争 **1 组通过**，另由独立审查者在另一随机空库复跑通过：同账号重复预占、权限撤销与预占的双向锁序、取消与 unknown、预占先锁并等待取消、不同管理员/运行竞争同一预算。两次 MySQL 测试发生在最后的纯 JSON 浮点解析修正前；该修正另经 SQLite 全量回归与独立输入测试。专用容器和本次受限临时文件已核验身份后清理。测试不证明旧 worker 或直接数据库写入已隔离，也不构成迁移与生产验收；历史合法 checkpoint 的兼容性尚未核验。
