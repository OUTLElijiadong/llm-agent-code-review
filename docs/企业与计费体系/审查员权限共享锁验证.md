# 审查员权限共享锁验证

## 复现与修复

在一次性 MySQL 8.0.45、完整迁移至当时唯一 head 111 的隔离库中，两个不同审查员分别持有自己的订单、退款和账号。第一人的 `check_paid_permission_fenced` 返回后保持事务，第二人的授权因共享 `role` 主键行的排他锁等待；`performance_schema.data_lock_waits` 记录为 `role.PRIMARY / X,REC_NOT_GAP`。这证明不同账号的受保护写入会不必要地串行，不证明发生死锁或生产负载故障。

修改 `check_permission_grant`：用户行仍使用排他当前读；角色绑定及权限记录改为共享当前读，持锁至受保护事务提交。共享读允许不同用户并行，同时继续阻止同一账号变更、角色停用和权限撤销抢先提交。未改变权限判断规则或放宽账号授权。

## 验证与边界

- 测试先行：不同审查员并发用例在修改前失败，角色权限撤销等待用例通过。
- 隔离 MySQL 联合回归 25 项通过，覆盖不同审查员、角色权限撤销、退款先后、JWT 会话撤销、连接池和 Studio 写入；另独立验证角色停用及权限撤销等待，共 3 项通过。等待由 `performance_schema` 实际确认。
- SQLite 的 RBAC API 和 Studio 权限定向回归 58 项通过；Ruff 和 `git diff --check` 通过。SQLite 不提供 MySQL 行锁证明。
- 测试使用合成账号和订单，容器均为本任务独占临时实例并已停止删除；未做真实用户、生产负载或所有业务锁序验收。
