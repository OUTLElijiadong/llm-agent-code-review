## 可重复读下的跨项目等待复核（2026-11-09）

在独占、临时的 MySQL 8.0.45 空库中重新执行 `init.sql → seed.sql → 当前 head`，以合成数据运行终态报告锁范围测试和旧快照回归：**4 项通过、1 项严格预期失败**。单独使用 `--runxfail` 复现后，`performance_schema.data_lock_waits` 显示无关委托插入等待 `uk_pentest_finding_engagement_fp` 的 `X,INSERT_INTENTION / supremum pseudo-record`；释放报告事务后插入完成。这证明指定测试中的等待，不代表已经测得生产频率、持续时间或死锁。

终态报告当前对发现、阶段和覆盖记录使用当前读，以包含旧事务快照之后已提交的数据，并将报告生成纳入同一事务。直接改回普通查询会重新引入旧快照漏记；跳过锁定记录也不能保证报告完整。仅调整索引无法据此证明空范围及索引末尾不再互相等待。旧正式执行路径的 `_staged_worker_is_current` 在试验门禁关闭时不会取得持久代次授权锁，发现新增和已有发现状态修改也没有统一的父委托锁协议，因此不能只依赖当前报告持有的父行锁就删除子记录当前读。

本次没有变更生产查询或移除严格预期失败。后续需要先为所有发现、阶段、推演线的新增、修改、删除及报告生成建立覆盖正式和恢复路径的相同委托粒度写入/读取协议，证明锁序、旧快照、取消、重跑、报告重发与跨项目并发；或者在认证的首条 SQL 之前限定事务隔离级别，并单独证明所有调用链的授权和一致性。隔离级别不能在已经开始的事务中临时切换来替代这些证明。该性能问题仍属于上线前容量与并发验收的未完成项。

参考 MySQL 官方文档：[事务隔离级别](https://dev.mysql.com/doc/refman/8.0/en/innodb-transaction-isolation-levels.html)、[InnoDB 锁](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking.html)和[锁定读](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html)。其中 `READ COMMITTED` 一般不锁搜索间隙，但可能出现幻读；因此更改隔离级别也不能替代对同一委托并发新增和报告完整性的证明。

补充实验：在隔离 MySQL 上将报告和插入事务设为 `READ COMMITTED`，报告读取发现后暂停，在同一委托插入发现并提交，再继续提交报告；实测报告仍为零项而数据库已有一项。该实验证明直接切换隔离级别会损坏此并发场景的报告完整性；它不证明已经在线上发生。回归探针保存在 `backend/tests/test_mysql_pentest_terminal_report_rc_phantom.py`，断言复现该不安全情形，不能将其当作修复通过。

## 发现写入的局部收紧及完整协议缺口（2026-11-09）

代码盘点中，个人渗透生产服务的发现新增仅由 `_phase_detect → _upsert_finding` 完成，验证阶段 `_phase_exploit` 对发现逐批修改并分别提交；`start_engagement` 重跑清理和 `_purge_engagement_rows` 删除均批量删除发现。`backfill_rule_scores.py` 读取发现并修改审查报告分数，不修改发现。独立的远程渗透模型使用另一张表。以上是对仓库内静态入口的盘点，不证明部署中的旧进程、手工 SQL 或外部程序均遵循相同协议。

已在隔离 MySQL 先复现旧正式路径的遗漏：终态报告持锁时，上一轮迟到的 `_upsert_finding` 被间隙锁暂时阻塞；报告提交后该写入仍成功。现已对发现新增入口在同一事务锁定并刷新委托，拒绝 `completed/failed/cancelled/expired`；保留历史合法的 `authorized` 和正式运行使用的 `running`，不删除既有发现。反向顺序则由先进入的发现写入持父锁，取消等待并将已提交发现纳入报告。该变更只覆盖新增发现的状态竞态，并未改变终态报告的当前读或移除跨委托等待的严格预期失败。

**代际缺口仍存在：** legacy `_upsert_finding` 没有持久代次参数，若另一个进程将同一委托从取消重新启动，迟到旧工作线程会看到新的 `running` 并被误认为可写。新增严格 xfail 单独记录该问题；同进程注册表不能证明其他进程或旧工作线程已经退出，不能用状态锁替代持久代次与终止证据。试验执行路径继续关闭。

阶段和推演线并非上述修复的一部分：`_advance_pipeline`、`_ensure_phase_run`、`_mark_phase_failed`、`_mark_unfinished_skipped`、`_phase_detect` 的子线程及 `_record_line_result` 均有独立写入或提交边界；特别是 `_mark_unfinished_skipped` 自行提交会释放已有父行锁。要以父委托协议替换当前的范围锁，还需覆盖阶段、线、发现修改和删除的全部路径，重新审查钱包、用户、项目、委托、执行、子记录的锁序，保证不在模型或沙箱外呼期间占锁，并为多进程旧版本交叠和历史记录定义上线门禁。单靠父行锁既不自动让 MySQL RR 范围当前读停止间隙锁，也不能让已有 RR 快照看到锁前新提交的子记录；尚无经验证的安全替代实现。

## 旧快照下重复发现的事务修复（2026-11-09）

在独占 MySQL 8.0.45 中，两个事务先建立没有同一 fingerprint 的 RR 旧快照，随后通过真实 `_upsert_finding` 依次竞争同一委托锁。第一事务提交后，第二事务虽已取得父锁，其普通查询仍看不到新发现，原实现会在插入时触发唯一键错误。仓库内回归在修复前实际得到 **1 failed、6 passed**。

MySQL 分支现在先将调用者已有的待提交修改在捕获区外 flush，再仅将新发现的写入置于 savepoint；仅对 MySQL 错误 1062 且错误末尾实际索引名为 `uk_pentest_finding_engagement_fp` 的冲突返回已有发现，不吞掉其他约束和数据错误，也不对缺失项增加当前读间隙锁。额外验证表明，若只搜索完整错误消息中的键名，重复值本身能伪造该文本；测试覆盖了这一反例。非 MySQL 路径继续使用原有写入流程：SQLite 的隔离实验表明，在尚无先前 DML 的事务中直接释放嵌套 savepoint，外层回滚可能无法撤销写入。

修复后隔离 MySQL 组合 **62 passed、2 strict xfailed**，包括旧快照重复、其他唯一约束和超长输入、外层 pending/rollback、不同委托并发、取消与报告两种锁顺序；SQLite 定向组合 **160 passed**，Ruff 通过。两项 xfail 仍为终态报告跨委托间隙等待和 legacy 旧代 ABA；实验中的其他约束在一次性数据库中临时创建并移除，并非生产数据库变更。不存在凭此开放销售或关闭持久执行门禁的依据。
