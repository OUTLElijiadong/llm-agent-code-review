# 审查员写入的会话撤销竞争验证

## 发现与修复

隔离 MySQL 8.0.45 的可重复读事务复现：请求使用真实 JWT 通过认证及权限依赖后，其他事务递增账号会话版本并提交；旧请求继续调用 Agent Studio 创建、个人渗透授权或个人远测授权，仍能写入。原因是写入栅栏虽使用当前锁刷新账号，却没有与此前认证的 JWT 版本比较。

认证成功时现将 JWT 的会话版本保存在 ORM 非映射的请求内快照；三类写事务在锁定账号及 RBAC 后，将当前账号版本与该快照比较。没有认证快照的可信内部服务调用继续遵循既有服务合同，不能因此推断其他 HTTP 写入口已获得相同保护。

## 验证与边界

- 先写入隔离 MySQL 红测，撤销先行时个人及远测授权均复现错误；Studio 路径另以真实认证依赖独立复现。
- 基于从空库迁移至 110 的独占 MySQL 8.0.45，三条路径分别验证撤销先提交则写入拒绝、写入先取得账号锁则撤销真实等待，以及真实 HTTP/JWT 在认证后撤销时拒绝写入，合计 **9 项通过**；锁等待通过 performance_schema 观察。
- Studio、RBAC 和企业远测相关 SQLite 回归 **73 项通过**，目标 Ruff 检查通过。SQLite 不证明数据库锁行为。
- 真实生产浏览器与线上账号未验收；其他业务写入口、后台 worker 和所有 API 并未因此获得同等覆盖。新代码尚未发布。

## 连接池与权益证据（2026-11-09）

独立 MySQL 复核发现，旧实现持有账号锁和一个池连接后又从同一池借用连接读取权益；当其余连接被等待该锁的请求占满时，持锁请求会因连接池超时而失败。缩小为两连接的隔离测试先复现该问题。

现改为在同一事务中先按订单、退款、订阅与周期、永久权益顺序读取并持有当前共享锁，再锁账号及 RBAC，使用锁定证据和写入前时钟判断权益。最初的历史快照仅用于定位候选订单；如果新购买的周期尚不在旧快照内，当前请求会失败关闭，重新发起即可使用新快照。不得在账号锁后反向获取支付写锁。

一次性 MySQL 8.0.45 空库至 110 的回归中，缩池进度、旧快照中永久权益撤销后付费期到期、退款先后、JWT 撤销先后、永久授权撤销和周期发放的等待顺序共 **20 项通过**；其中等待通过 performance_schema 实测。角色、Studio、退款、会话的 SQLite 组合 **189 项通过**，相关 Ruff 检查通过。以上不证明所有支付/调度/业务组合均无死锁，仍需独立锁序复核和生产负载验收。
