# 企业月额度与钱包旧快照修复

## 已复现问题

隔离测试先以企业钱包结算 30 积分，再在当月首次设 20 积分上限。旧逻辑把已用和预占初始化为零，允许继续预占 20 积分；企业、小组和成员三个范围均有相同缺口。额度设置之前已存在的未结算 reservation 也没有关联新额度，后续结算或释放无法更新上限。

独立 MySQL REPEATABLE READ 测试还复现：旧事务缓存积分批次，另一事务先预占后提交，旧事务再预占会依据旧对象覆盖批次，导致两个 reservation 总额大于批次冻结额。另一测试复现自动退款冻结与并发预占之和超过批次余额，及旧事务将已结算 reservation 改回 unknown。

## 本地修复

- 112 为额度增加 `accounting_version` 并为企业账单按来源和创建时间建立索引；历史额度保持原数值并标记待重建，不在迁移中猜测历史消耗。
- 设置额度时先锁企业钱包；基于同一一致性快照按企业实际出资的批次重建当月已结算和未终态金额，为现有未终态 reservation 补充额度链接。已用加预占大于所设上限时拒绝设置；缺少或矛盾的历史明细失败关闭。
- 旧额度查询以账本只读计算展示；首次预占前，在企业钱包锁内重建并绑定未终态记录。公司出资为零的个人兜底不会记作企业使用。
- 为避免 MySQL RR 历史范围锁阻塞其他企业插入，重建前比较事务快照中的钱包版本与当前锁定版本；若已有并发钱包变更，拒绝操作并要求新事务重试，不使用过期历史猜测。
- 余额预检查、批次/预占状态及结算、释放和对账使用钱包先锁及当前读刷新；结算与释放读取额度链接时采用当前锁定读，能看到旧快照之后新增的链接。退款检查也先锁付款钱包，并对过期钱包快照失败关闭。
- 企业订阅激活、续费及退款结果与额度设置统一企业→钱包顺序；额度历史关联数据改为每 500 条分批查询，避免每笔账单分别往返数据库，但大量额度和超大月账单仍需容量验证。

## 当前验证和边界

额度、账本、工具、对账、退款及 API 的 SQLite 定向组合 **206 项通过**；隔离 MySQL 从空库迁移至 112 的合并回归 **28 项通过**，包括旧快照结算/释放及 C4 审批看到新链接、额度先行/预占先行实际钱包锁等待、旧快照拒绝和不同企业并发、个人/企业/混合/工具钱包旧对象、退款/预占及状态回退，以及额度与订阅生效、续费支付、退款确认各自双向先后。独立复核的坏数据回归覆盖缺失批次、跨钱包、伪释放、钱包缺失和真实空额度；仍需整体最终回归。

结果只覆盖已进入账本的企业付款调用，不代表所有模型或外部成本已经计量。112 尚未在生产数据副本演练，真实商户、供应商账单和多账号浏览器尚未验收；发布前需确认迁移与账本保留、旧 worker 切换、112 后完整自动化和生产数据恢复。对历史账本明细不完整或与已记录额度矛盾的情况必须人工核对，不能按零值修复。
