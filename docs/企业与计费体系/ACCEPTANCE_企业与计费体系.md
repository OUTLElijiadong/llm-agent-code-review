## 最新追加：小菱模型预占与检查点崩溃防重（2026-11-06）

## 企业 Agent 预算拒绝终态与覆盖状态（2026-11-07）

### 退款竞态与冻结复核补充

- 已先复现历史已批准退款的拒绝分支在冻结额异常时仍会清零冻结的问题；现在旧批准单仅在冻结额等于剩余额时允许拒绝并解冻，普通待审核单仅接受零冻结。异常时事务回滚，原退款状态、审核人和审计证据保持不变。
- 查单 `NOT_FOUND` 不证明退款请求未送达；当前结果维持未知和冻结，不允许再次发起。升级前已持久化的 `approved/failed + NOT_FOUND` 仅允许再次核对渠道，不自动退款；旧 `failed` 单的额度可能已由旧代码释放，如已有消费，成功结果将进入人工复核，不能将历史冻结视作已恢复。
- 退款发起响应携带本地 attempt 代次，旧代次的失败和未知响应不能覆盖新代次；旧代次成功只能冻结并要求再次查单。发起新代次时使旧查单认领失效，缺少代次的多次尝试结果拒绝应用。这些保护不证明切换部署时仍在运行的旧版本 worker 已停止，生产发布需确认旧进程退出和在途单核对。
- 同代次已应用验签查单后，迟到的退款创建响应只记录冲突审计，不覆盖查单或据此完成退款；与已有失败等状态冲突的迟到成功转为未知并等待再次查单。创建调用未返回时，即使查单报告失败也先保持冻结，避免在途创建请求晚到后出现资金冲突。109 迁移为创建响应和查单分别记录代次，旧行保留 NULL 表示顺序未知，新建尝试初始化标记；历史在途单的创建响应不作为结算证明。支付宝和微信均须由已验签查单确认成功才回收权益；查单通信或验签异常释放查单认领并返回错误，不伪造为已验签查询。隔离测试先以正式认领令牌复现两种相反结果，再验证保持退款及账本状态；全新 MySQL 8.0.45 建链至 109，并完成 head、委任撤权锁序和查单租约共 **4 项通过**。
- 微信文档指出刚发起退款时查单不存在可能需要稍后再查，使用同一退款号重试有特定条件；本系统在结果不明时采取更保守的冻结策略。[微信退款错误码](https://pay.wechatpay.cn/doc/v3/merchant/4020801246)、[微信退款开发指引](https://pay.wechatpay.cn/doc/v3/merchant/4013071031)。支付宝文档说明同一退款按外部请求号幂等，超时不能推断结果：[支付宝交易退款接口说明](https://developer.alibaba.com/docs/doc.htm?articleId=105170&docType=1&treeId=292)、[支付宝退款查询指引](https://aipay.alipay.com/article/3471)。具体渠道结果和资金状态仍需商户沙箱与原始账单核验。
