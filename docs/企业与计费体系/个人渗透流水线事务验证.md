# 个人渗透流水线事务验证

## 范围与方法

`backend/tests/test_mysql_pentest_staging_writes.py` 使用独占空 MySQL 8.0.45 和 REPEATABLE READ，验证个人渗透持久化试验路径的报告引用、撤权、取消、推演线和重启扫尾。模型返回和流水线 worker 使用测试替身；未调用真实模型、沙箱或生产服务。跨事务锁等待以 `performance_schema.data_lock_waits` 观察。

## 已复现并修复的问题

- 完整报告曾先提交 ReviewTask，再设置委托报告引用；紧接着的流水线存活检查执行 rollback，丢失引用。修复后报告、引用与摘要在一个事务提交。注入报告 flush 后异常，验证回滚不留孤儿报告；取消或停用先提交时报告不能发布，报告先持锁时这两种操作实际等待提交。
- 启动扫尾曾读取 running 旧快照；用户取消并提交后，扫尾仍将状态和取消报告改为失败。旧路径改用当前锁读和报告前复核；持久执行试验路径不能仅因进程启动就认定 worker 已退出，因此暂不自动扫除 running。
- 定时孤儿扫尾曾有相同的旧快照覆盖取消问题，且把缺少当前进程注册记录当成持久执行已退出。相应回归用例在测试文件中分别验证旧路径和持久执行试验路径。

- 旧路径曾在提交 running 和进程内注册之间被定时孤儿扫尾误标失败。调整为提交前注册；在隔离 MySQL 中并行扫尾看不到尚未提交的 running，安全跳过，新注册窗口回归转绿。该用例没有观察到锁等待，不能据此声称等待已验证。

上述修复后的隔离 MySQL 全量回归为 34 项通过。

## 已验证边界与待办

- 模拟模型外呼期间取消或停用，迟到的 exploit 结果不能修改 finding。推演线结果测试覆盖停用、取消和模拟旧代被新代替换。模拟退出与新代创建不是进程重启证明。
- 父线程退出、子线程退出与取消的六种提交顺序，分别覆盖有无未知模型外呼；仅有本地父子退出事实且已取消时可排空，存在未知外呼时保持 cancelling。另用双事务观察到父线程退出持锁时取消等待，释放锁后按同一规则收敛。退出事件由测试直接模拟，不证明真实线程、进程重启或外部调用已停止。
- 上述注册修复只覆盖同进程窗口；进程内注册表不能证明其他进程中的 worker 已退出，跨进程恢复需要独立证据。
- 本记录只描述隔离测试与源码中的行为，不作为真实浏览器、真实支付、生产部署、跨进程退出或恢复完整性的验收证明。

## 终态报告自动补发

`backend/tests/test_mysql_pentest_report_recovery.py` 在独占空 MySQL 8.0.45、REPEATABLE READ 下通过 10 项。真实启动与补发竞争的两个方向均由 `performance_schema.data_lock_waits` 观察到等待；启动先提交时，旧候选快照不会覆盖 running。候选选取后新提交的发现和错误信息进入补发报告；报告 flush 后注入失败会回滚报告及状态变更。

另外验证了保留的过期执行仍可补发、205 条已有完整报告不会挤占缺失报告候选、已有调用者写入被拒绝，以及定时入口的单连接池。应用生命周期测试实际进入 `main.lifespan` 并以单连接池完成启动补发，但其他子系统的调度、支付、外网和自动恢复钩子均使用替身；真实启动后的后台 worker 也为替身。该结果不构成完整生产应用启动或真实支付验收。独占数据库容器在测试后自动删除。

## 阶段回写与排空门禁

独占 MySQL 8.0.45 回归 `backend/tests/test_mysql_pentest_phase_finalization.py` 和 `backend/tests/test_mysql_pentest_fail_closed_independent.py` 共 15 项通过。验证涵盖阶段摘要的成功、取消、停用、到期及事务持锁，授权过期时禁止登记新模型活动并生成终态报告，以及固定关闭的登记完整性门禁阻止把新退出事实和缺乏完整性证明的历史 drained 当作排空。真实线程已在运行但启动包装对象显示 `ident=None`、`is_alive=False` 时，模拟的启动异常不会将该运行标记为已退出。

另在测试中人为设定“活动登记完整”并构造历史执行的账号或项目归属矛盾，验证项目证据返回 unknown、不得新建代次；较早历史代次矛盾即使最新代次一致仍被拒绝，无关项目的草稿仍为 clear。旧代摘要和这些历史矛盾场景依赖人为开启该标志或模拟退出事实，仅用于检验防线，不能证明产品已完成活动登记或真实跨进程排空。隔离容器在测试后删除。

上述阶段回写的执行身份校验属于默认关闭的持久执行试验路径；旧版正式流水线未接入同一套持久代次与活动 fencing，不能把试验路径的测试结果当作旧版全链路保护已完成。
# 阶段摘要与授权窗口收尾（本地验证）

## 终态报告当前读的负载门禁

为阻止 MySQL RR 旧快照漏读新发现及并发生成重复报告，终态补报现在锁定当前委托，并对相关发现、阶段和报告采用当前读。隔离 MySQL 8.0.45 实测：目标委托没有 finding 且补报事务持锁时，另一项目插入 finding 会等待 `uk_pentest_finding_engagement_fp` 的 `X,INSERT_INTENTION / supremum pseudo-record`；补报事务结束后插入继续。对应无阻塞期望为 `test_mysql_pentest_terminal_report_lock_scope.py` 的 strict xfail。这是本地可复现的跨项目等待，不等于生产已发生死锁或可以接受生产负载；发布前须设计并验证安全的事务/索引方案和负载，不能用旧快照普通读取替代当前读。

隔离 MySQL 曾复现取消与完成/失败两向覆盖，以及旧终态快照在重跑后漏取消、错误补报或重复创建报告。当前取消、完成和失败在写回前锁定并重读委托，已终态不再被迟到的取消/完成/失败覆盖；终态报告在当前行及当前相关数据下生成，完成/失败事件只在相应状态提交后发送。最新本人执行的隔离 MySQL 组合为 **21 项通过、1 项 strict xfail**，覆盖上述先后顺序、已提交发现及报告、本人取消和终态权限；独立复核仍进行中。旧版没有不可复用的持久执行代次，同秒重跑或跨进程旧 worker 的 ABA 不能用状态与时间戳排除，不得将本次修复描述为完整旧代 fencing。

独立 MySQL 另复现试验路径跨账号取消死锁：真实 worker 先锁 owner 后等待项目，管理员取消先锁项目后等待 owner，数据库选择 worker 为 1213 victim。取消入口现按账号 ID 固定顺序锁 actor 与 owner，检查账号、令牌及当前管理员角色后再锁项目和委托；本人仍可在项目成员权限撤销后安全取消。最新本人隔离 MySQL 取消、终态、补报和真实 worker/超管取消组合 **16 项通过、1 项 strict xfail**；独立复核确认真实 worker/超管和双普通管理员交叉取消通过，本人取消/撤权/退款组合 **25 项通过、1 项既有 strict xfail**，另验证本人取消先锁时真实退款审核实际等待后两者成功。交叉管理员用例未单独观察等待；锁顺序修复不代表其他所有调用或生产负载已验收。

- 隔离 SQLite 重现：阶段 runner 写入内存摘要后，边界检查通过 `rollback` 刷新快照，导致成功阶段摘要被清空；旧路径和持久执行试验路径均受影响。现在先保存摘要，并在重新核对执行与权限后，与输出和成功状态一起提交。账号先停用时，迟到摘要与输出均不发布。
- 隔离 SQLite 重现：持久执行到授权窗口末尾后，原普通执行校验先拒绝过期，轮询无法把仍为 running 的委托改为 expired。轮询现在使用只允许检查和终态收尾的独立校验，仍需当前账号、项目和代次有效；过期后不能登记新的模型活动，过期报告可在有效权限下发布。终态不代表远端执行已结束。
- 以人为构造的矛盾持久记录验证：活动写有 `finished/not_sent` 却仍关联缺失、未知或已释放预占，或关联沙箱环境时，旧排空判断会误放行。现保守保留全部此类关联为未决，父线程退出和手动底层确认都不能排空；未关联的真实未发送活动仍可正常收口。这些夹具证明一致性校验缺口，不证明真实 provider 已产生该矛盾；关联完整性与跨事务对账仍未闭环。
- 目前所有执行入口的活动登记完整性尚未验证，因此即使父/子退出事实都已记录，也不得把运行标为 drained。执行服务内增加固定关闭的完整性门禁，不能通过配置开启。隔离测试用真实线程复现：操作系统线程已经启动、bootstrap 尚未登记标识时，`ident` 仍为空且 `is_alive()` 为假，因此一旦调用过 `start()`，其异常不能只凭这两个字段认定线程未启动；此类启动异常也保持未决。旧的父子归并正向测试显式模拟未来完整登记，不能当作现有全链路排空证明。
- 独立隔离 MySQL 复现历史数据绕过：人为构造历史 `drained`、有父退出时间但没有活动登记完整证据时，旧版仍允许新代次。试验路径现将完整登记作为既有代次重跑和项目绑定证据的前提，旧 `drained` 也保持待核查；没有执行记录的未启动草稿维持原有判定。另在仅供测试的“假设未来登记完整”条件下发现旧代次与委托 owner/project 不一致可能被当作安全；现对全部历史代次核对归属，不一致时重跑拒绝、项目证据为 unknown。上述仅约束关闭的试验路径，当前旧版项目绑定尚未启用此门禁。
- 超管核查页面对归属匹配且状态为 unknown 的账务提供“账本对账”入口，并保留预占编号便于查找；归属无法确认或非 unknown 不显示入口。该入口进入既有双人账本对账，不代表线程或 provider 终止，也不自动解除执行冻结。前端定向 9 项、ESLint 和类型检查通过，真实浏览器尚未验收。
- 阶段摘要与授权窗口新增专项在一次性 MySQL 8.0.45 RR 空库、迁移至当时 head 113 后 6 项通过：取消、停用和到期先行时不写迟到摘要；正常写回保留摘要；写回先持锁时账号停用在 `performance_schema` 实际等待；到期后生成真实终态报告且新模型活动被拒。模型 runner 为替身，测试由实现者执行、独立复核待做。真实 provider、跨进程退出及生产行为仍需单独验证；持久执行试验路径保持关闭。

### 独立复核：取消、执行器和退款的锁序

在一次性隔离 MySQL 8.0.45（启用 `performance_schema`）中，从空库执行项目初始化和迁移；未连接生产数据库。管理员取消与真实执行器当前代次校验原先可形成锁环，修复前的独立探针实际复现 MySQL 1213；修复后管理员取消等待执行器持有的用户锁，执行器提交后取消成功。该场景已保存为 `backend/tests/test_mysql_pentest_admin_cancel_lock.py`。

`backend/tests/test_mysql_pentest_cancel_refund_and_admin.py` 另保存两项回归：本人取消持有用户锁，退款人工审核实际等待 `user` 行锁，放行后两者依次提交；两名普通平台管理员同步发起对彼此委托的取消，均成功。**双管理员用例没有捕获实际锁等待**，只证明该次同步并发运行成功；退款用例只覆盖取消先持锁的次序。三个持久化用例本轮合计 **3 passed、1 warning**，不能代替全部提交次序或生产验收。

此前独立复跑的终态竞争及报告补发组合为 **21 passed、1 strict xfail**，其中 xfail 是 MySQL RR finding 唯一索引的 supremum 间隙锁可能阻塞其他项目插入；本人取消、撤权及退款审批组合为 **25 passed、1 strict xfail**，后者是项目当前读的 supremum 间隙锁可能阻塞无关企业项目绑定。两项 xfail 不计为通过。上述 durable staging 测试不能证明旧内存注册表跨进程或重启后的 ABA、旧 worker 迟到写入已解决；相关接入和终止证据仍未完成。

### 旧版报告阶段与取消的并发保护

隔离 MySQL 复现旧版报告阶段通过前置检查后，本人取消已经提交，但迟到报告仍覆盖取消报告引用。现在报告写入事务依次验证当前账号及项目权限、锁定并刷新委托和此次报告阶段，检查归属、running 状态与授权窗口；报告与关联在同一事务提交。被拒的旧报告写入者仅回滚退出，不得调用通用中断收尾而跳过其他运行的阶段。

实现者在一次性 MySQL 8.0.45 完整建库链运行报告竞争、staging 阶段和终态回归 **44 项通过**；其中取消先提交后不覆盖取消报告、普通用户正常发布、模拟报告阶段被替换后旧阶段不得发布。另有 **172 项**个人渗透单元、JWT 撤权和事件测试通过。随后实现者对报告竞争四项单独复跑通过：报告已完成当前权限与阶段锁定、尚未写报告时，本人取消在 performance_schema 确认实际等待，最终保留单份取消报告；这次运行由实现者完成。有关旧版报告竞争的独立复核代理被环境检查中断，其后续复核未完成。

报告阶段身份由现有 phase ID 辅助校验，不能替代持久且不可重用的执行代次。旧版进程内 generation 仍可能复用，跨进程迟到 worker、所有写点及外部活动的完整 fencing 尚未闭环；持久执行试验路径仍关闭。报告发布新增的项目当前读可能受已知 MySQL RR 间隙锁影响，该新增路径的跨项目负载尚未独立量化，不得据此宣称性能验收通过。

### 执行与委托项目矛盾的反向检查

隔离测试先复现：委托已经改指新项目且状态为 cancelled，但历史 running 执行仍指向原项目时，原项目证据检查原先返回 clear。尚未发现正常业务入口会这样修改委托项目；这是合成数据矛盾，不是生产已发生的证明。关闭的 staging 路径现按项目、其委托及执行的顺序取得当前行后，反向当前锁读 `PentestExecution.project_id`；如果执行仍指向原项目但其委托不属于原项目，就返回 unknown。登记完整性开/关及 running/drained 等六个 SQLite 正反场景均通过；存在新项目时，委托 running 的新项目为 active，cancelled 的新项目为 unknown，原项目均为 unknown。

独立隔离 MySQL 8.0.45 RR 的 `backend/tests/test_mysql_pentest_reverse_evidence_independent.py` 为 **4 passed、1 strict xfailed**：旧快照下新旧项目判断正确；真实 `project_execution_evidence` 与合成归属写入按项目→委托加锁的两种先后顺序，均在 `performance_schema` 观察到项目行实际等待。归属写入为测试模拟，不能称实际绑定 API 或生产路径已验收。

严格预期失败复现新增的跨项目负载边界：原项目无执行而持有反向范围锁时，另一项目调用真实 `create_execution` 等待 `pentest_execution / ix_pentest_execution_project / X,INSERT_INTENTION / supremum pseudo-record`。这项 xfail 不是通过，需设计并验证不丢失当前读取安全性的锁/索引方案及负载；当前持久执行试验与完整登记门禁均保持关闭。
