# 退款查单响应核验

本地查单在验签后再核对订单和金额；不代表已完成商户沙箱或真实资金验收。销售代码锁继续关闭。

微信 [Native 下单合同](https://pay.wechatpay.cn/doc/v3/merchant/4012791877)要求商户订单号为 6 至 32 个允许字符。旧生成规则 `pr` 加 32 位十六进制为 34 字符，不符合该合同；新订单改用 `pr` 加无填充 Base32 随机数（128 位随机源，28 个字符）。历史订单号不改写，同一幂等请求仍指向原订单；旧微信订单若为超长号，不能再用于预下单，应保留订单和幂等证据、核实渠道状态后使用新的请求创建订单，不得推断旧订单未支付。已支付历史订单的查询和回调并未因为此新订单规则而重写或丢弃。

微信 Native 直连[查询单笔退款](https://pay.wechatpay.cn/doc/v3/merchant/4012791884)的 200 应答将商户退款号、商户订单号、`amount.total`、`amount.refund` 和固定为 `CNY` 的 `amount.currency` 标为必填。查单与本地订单号、退款号、订单总额和退款额逐项核验，并要求币种为 `CNY`；金额单位均为分。`payer_refund` 是现金退款，可能因为优惠小于申请退款额，不用于判断退款总额是否匹配。验签成功但币种缺失或错误时，查单失败并保持退款冻结；本地测试已覆盖这两种情形，真实商户应答仍待核验。

[支付宝退款查询](https://aipay.alipay.com/docs/vibe-pay/ai-web-app-payment-qianyi/api-list/alipay-trade-fastpay-refund-query.html)将返回的退款请求号、退款金额和订单总额标为特殊可选。接口若提供这些字段，逐项核验；成功状态缺少退款请求号或退款金额时，保持结果未知，不据此结算。该保守规则可能使合法但字段缺失的真实响应进入待核对状态，须结合商户沙箱、实际响应和人工对账验证恢复流程，不能假定所有场景必返这些字段。

支付宝文档说明查询过早可能在稍后出现成功；[微信退款指引](https://pay.wechatpay.cn/doc/v3/merchant/4013071031)也指出申请受理不等于退款完成。退款单、冻结及迟到结果的并发处理须由独立状态机和商户沙箱验证，不能仅凭查单一时未找到就推断原请求不可能成功。

支付宝响应节点使用原始 UTF-8 JSON 字节验签，符合[支付宝官方 SDK 的原始响应验签实现](https://github.com/alipay/alipay-sdk-nodejs-all/blob/master/src/alipay.ts)。本地测试覆盖节点内空白、转义、中文、嵌套、重复键、无效 UTF-8、尾随数据和错误签名；重复键及不合法报文拒绝处理。退款查单当前官方合同只明确 `REFUND_SUCCESS`，无状态时保持处理中，其他非空未知状态保持未知，不能据此解除冻结。相关网关、账单网关和订单 API 合计 **78 项本地测试通过**；这些结果不能替代真实商户响应和沙箱验收。

退款创建请求的超时、验签失败及其他异常，不证明渠道处理已结束，不记录为已收到有效创建响应。即使随后查单返回失败，缺少创建响应证据时也不能释放现有冻结；收到与当前尝试对应的有效创建响应后，仍须再次通过签名查单才能按失败结果恢复。查单先于创建响应时，迟到的有效响应只补充完成证据，不覆盖查单结果。无代次的结果不能覆盖已应用的查单结果；升级前的旧 worker 必须退出并完成在途请求清点。以上为本地隔离测试边界，不代替商户真实网络和资金核对。

历史已尝试但创建响应或验签查单代次缺失、不匹配的 `approved` / `failed` 退款，以及渠道状态并非明确 `FAILED` 的此类退款，禁止重新提交；最高管理员可经认领令牌重新查单。旧版本可能已经释放过积分，系统保留现有账本证据，不把这类订单宣称为已冻结；签名查单成功仍须核对本地批次，无法核对时进入人工复核。新增红测先复现 6 种缺失证据组合错误重发，修复后退款服务、网关、API 和迁移相关 **151 项通过**，退款页面 **15 项通过**。此结果不证明真实渠道结果及旧生产数据已核验。
