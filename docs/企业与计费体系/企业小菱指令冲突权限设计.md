# 企业小菱指令冲突：现状、边界和实施设计

## 原始目标与当前结论

企业群、小组群和企业内私聊的小菱应在同一事项出现冲突时优先听从有较高权限的成员；这不赋予发起人原本没有的资源访问、审批或执行权限。公司范围的所有者和管理员、当前小组组长及普通成员按现有会话内角色规则排序。私聊和小组会话仍须先满足该会话实际成员资格，不能凭企业管理员身份读取未加入的小组或其他人的私聊。

当前代码已给运行保存服务端角色快照，对后到的同级或更高权限成员 `@小菱` 消息阻断旧运行；角色撤销及结果发布竞争另有 MySQL 当前读测试。**对已经存在于同一上下文的自由文本冲突，是否遵循高权者仍主要依赖模型提示词，服务端没有完整的语义冲突判定。** `resolve_conflict` 是独立策略函数，目前没有接入运行时；`ask_user` 由模型决定是否调用，不能保证模型一定发现冲突。

### 2026-11-09 最新运行时状态

已在企业小菱运行入口接入同一冻结上下文的显式指令澄清门：候选限最近 30 条冻结人类消息中、由其他当前有效成员发送、角色等级不低于发起人且正文包含 `@小菱` 的消息。存在候选时先持久化 `model_send` 待处理项，运行不入队、不预占、不调用模型；原发起人只有在合格成员完成澄清后才能恢复。没有候选时写入精确上下文及权限版本证据。所有白名单工具调用也通过精确到调用 ID、工具动作、目标和参数摘要的独立澄清门；停止操作保留快捷路径。主动建议遇同类候选会停止，不发模型请求。

每一次 Responses 请求都在积分预占事务前检查模型发送证据，绑定冻结消息内容/作者/角色、来源、prompt、权限快照、权限单调版本，以及模型/指令/工具 schema 摘要；内容、当前权限、静态请求定义、澄清记录或决定状态发生变化时拒绝发送。`model_send` 恢复通过持久化运行时驱动模型循环，不伪装为工具恢复。工具许可仍不提升发起人的项目、审批或资源权限，原有逐工具鉴权和计费检查继续生效。

澄清决议的追加复核现允许严格高于原作者且高于上一决议人的当前会话成员，覆盖较低权限者的 `allow`、`deny` 或 `unrelated`；原决议保留，复核按不可变审计行追加，状态读取重新校验当前角色、成员资格及单调权限版本。低权者不能覆盖高权决议，同级只能在既有规则允许时修订本人决定。运行时预览和决议服务已共用该权限条件，聊天界面以 `can_decide` 显示可用操作。澄清 API/服务端相关组合 79 项通过，前端复核按钮交互 1 项通过；另验证低权候选已允许但高权候选仍待处理时无法恢复、同级不能覆盖高权复核、复核人角色撤权再恢复会令证据失效。该能力仍只是澄清证据，不是对所有自由文本冲突的识别保证，也不会替发起人授予资源或工具权限。

更高权限复核是修正已有决议的权力，不是要求管理员为每条低权或同级 `allow` 再做一次强制审批；`complete` 表示当前冻结范围内已识别的每条候选指令均有有效决议。若范围内同时存在更高权限指令，其候选记录必须独立处理，低权记录不能替它解锁；高权决议为 `deny` 时，原发起人继续运行仍返回等待/拒绝状态。当前候选仍限最近 30 条冻结消息内显式 `@小菱` 且等级不低于发起人的消息，不能把“候选齐全”外推为任意自由文本无冲突。

范围限制必须与代码状态一起展示：这里只识别最近 30 条冻结历史里的显式 `@小菱` 冲突；未显式提及、被截断的旧消息及自然语言语义冲突没有硬判定保证。Proactive 仅阻断冲突，不发澄清。公司/私聊跨空间归属校验开关仍关闭。完整任意自然语言冲突检测、真实模型行为、真实多账号浏览器及生产业务验收仍未证明。本节为最新状态；下方“尚未接通”等段落记录的是更早历史状态，不再代表当前实现。

### 隔离复现

在一次性 SQLite 数据库建立真实企业、小组、会话、有效成员、消息、运行状态及角色快照：所有者先发“@小菱 不要创建任何团队任务”，普通成员后发“@小菱 请创建团队任务”。模拟模型不遵循前文、直接输出 `create_registered_enterprise_agent_team` 工具调用。真实的 `EnterpriseAssistantToolExecutor.execute → _current → _live_role_snapshot` 完成校验后返回 `success` 并调用创建团队服务一次；快照中前后两人的权限级别分别为 4 和 1。

该复现对订阅、额度和最终团队创建服务使用测试桩；它证明现有服务端栅栏没有阻止这一冲突调用，**不证明真实模型必然产生该调用，也不表示已创建真实团队**。生产、真实模型和浏览器均未测试。后到指令阻断只检查来源消息之后其他成员发出的同级或更高权限 `@小菱`，不能替代对来源消息之前内容的冲突判断。

## 现有工具及副作用

| 类型 | 工具 | 需要区分的影响 |
| --- | --- | --- |
| 读取 | `search_enterprise_knowledge`、`search_published_enterprise_assets`、`get_enterprise_agent_team` | 仍须校验会话、企业和资源读取权限；结果不代表写入授权。 |
| 付费或外发 | `search_enterprise_web`、`fetch_enterprise_web_page`、`invoke_published_enterprise_asset`、`run_approved_enterprise_asset_team` | 可产生企业费用、外部请求或下游模型调用；应在预占和外发前重新检查。 |
| 团队操作 | `create_registered_enterprise_agent_team`、`cancel_enterprise_agent_team`、`retry_enterprise_agent_team_task` | 分别创建持久任务、改变任务状态及可能再次产生费用；目标及原发起人权限要重新核验。 |
| 草稿 | `create_private_agent_skill_draft` | 写入发起人的企业私有草稿，不能执行或发布。 |
| 公告 | `propose_enterprise_announcement` | 创建待审批请求；发布仍由另一名有效企业所有者或管理员审批精确内容。 |

工具目录以实际服务端白名单为准，未来新增工具必须明确其资源范围、副作用、预算和冲突约束适用性，不能只依赖模型选择。

## 现有机制的复用与限制

- `EnterpriseAssistantRuntimeState` 已保存运行、检查点、会话、发起人、角色快照哈希和租约代次，可用于绑定已有运行与并发防护。
- `EnterpriseAssistantApproval` 绑定运行、工具调用、参数哈希、决定者和状态；公告审批只接受企业 owner/admin，且不得由原发起人自审。其精确载荷和幂等思路可复用，但当前权限与结果类型不能直接覆盖小组长、同级冲突和一般澄清。
- `ask_user` 的回答接口要求原发起人回答。普通发起人的回答不能替代高权限成员的确认，也不能视作解除高权限约束。
- `EnterpriseChatMessage` 是会话中的原始文本及作者记录，不包含经确认的事项、资源、动作、约束有效期或撤销状态。不能仅根据消息中自称的职务赋予权限。

## 分层目标设计

以下是后续实现设计，**尚未实现**。它保留普通聊天及既有工具权限，并为可明确表达的冲突增加服务端可验证的约束；单靠引入结构化约束，不能自动识别所有历史自由文本中的冲突。

1. **身份与资源层**：操作前取得当前账号、企业和会话成员关系，组内还要校验当前小组成员身份；确定发起人对具体团队、草稿、知识或公告的现有资源权限。角色优先级不能扩大这些权限。
2. **经确认的约束层**：保存与会话内特定事项或资源关联的动作、允许或禁止、来源消息、确认作者、版本、状态及可选有效期。约束创建或撤销必须绑定当前有效作者，不能由模型单独创建、覆盖或解除。模型可提出候选供人确认，候选不产生授权。
3. **冲突判定层**：只比较同一企业、会话、事项或资源及动作的当前有效约束；高角色优先。同级相反的有效约束进入待澄清，不能自行选择其中一方；不相关事项和已失效约束不因历史存在而阻断。历史作者已停用、退出会话或角色变化时，以当前身份和版本重新核验，不能沿用过期等级。
4. **澄清与批准层**：澄清明确展示动作、目标、来源及有效冲突；由对该会话和事项有当前资格的人处理，并记录具体决定。小组内不能要求不在会话中的管理员读取群消息；同级冲突应允许相应作者撤销本人约束，或由有资格且更高权限的人解决，避免不可恢复的永久等待。公告发布仍走原有独立审批，不因澄清而绕过审批。
5. **执行与恢复层**：对同一运行、调用 ID、参数摘要及约束版本进行幂等绑定；在排队、计费预占、外部副作用和最终结果发布前按各自业务边界重验。成员撤权、角色/会话资格变化、规则更新、调用参数变化或租约更替时，旧确认不能继续授权新动作。未知费用保持既有对账规则。

### 自由文本的不可自动判定边界

任意自然语言可能省略对象、跨多条消息、使用代词或暗含条件；普通规则或模型分类都不能证明所有相关冲突已识别。要提供硬保证，系统必须要求有关成员明确确认结构化事项和约束，或在系统无法确定关联性时暂停有副作用的动作并交由有资格的人澄清。前者要求用户明确登记约束，后者可能对相关性未知的历史消息增加等待；不能把模型判断“无冲突”当成证明。

历史消息可能不在最近 30 条或被上下文长度裁剪；角色快照和提示词不能保证保留所有历史指令。正式约束若要跨上下文生效，必须独立持久化、可查看、可撤销、有明确范围，并以服务端记录为准。未登记或未确认的自由文本仍需标记为尚未形式化覆盖，不能将其宣传为已由服务端保证。

## 首个可独立验证的切片

以**当前会话内、指定已存在 `team_id` 的团队取消和任务重试**为首个切片，避免把每条历史消息与所有动作无差别绑定：

- 输入：当前企业、会话、有效成员、来源消息、具体团队 ID、`cancel` 或 `retry` 动作及经作者确认的约束。创建约束前核验消息确由该作者发送，并使用现有服务校验团队可见范围；约束不提供原本缺失的取消或重试权限。
- 匹配：仅同会话、同企业、同团队、同动作及当前有效版本参与排序；另一团队、另一动作和已撤销约束不得阻断。团队存在会话/项目隔离时继续取现有授权交集。
- 决策：高权有效约束与低权相反动作冲突时保守阻断；同级相反约束暂停；原发起人不能以自己的普通 `ask_user` 回答覆盖其他人的高权约束。允许作者撤销自己的约束并提供有权限者处理冲突的路径。
- 并发与恢复：操作事务按现有企业/运行/资源锁序设计并验证；约束新增、撤销、作者角色变更和工具动作竞争时，以已提交且持锁校验的结果为准。调用参数和约束版本变化时，不复用旧确认或旧工具结果；幂等重放不能重复取消、重试或计费。
- 验收：在隔离 SQLite 验证高/低权正反向、同级冲突、其他团队或其他动作不阻断、原发起人自答、作者撤销、权限丢失、跨企业和跨小组；在一次性 MySQL 的可重复读事务中分别测试约束/撤权先提交和工具先持锁两种顺序，观察真实锁等待；再以真实浏览器多账号核验澄清和恢复操作。真实模型语义能力另行测试，不能由模拟工具调用代替。

该切片只是验证结构化冲突机制的起点。创建团队、公告提案、私有草稿、付费查询与资产调用，以及任意自由文本中的冲突仍需逐项设计、实现和验收；完成该切片不能声称完整小菱生态或原始冲突需求已经完成。

## 完整交互与执行契约（待实现）

本节进一步拆解原始目标，不改变既有用户需求。`enterprise_assistant_policy.decide_trigger` 和 `resolve_conflict` 仍没有作为自然语言冲突的可靠仲裁器接入。原有本人 `@小菱` 路径继续要求消息由本人发送；公司群与小组群另有默认关闭的本地主动建议实现，具体证据及未完成项见《企业小菱受控主动讨论_设计与任务》。不应因策略函数或局部主动建议存在，就认为所有冲突和主动协作需求已经完成。

### 消息、议题和约束

1. **身份来源**：每条有效人类消息以服务端持久化的作者、企业、会话和当前有效角色为准；消息中的自称、模型输出、网页、知识条目与其他 Agent 输出不能创建或提升权限。公司群、当前小组群和两名参与者的私聊分别计算范围；没有实际会话访问权的企业管理员不能借澄清流程读取群聊或私聊。
2. **指令确认**：小菱可提出“这条消息是否构成某事项的允许或禁止”的候选，但候选只是建议。必须由消息的有效作者在会话内明确确认、修改或撤销；已确认记录绑定来源消息、作者、会话、事项或具体资源、动作、允许/禁止、版本和状态。约束不授予资源或付款权限。
3. **事项范围**：显式事项或精确资源 ID 可减少无关等待；由模型推断的事项关联不能单独作为排除其他消息的证据。没有可靠事项归属时先按当前会话范围处理。不能只扫描最近 30 条、只扫描 `@小菱`、或静默忽略历史消息，就声称已覆盖全部自然语言冲突。
4. **实际限制**：自由文本可能含否定、例外、跨消息代词、条件或后续修订，模型不能证明所有冲突都已识别。若用户要求对任意未登记的自然语言作硬保证，所有相关性不能排除的潜在指令必须停下来由当前有资格的会话成员澄清；原作者离线时可等待，不能因超时自动允许。对可明确归属的已确认约束按精确事项判断，其余仍须保持未知；不能把“模型未发现冲突”当证明。这意味着覆盖任意历史自由文本与完全无额外确认、完全不误拦不能同时保证。
5. **历史与变更**：保留约束及来源的审计历史，显示当前是否有效；作者撤回或有资格者作出新决定应形成新版本，不覆盖旧记录。作者退出、停用、移出小组、角色变化，或会话/资源权限变化时重新计算当前资格和优先级。历史尚未确认或无法读取的内容不得被自动写成已确认约束，也不得被猜测成“没有限制”。

### 可执行的决策顺序

对每个具体动作，服务端而不是模型做以下判断：

1. 固定企业、会话、发起人、来源消息、目标和动作；验证发起人的当前账号、成员、小组、项目/资源、订阅与预算权限。较高角色对动作的确认不能赋予发起人原本没有的权限。
2. 检索同会话、同事项/资源和动作的当前有效约束及尚未澄清的相关性未知消息。高角色的明确冲突优先；同级不同作者的明确冲突暂停并请求澄清。原发起人的普通 `ask_user` 回答不能替代其他作者或高权限成员的确认。
3. 仅有当前具备会话访问权、具备相应资格的作者或更高角色可对冲突作出决定；同级作者可以撤回或修订自己的约束。无合格处理者或处理者不在线时保持等待，可由发起人取消，不自动升级给无权查看会话的人。企业公告仍另走现有非发起人的 owner/admin 审批；冲突澄清不能替代该审批。
4. 将规范化动作参数、精确目标版本、调用身份、来源与冲突规则版本绑定到本次运行与调用。任一参数、目标、规则或当前权限变化，旧确认失效，重新核对；同一运行/调用/参数的重放只能返回原状态，不能重复创建、外呼或扣费。
5. 数据库内写操作在实际副作用事务中再次校验上述版本和权限；不能只在外层 executor 查一次后由另一个 session 无保护写入。付费/网络动作在预占和发送授权边界再次检查，已经获准发送的请求按“可能已发送”处理；之后的撤权可阻止新尝试和结果发布，但不能声称已发出的供应商请求没有发生或不计费。
6. **人工停止**：用户对自己有权停止的当前小菱运行作出明确停止时，应立即走现有取消和代次 fencing，不要求模型判断，也不被另一条聊天指令阻止；已发送请求仍按实际结算或未知对账。停止其他团队或他人运行仍遵循现有控制权限，不因角色排序自动扩大范围。

会话显示保持简洁：仅在等待时显示一个动作卡片，列出目标、精确动作、需要谁处理以及“确认/不允许/取消”；需要证据时再展开来源消息和规则。已完成或被撤回的历史可按需展开，不用重复标语和次要标签。对不可见的资源、群聊及历史，仅返回必要的无权或等待状态，不能在跨会话通知、错误或审计列表里泄露正文、私有目标或密钥。

### 群内受控主动讨论（局部本地实现，仍需验收）

- **明确区分三个入口**：本人 `@小菱` 是明确发起的请求；公司群/小组群的主动建议是受限讨论，不代表成员委托了业务写入；任何实际业务写入仍需要有权用户明确发起并按上述规则执行。企业内私聊沿用本人明确 `@`，不自动插话。不同企业、群和私聊独立隔离。
- **在任何供应商请求前建立条件**：企业及会话可用、来源成员及小组身份有效、已配置可验证付款主体和有效订阅、平台已开放计量、企业主动预算足够、存在可执行的调用上界。主动建议由企业钱包支付并归集到所属小组，不占用员工个人钱包或员工个人额度。尚无可靠计价或预算时不发送模型、搜索或抓取请求；不能把“主动建议”变成未计费的平台代付。管理员可管理企业级主动讨论开关和预算，并明确展示停用/额度不足状态；不开通或预算不可证明时不能自动外呼。
- **非递归和节流**：以企业、会话、来源人类消息和触发代次建立幂等键；同消息重复投递、刷新、worker 接管不产生第二次主动请求。同一会话限制排队数、触发频率、讨论轮数及每轮费用上界；机器人、其他 Agent、审批结果及小菱自身消息不能无界触发新话题。运行停止或权限撤销后不自动恢复人工停止的任务；意外中断按现有检查点和未知费用语义恢复或待核对。
- **主动建议的权限上界**：不把未 `@` 消息的作者隐式冒充成已经委托写操作的人。主动分支只能形成会话内有权可见的建议或提出待确认计划；不能自行创建团队、草稿、公告、重试、外部查询或调用其他资产。若建议需要这些动作，须等有权成员明确发起，随后进入原有资源权限、冲突和预算门禁。仅能向本会话发布对该会话受众可见的数据；不因为触发者个人有权就把私有项目、他人私聊或小组数据广播给公司群。
- **冲突先于主动输出**：主动建议同样不能覆盖较高角色的已确认约束；相关性不明时不自动认定不存在冲突。可以在本地显示简洁的待澄清状态，不能用模型自信程度当授权，也不能把高角色或不在本群的人拉进无权会话。消息删除、角色变化、规则撤销和新指令到达时，继续按运行租约与版本重验。

### 验收与未实现边界

最少覆盖：公司群/小组群/私聊各角色；高低权正反向、同级矛盾、同一作者明确修订、离职/降级/移组、规则新增/撤销与工具竞争；不相关事项、历史未确认消息、中文否定/例外/代词、伪造角色和外部提示注入；所有上表工具的参数变更、重放、未知账单与权限撤销；组外管理员不能查看会话，群成员不能借他人权限读取私有资源；用户停止优先且不把已发请求标记未发送；群主动触发去重、循环、预算不足和停用行为。

隔离 MySQL 仍需验证“规则/撤权先提交”和“动作先持锁”两种真实顺序及跨企业隔离；真实浏览器按多账号验证卡片、切群、刷新、等待者离线和撤权；真实供应商/费用另行核验。主动建议的局部测试不等于完整验收；模拟模型选择正确、静态文档或健康接口不能证明自由文本语义冲突已解决。

### 候选版本契约

1. **逐行身份与单调版本**：后续迁移为实际参与授权判定的账号、企业、企业成员、小组及小组成员建立受数据库保护的单调版本，并为允许删除重建的授权记录建立数据库生成、普通 DML 不可指定或修改的唯一实例标识。快照必须绑定企业、对象类型、对象标识、实例标识和版本。仅比较自增 ID 与从 1 开始的版本不足以防止显式复用 ID 后重建。实例标识的生成、唯一性与权限限制必须在目标数据库上实测，不能仅依赖应用约定。
2. **覆盖决定与上下文**：保存发起人、所有无法证明无关的有效来源作者、实际决定人的当前账号、成员和必要的小组成员版本；同时固定企业/小组/会话身份、源消息及相关消息的不可变身份或版本。会话范围、发起人、作者、决定者、具体动作、目标、参数、付款主体或任一适用版本变化，旧意见不得直接授权。角色版本不能替代项目、资产、公告、钱包、额度及订阅的实际权限与版本检查。
3. **数据库强制变化**：MySQL 候选做法是在受影响的真实行更新时，由同事务行级触发器对指定权限字段的有效变化递增版本，并禁止回退、伪造实例身份或原地改变租户归属键。字段未变化可不递增；事务回滚后版本与业务变更一起回滚。物理删除和重建、显式指定相同主键、`REPLACE`、`INSERT ... ON DUPLICATE KEY UPDATE` 及批量 SQL 都须专门验证。应用数据库账号不得具有删除/修改触发器、禁用约束或随意重置版本的权限；具备数据库管理权限的外部修改不在普通 DML 防护保证内。
4. **触发器与跨数据库限制**：当前 MySQL `user` 表已有迁移 022 创建的 `BEFORE UPDATE` 触发器；新触发器的顺序、权限、现有规则、备份和恢复都必须一起验证。MySQL 8.0 同一事件和时机可有多个触发器，但其外键级联动作不会触发子表触发器，因此相关外键的 `CASCADE`、`SET NULL` 和直接父表变更必须盘点，采用禁止级联、父级版本联动或其他经过实测的方案，不能默认子表版本一定增加。[MySQL 8.0 CREATE TRIGGER](https://dev.mysql.com/doc/refman/8.0/en/create-trigger.html)
5. **SQLite 独立验证**：SQLite 不能直接套用 MySQL 修改 `NEW` 的触发器写法；如采用 `AFTER` 触发器，必须验证递归触发器、显式写版本、删除重建和与 ORM 的配合。SQLite 的 `RETURNING` 不反映后续 `AFTER` 触发器修改值，ORM 必须重新读取；SQLite 测试不能证明 MySQL 的锁和触发器行为。[SQLite RETURNING](https://www.sqlite.org/lang_returning.html)
6. **消息变更栅栏**：可考虑在会话行上维护与新增/修改消息同事务的单调消息版本，用于发现会话新消息，而不把 `MAX(message.id)` 当作提交顺序。所有应用与直接 SQL 消息写入是否都受数据库机制约束、其锁顺序和对跨会话性能的影响仍需验证；无关消息也可能使待处理请求失效，不能声称这个机制已解决议题相关性。

### 事务、迁移和恢复

- 当前企业小菱部分路径按 `run → state → enterprise` 获取锁，团队运行路径存在 `enterprise → member/group → run → state`；发消息和组织变更也有各自锁序。引入版本门禁前，必须逐入口绘制实际锁序并统一或消除反向依赖，再用独立 MySQL 双事务测试撤权先提交、动作先持锁、消息插入、重试及死锁恢复。不得只在外层 executor 检查后由新 session 无保护地执行真实副作用。
- 供应商请求与数据库不能作为同一原子事务。发送前必须有精确请求的授权、租约、费用预占和可核验的发送边界；撤权先于发送授权应拒绝，授权之后是否已发送按真实发送证据、账单结算或未知对账处理，不能声称已发出的请求被撤回。本人停止继续走既有取消与租约 fencing，不依赖冲突澄清。
- 版本机制宜由 115 后的新迁移引入，不把旧 115 请求自动转换为有效授权；旧请求缺少完整版本证据，应保持不可用于执行。正式接线和滚动升级前，必须验证新旧应用共存、触发器状态、数据库账号权限及开关默认关闭。应用回退不能让旧版本绕过已经开启的授权门禁；回退方案须先关闭相关商业执行入口并核对未完成运行。
- 恢复旧数据库备份可能回退所有行版本；恢复流程应使所有未完成或来源不明的旧决议失效，并单独核对备份后可能已经发送的模型请求与账单。数据恢复、历史聊天或已发送供应商请求不能靠版本号自动撤销。

### 下一阶段验证与用户操作代价

必须覆盖：管理员降级再恢复、退出企业/小组再加入、账号禁用再启用、会话身份变化、源消息修改后恢复、不同租户与私聊隔离、直接 SQL 修改、删除后以相同 ID 重建、相同值更新、回滚、旧 MySQL 可重复读快照、授权和撤权竞争、触发器与 022 共存、迁移前后数据及账单不变。角色版本、锁序和对应业务调用都通过后，才能把证据服务接入真实权限判断；真实多账号浏览器与外部服务费用仍分别验收。

对于相关性无法证明的历史消息，候选方案仍需要有关作者或会话内更高权限者澄清；全量历史逐条处理在大群里会产生大量等待和长事务。下一阶段必须设计明确的人类确认议题、分页和可撤销的约束及其可访问范围，提供取消和过期停止，不因超时默认允许。未经证明的模型分类或截断历史不能代替这一确认；它们可能减少等待，却不能提供覆盖所有自由文本冲突的硬保证。

## 团队结果在会话中的可见性（本地修复）

- 复现：真实 SQLite 企业、小组、私聊、团队与成员数据中，同一账号有权读取两个会话的团队；通过 A 会话的小菱调用 B 会话的团队详情，修复前返回成功并包含 B 会话内容。当前群里，发起人有权看的团队目标同样会作为工具输出交给模型，可能被转述给无权看团队详情的群成员。
- 修复：小菱读取团队时，先由团队服务在读出详情前核验来源会话与当前运行会话一致，并继续执行当前成员、团队结果和项目查看权限检查。成功时模型只收到“请在当前会话点击「团队进度」查看”，不含团队 ID、标题、目标或结果。会话标题栏的既有“团队进度”入口继续按当前用户加载列表及详情，详情接口保留独立鉴权。

### 118 的 SQLite 版本回退补强

独立复核发现，原 SQLite 触发器允许直接 SQL 把版本值回退，降权后恢复的旧澄清可能重新显示为 `recorded`；尚未发现可利用此操作的 HTTP 写入口。118 的 SQLite 安装逻辑现增加版本守卫：版本字段只允许保持不变或精确递增一次，回退、跳增和空值失败；权限字段变化仍由数据库原子递增。权限字段与版本同时写入时只递增一次，`PRAGMA recursive_triggers` 开启或关闭均不出现无限递归。直接递增版本会保守使旧证据失效；版本仍只服务于澄清证据，不构成执行授权。

回归：先记录 SQLite 两种递归设置下直接回退和同时修改权限/回退的 4 项红测，再验证修复；四类版本行的回退、跳增、空值、合法递增和同写单次递增均在两种递归设置下测试。完整相关 SQLite 定向 70 passed、104 deselected，独立组织及权限兼容 44 passed；一次性 MySQL 从初始化迁移到 118、同字段对等写入、竞争及真实 117 历史记录升级共 13 passed。MySQL 对显式版本写入保持原有数据库触发器行为：以旧版本和实际权限变化计算新值，不采纳调用者提供的版本。

### 118 独立复核发现：SQLite REPLACE 路径尚未关闭

SQLite 的外键未启用时，直接对账号行执行 `INSERT OR REPLACE ... SELECT` 可以重新插入相同主键并回写旧版本，绕过 `UPDATE` 版本触发器，使旧证据从 `stale` 回到 `recorded`；`recursive_triggers=0/1` 均已复现。现有项目源码中未发现这四类权限表通过 REPLACE 或原生 upsert 写入的直接路径，也未确认可利用的 HTTP 入口，但数据库层单调版本保证尚未闭合。

另外，`recursive_triggers=0` 时，REPLACE 的隐式删除不会触发原决定的删除保护；隔离复现中，直接 SQL 可把已记录的 deny 替换为 allow，使状态从 `denied` 变为 `recorded`。因此此前关于 SQLite 数据库层证据不可变的表述不包含 REPLACE，尚不能视为完整保证。简单地对现有主键一律拒绝 BEFORE INSERT 同时会拦截原生 `ON CONFLICT DO UPDATE`；不得以该补丁声称兼容 upsert。相关红测已保留，解决方案及升级兼容尚待独立审查；执行链继续保持未接入。

### SQLite 连接递归选项与 MySQL 替换的边界

隔离复核使用 SQLAlchemy Engine 的 connect 监听为 SQLite 连接设置 `recursive_triggers=ON`，并运行澄清、企业组织以及既有用户、计费和安全证据迁移相关测试，93 passed、2 条已知 REPLACE 红测未运行。开启后，已决定证据表的 DELETE 触发器可以拦截 REPLACE 的隐式删除；但权限实体表没有禁止普通 DELETE 的触发器，开启递归本身不能阻止权限行 REPLACE。主应用 Engine 与 Alembic Engine 是不同连接入口，外部 SQLite 连接也有各自的 PRAGMA；仅在一处设置连接选项不能形成跨连接硬保证。当前没有修改应用连接配置。

隔离 MySQL 8.0.45 上，默认外键检查启用时，`user`、`enterprise`、`enterprise_member`、`enterprise_group_member` 均可经 `REPLACE INTO ... SELECT` 或 DELETE 后按相同主键 INSERT 将版本 2 重置为 0，使旧证据从 stale 恢复 recorded；决定与复核证据表的 REPLACE 被不可变触发器阻止。故权限版本仅能保证受现有 UPDATE 路径约束的权限变更，不保证拥有数据库任意写权限者无法删除或替换行。目前未发现四类表的应用 REPLACE、物理删除重插或 SQLite upsert 写路径，不能将隔离数据库操作者的能力描述成已证实的 HTTP 漏洞。

现阶段不接入执行门禁。候选最小边界是限制运行数据库账号对权限行的 DELETE 与替换能力，保留现有成员软删除和正常 upsert；但这必须先逐项验证实际部署的级联、维护与迁移需求，SQLite 文件级访问者仍可绕过应用连接设置。若需要不依赖数据库写权限边界的持久代次保证，须另行设计和验证，不能把简单 INSERT 拒绝规则当成兼容 upsert 的修复。

### 118 REPLACE 修复复核（2026-11-09）
