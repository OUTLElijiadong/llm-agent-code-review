# 企业邀请撤销与单次使用并发验证

## 问题与修复

独立复核组织计费版本时，发现现有邀请接受流程先按令牌进行普通读取，再对邀请执行当前锁定读取，但未刷新 SQLAlchemy 已加载的对象。在 MySQL `REPEATABLE READ` 旧快照下，即使锁定读取得到最新数据库行，应用仍可能使用对象中撤销前的 `revoked_at` 或使用前的 `use_count`。该缺陷属于原有邀请流程，不是迁移 116 引入的计费归属逻辑。

隔离 MySQL 真实服务红测分别复现：邀请撤销已提交后仍可接受；单次邀请已被其他用户使用后仍可由旧快照再次接受。另一个并发顺序中，接受事务先持企业锁，撤销事务实际等待企业行并在接受事务提交后继续。

现于原企业锁之后，对本事务内调用者已修改的邀请先局部 flush，再以 `populate_existing` 执行邀请当前锁定读，按最新撤销、有效期和使用次数校验。局部 flush 保留同事务中尚未写出的邀请修改，并保持企业 → 邀请的原有锁顺序；邀请已不存在时安全拒绝。

## 本地验证

- 一次性、无持久卷的隔离 MySQL 8.0.45 从部署基线迁移到当时 head 116：邀请和组织版本组合 **9 项通过**。邀请测试覆盖撤销先提交、单次邀请先使用、接受先持锁与撤销实际等待，以及同一旧事务中存在本地未提交修改时并发撤销仍拒绝且回滚不影响已提交撤销。后者实捕 SQL 确认仅更新本地修改的有效期、不覆盖 `revoked_at`，并确认锁读刷新后 ORM 对象看到已提交撤销。
- SQLite 的组织服务、组织版本、116 迁移及 FastAPI 组织路由组合 **21 项通过**。路由测试使用身份依赖覆盖，验证其他企业不能撤销该邀请，以及本企业撤销后接受被拒绝；不能称为真实 JWT、多账号浏览器验收。
- 被修改服务、测试的 Ruff 检查通过。临时数据库仅使用合成数据，不涉及生产数据库或真实商户。

这不覆盖任务要求中的全部企业权限、模型费用、支付渠道、生产数据迁移或浏览器验收。新工作树的完整后端回归需要在所有并行改动稳定后重新执行。
