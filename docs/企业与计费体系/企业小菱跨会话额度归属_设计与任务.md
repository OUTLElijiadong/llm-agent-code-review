# 企业小菱跨会话额度归属：设计与任务

## 状态与范围

本文件是实施契约，**不是已完成功能**。适用本地工作树；生产部署、真实浏览器和供应商账单均未核验。销售和未完成的安全门禁继续关闭。管理员设置成员默认小组的前端入口已接现有后端接口并完成本地定向测试；新计费归属虽有关闭状态下的代码切片，尚未满足启用条件。

本阶段只修正新建人工企业小菱运行中，公司群与企业私聊没有计费小组的问题；不改变现有小组群、企业项目、主动建议、历史运行与历史账单的口径。多组用户可在其有权使用的其他小组群使用该群预算，本阶段不能声称所有小组预算都防跨组绕过。

## 已核对的现状与复现

- 企业小菱新运行将公司群、私聊设为 `group_id=None`，小组群设为会话小组：`backend/app/services/enterprise_assistant_runtime_service.py` 的运行创建段。`billing_ledger_service._limits` 只匹配小组为 `NULL` 或调用指定小组的额度，因此公司群/私聊不匹配组长设定的小组或小组内成员额度。
- 只读内存 SQLite 复现：企业额度 100000、小组 9 内成员 42 额度 0；传组 9 命中两条额度，传 `None` 仅命中企业额度。该实验直接调用真实 `_limits`，未调用真实模型、真实数据库或生产。
- `EnterpriseMember.default_group_id` 已存在；`enterprise_org_service.set_default_group` 仅允许企业 owner/admin 将其设为用户当前有效小组或清空。移除默认组会清空，移除企业和重新加入也不会恢复。本地管理界面已有设置入口。
- `run.group_id` 是会话权限范围而非纯账单字段：当前角色快照、组内权限和企业团队均使用它；迁移 094 的团队会话/父运行复合范围外键也依赖它。不能直接把公司群或私聊的该字段改成默认组，否则改变权限或破坏关系。
- 现有企业项目审查按项目绑定小组计费；小组群按群小组计费；主动建议用 `enterprise_auto` 企业独立预算。不能为补公司群计费而静默改写这些口径。

## 本阶段规则

| 入口 | 会话授权范围 | 新运行计费小组 | 配额与统计 |
| --- | --- | --- | --- |
| 公司群、企业私聊，人工 `@小菱` | 原公司群或私聊参与资格，不增加组权限 | 管理员设定的有效默认组 | 企业、小组和小组内成员等适用额度；账单按该组记一次 |
| 小组群，人工 `@小菱` | 原实际会话小组 | 原实际会话小组 | 保持现有小组额度与统计 |
| 未加入任何小组的有效员工在公司群或私聊使用 | 原会话资格 | `NULL`，即企业未分组 | 按企业及企业范围成员额度；不得伪造小组 |
| 已加入一个或多个小组但无有效默认组 | 原会话资格 | 未确定 | 公司群/私聊新人工运行在预占和外呼前拒绝，并提示联系管理员设置；不能任取首组或当未分组 |
| 公司群/小组群主动建议 | 原会话资格 | 保持现有会话口径 | 仅使用 `enterprise_auto` 独立预算，不占触发者个人额度 |
| 企业项目审查 | 项目原权限 | 现有项目绑定小组 | 保持现有计量口径 |

默认组只决定**公司群和私聊人工请求**的计费，不赋予默认组长读取公司群、私聊、其他小组内容或改变项目权限。用户及管理员界面必须明确指出该规则；不同群切换到其他有权小组可能使用该组预算，不宣传为全局防绕过。

## 数据、锁和兼容

1. 新增顺序迁移，保留 `EnterpriseAssistantRun.group_id`、团队/会话外键；在运行保存独立 nullable `billing_group_id`、计费归属版本以及默认组变更序号快照。企业成员增加默认组单调变更序号：真实改组、清空、移组/移出企业导致默认组变化同事务递增；无效输入和未变化不递增。新旧运行以独立版本明确区分，`NULL` 既不能单独解释为旧记录，也不能解释为无组已验证。
2. 创建运行时在现有锁序内锁定企业成员及其默认组关系，重验成员和组都属于同一企业且当前有效，冻结默认组及单调版本；不得信任客户端提交组号。新小组群运行保留会话组，主动建议仍使用原自动预算口径。
3. 每次新的模型预占、流式发送、Search/Fetch、已发布资产子调用及团队 Agent 子调用，沿父运行读取可信计费组，并在当前锁定读下重验成员、默认组状态和版本；默认组 A→B→A 不复用 A 的旧运行授权。会话和项目授权仍使用原 `group_id`。实施前须逐条盘点已有运行、组织、成员及钱包的实际锁序，并用 MySQL 两顺序实测，不能凭统一顺序的假设引入反向锁。
4. 已发请求按原预占和费率快照结算，默认组变更不能把费用转嫁、释放未知账单或重发；未发出请求按现有严格未发送协议释放。后续新调用因归属变化停止，新运行重新授权。
5. 既有运行和已存在 reservation 的 `group_id` 与费用一律保留；迁移只标记历史口径，不按当前成员关系回填历史。历史进行中运行继续按已冻结身份及既有未知费用协议处理；发布前应盘点旧 worker 和在途请求，防止新旧计费逻辑并行写入。历史曲线与新口径的截止边界须可辨认，不能声称历史费用均属于当前默认组。

5. 组件测试覆盖管理员设置、组长无权限、选择与迟到结果、无默认组提示；真实普通浏览器多账号验证公司群/私聊、小组切换、管理员变更、额度图和撤权。以上测试均须分别记录，不以模拟接口或空库迁移代替真实业务验收。

仍未解决的**双维度限制**：成员负责组 A 与其操作所在 B 群/项目各有预算时，单个小组字段无法同时约束 A 与 B。未来若需要同时约束而仍按 B 统计，应另行设计不可变双组快照、同 reservation 关联去重的多额度、月中新增额度的可核验重建、变更版本和账单说明；不得用现有单组行为宣称已经实现，也不能把企业钱包扣两次。

## 本地实施检查点与发送边界

迁移 `116_ent_billing_group`、组织版本、运行快照及部分父子调用归属已有本地切片；但公司群和私聊新人工运行仍由 `_CROSS_SCOPE_ATTRIBUTION_VERIFIED = False` 硬关闭。旧运行、小组群及主动建议维持旧范围。本人会话计费归属只读接口和前端展示已在本地接线；不得把测试内临时打开开关的结果视为已售功能。

只读接口 `GET /api/enterprises/{enterprise_id}/conversations/{conversation_id}/assistant-billing-context` 仅供当前账号访问自己有权的公司群或企业私聊，拒绝其他企业、他人私聊及被撤销成员；复用创建运行的归属解析和当前账号 token 版本校验。响应 `data.status` 为 `group`、`unassigned` 或 `default_group_required`，`group_id` 与 `group_name` 只在有效组时提供；`enabled` 只说明跨会话功能门禁，目前为 `false`，不保证后续请求成功、余额充足或获得执行授权。小组群不适用此接口；前端不得推断或缓存它的执行权限。

本地预览回归包含真实 JWT 的本人、他人私聊、跨企业、撤权、token 版本变化以及匿名和禁用账号；另在一次性 MySQL 8.0.45 全新迁移链验证旧事务快照下改组、企业移除、token 版本变化及私聊范围变化。私聊范围变化使用合成数据库更新模拟，仅用于验证拒绝旧快照，不表示产品提供此编辑功能。这些结果不代表浏览器、生产或全部并发安全已验收。

前端独立复核复现：门禁错误原与企业撤权共用 `40300`，用户已成功发送的聊天消息被清屏。后端现区分 `40360`（功能未启用）与 `40361`（需设置默认小组），前端显示对应状态并保留会话与消息，真实 `40300` 撤权仍清屏；后台状态 `billing_attribution_unavailable` 显示为可读文案，未知账单仍沿用待核对语义。另修正前台恢复时组织列表挂起导致旧计费预览不刷新的问题；该只读预览使用独立的 15 秒超时，刷新、切换身份或会话以及卸载时取消旧请求，既有模型等请求的全局 600 秒超时不变。企业沟通、接口和 HTTP 辅助函数 **108 项通过**，目标 ESLint、`vue-tsc` 通过；测试使用模拟接口，真实浏览器前后端联动和最终全量仍待验证。

最终检查结束至外发之间仍可能发生默认组 A→B→A；该未完成契约保留严格 `xfail`。Search/Fetch、资产和团队子调用的实际发送边界、旧独立 `enterprise_assistant_service.run_for_message` 的入口边界、成员及会话撤权和企业状态 ABA 均未闭环。未知账单不得自动重发或释放。

在本机 httpx 0.28.1 / httpcore 1.0.9，直连本地 HTTP/1.1 实验观察到请求体 complete trace 先于响应头；这不证明供应商接收。独立本地代理实验发现 CONNECT 能在目标 POST 前触发同名 complete，不能仅凭事件名解锁。trace 的事件跨版本不稳定；非 lock 依赖未固定 httpcore，生产版本未核验。代理、重定向、重试、流式上传、HTTP/2、异常和取消均需单独验证；未知能力必须保持门禁关闭。

将同步 SQLAlchemy 会话持锁跨 `await` 的实验接线已撤下。隔离 MySQL 8.0.45 和本地 HTTP 探针显示：另一个同 loop 协程同步等待行锁会阻塞 loop，锁等待 1.025 秒超时前，原定 0.05 秒启动的 HTTP 无法启动；持锁会话置独立线程本身也不能解决同 loop 等锁。第二个探针将整个发送 loop 放专用线程：竞争请求等待 0.322 秒，主 loop 原定 0.05 秒心跳同样延迟到 0.322 秒；独立成员行读取 0.012 秒。这些是隔离合成行和本地 HTTP 测试，不是企业业务端到端、生产或并发容量验收。

| 实际调用入口 | 当前执行位置与竞争点 | 未完成核验 |
| --- | --- | --- |
| 调度器队列 `dispatch_once` | 每运行独立线程 `asyncio.run(execute_queued_run)`，运行会话在线程内创建 | 同一 loop 还并发模型任务和取消轮询；需实测相关状态更新与锁竞争 |
| HTTP 新运行及 BackgroundTasks | 异步 `request_assistant` 调用同步数据库，后台登记异步 `execute_queued_run`，运行在 ASGI loop | 需避免与同一 loop 的同步锁请求互相阻塞，不能把现有请求 Session 传到其他线程 |
| HTTP 审批、答复、重试 | `decide_approval`、`answer_run`、`retry_run` 在 ASGI loop 同步数据库操作并直接续跑模型 | 仅改队列 worker 无法覆盖；须定义持久恢复、取消、幂等及多进程语义 |

| 组织、资产、团队、项目、知识库 | 多服务调用 `require_enterprise_member(lock=True)`；组增删、默认组和成员变更亦争用成员及企业行 | 全部实际调用链和锁序需覆盖，尤其不同用户与公司行的排队影响 |

独立 worker 是可评估的执行隔离手段，不是完整证明：还需要确保 ASGI 上所有可能同步等待相关锁的路径不会阻塞公共 loop，且每个线程独立创建、使用和关闭 Session。需要真实 MySQL 事务先后、并发其他成员、同 loop 取消与恢复、连接池和线程池耗尽、锁等待上界、进程崩溃及未知账单测试；已发或可能已发的费用不能视为未发送。所有受限调用闭环并通过真实多账号验收前不得解除门禁。

## 独立复核：关闭门禁与已排队运行

- 本地真实账本配合模拟供应商先复现：测试中开启归属功能并创建 v1 运行后，若在领取队列前或预占后关闭 `_CROSS_SCOPE_ATTRIBUTION_VERIFIED`，修复前这两种情况仍可发送模型请求。迁移 116 不会将历史运行伪造为 v1；复现数据来自显式测试开启，不能据此声称生产已出现。
- v1 的排队、恢复、团队新计费和工具授权现复用的 `billing_group.validate` 会再次检查进程内门禁；`frozen` 仅读取原快照，供已发请求结算和账本核对，不因门禁关闭而改写。预占后、外发前检查到关闭时保留 unknown；模拟请求已经发出后关闭仍允许按原快照结算、保存已完成团队结果。历史 v0、小组群和主动建议不因该 v1 校验改变既有口径。
- 关闭功能使用 HTTP 403 / `40360`，默认组缺失或失效使用 HTTP 403 / `40361`；真实权限拒绝仍为 `40300`。真实 JWT 的隔离 HTTP 用例验证了三种语义。后台队列若在预占前遇关闭，会记录 `billing_attribution_unavailable`，关闭期间不提供恢复操作；存在未决预占仍走原人工对账语义。
- 相关后端组合 **170 passed、1 strict xfailed**；一次性 MySQL 8.0.45 全新迁移链验证预览/组织版本/持久化 v1 门禁 **8 项通过**。测试中的请求外发为替身，MySQL 侧没有真实供应商调用。`--runxfail` 实测保留项确实是最终检查后改组仍外发，现限定专用异常以免把无关失败误计为 xfail。
- 本门禁是**进程内代码常量**，不是跨进程的即时开关；旧代码 worker、已经过最后检查的请求、Search/Fetch 和各子调用的真实发送窗口仍需分别处理。升级或回滚时须管控旧 worker 和在途请求；不能因此声称已支持实时安全关停或开放公司群/私聊新付费运行。真实浏览器、生产数据库副本、支付渠道及供应商账单均未验收。

### 发送栅栏并发补充验证

`backend/tests/test_mysql_enterprise_send_lock_probe.py` 使用一次性 MySQL 8.0.45 与本地 HTTP 服务器完成隔离测试：

- 假设持有发送人的成员行锁而不持企业独占锁，真实 `set_default_group` 或 `remove_enterprise_member` 仍先持企业行并等待该成员，另一成员的默认组变更因此等待企业行；MySQL `performance_schema` 分别确认等待 `enterprise_member` 与 `enterprise`。这是对现有锁序的观察，不是已接入的发送协议。
- 持企业行共享锁时，真实企业订阅退款能从人工复核经审核到处理状态并提交，退款挂起状态从 false 变 true；该探针未创建预占，不涉及真实收款或外部退款。故仅锁企业行不能证明发送与退款状态串行。还须覆盖申请、审核、发起、确认及各阶段与预占、账本锁的既有顺序。
- 另一个真实账本场景先对当前周期积分完成 reservation，再持企业共享锁并通过 `billing_group.capture` 锁定成员；未来续费周期的退款仍可通过审核并进入处理，退款挂起状态改变而 reservation 仍保留。没有发送模型请求或调用支付渠道；这证明假设的企业共享锁加成员锁不能保持预占后的退款授权状态稳定。
- 用真实 MySQL 账本、真实 `NativeResponsesTransport` 和本地 HTTP，在服务器接收请求体后分别取消及触发读取超时；均只观察到一次本地请求，预占保持 `unknown` 且金额未释放。为避免外呼，仅 provider 身份解析使用测试替身。它不证明供应商已收到，也不证明 Search/Fetch 或资产、团队调用的发送和恢复安全。
- 持锁 session 在专用线程时，另一个协程直接同步等待真实成员行锁，仍使其所在 event loop 在 MySQL 锁超时前无法按时启动本地 HTTP；此测试固化了独立线程不足以隔离其他同步竞争者的现象。
- 两个员工同时读取同一会话和同一默认组时，原排他读取会相互等待；当前归属校验将只读会话及组改成当前共享锁，隔离 MySQL 验证两人可同时读取，同时合成的小组禁用写入必须等锁释放、此后再次校验被拒绝。该测试没有开启外发栅栏，也不消除组织写入等待企业行的问题。

上述发送、互斥原型及预览的三组 MySQL 联合回归共 **14 项通过**；场景使用隔离数据和本地 HTTP，不能据此声称真实供应商或生产已验收。

当前不能证明移除默认组操作的企业全局锁安全：除了企业行，现有实现还排他锁定管理员成员和目标组等共享行；企业退款审核与发起的锁路径也不以企业行作为统一入口。后续如考虑共享锁或行级授权，必须先完整定义账户状态、管理员撤权、企业状态、成员和组变更、退款各状态及钱包的统一锁序或持久版本，逐条验证跨员工并发、移除、退款、取消、连接池耗尽和真实发送边界；在证明前保持现有锁序和新运行门禁。

### 企业订阅退款与发送授权的事实源及候选锁序

以下是尚未接入产品的候选方案；不改变当前门禁。企业订阅退款挂起以 `billing_refund_policy.pending_access_expression()` 为唯一事实源，按订单所属企业、商品 `enterprise_create` / `enterprise_renew` 关联；不能另存可能漂移的“退款中”布尔值代替它。它不仅取决于 `status`，还取决于 `provider_status`、`attempt_count`、`refund_creation_attempt`、`reconciliation_query_attempt`。特别是 `approved` 且渠道状态为空或在途时已经挂起，不应等到 `processing` 才阻止新发送；`failed`、`approved`、`manual_review` 在证据代次不完整时亦可能因待对账而挂起。

| 路径 | 对事实源的影响和当前真实锁序 | 候选序列化要求 |
| --- | --- | --- |
| `request_refund` | 订单当前锁读、已有退款锁读，创建 `requested` / `manual_review`；按商品可能锁钱包批次 | 企业订阅相关的创建事务也纳入互斥协议，避免后来新增状态被遗漏；须考虑不存在退款行时的索引间隙锁 |
| `review_manual_refund` | 先订单、后退款，再钱包/周期；`manual_review` 可转 `approved` 或 `rejected`，其中 `approved` 可立即令挂起为真 | 在订单、退款之后、钱包之前取得同企业授权互斥行独占锁；审批提交与发送授权有确定先后 |
| `prepare_refund` | 订单→退款→钱包/周期，修改 `processing`、尝试代次及证据字段；不先锁企业 | 在修改前取得同一互斥行独占锁，不能只盯 processing 而漏批准状态 |
| `update_refund_result` | 订单→退款→企业→钱包/周期；根据渠道结果、过时代次和冲突证据写 `manual_review`、`approved`、`failed`、`unknown`、`processing` 或 `succeeded`，成功也改变订单和企业权益 | 在企业及钱包之前取得独占锁，所有提前返回、迟到成功及冲突分支都须覆盖；退款失败恢复并非始终等于解除挂起 |
| 对账 `claim_refund_reconciliation` / `release_refund_reconciliation` | 仅修改退款行的对账租约与更新时间，不直接改变当前挂起表达式，但会先锁退款行 | 仍需验证与订单→退款→授权行的竞争及取消；任何以后改变表达式字段的实现必须进入同一协议 |
| 周期激活、续费、企业状态与自然到期 | 周期、企业和钱包变化也影响执行资格；到期可仅由时间推进 | 必须按实际公司/钱包锁序与数据库当前时间校验；版本递增无法阻止时钟到期，外发也必须受有限连接/写入时限约束 |

候选实现是为每个企业准备一个**只承担互斥和单调变更序号**的授权行；不存在或损坏时失败关闭。退款写事务在现有**订单→退款→授权行→企业→钱包**顺序内持独占锁并同事务递增序号；发送事务先持同一行共享锁，再使用新的可见快照计算原有退款事实源并校验企业、账号、成员与小组，直到可信传输发送边界。任何仍沿用旧二进制的退款 worker、直接 SQL 或绕过该事务的写路径都会破坏保证，须先通过部署排空、数据库权限及迁移兼容验证。已有预占和已发请求按原 reservation 结算或未知对账，不因权限变化自动重发或释放。

独立 MySQL 测试 `backend/tests/test_mysql_enterprise_billing_auth_protocol_probe.py` 仅在一次性数据库创建测试互斥表：真实退款审核批准、已核对失败后重新发起、迟到成功引发状态冲突三条事务，均覆盖发送先和退款先两种顺序；前者本地 HTTP 已发送后退款继续并可结算合成用量，后者提交退款状态后阻止本地 HTTP。另验证审核与测试版本递增在异常时一起回滚，以及未改造旧退款 worker 能绕过互斥表并提交审核。八项测试通过，以实际 `pending_access_expression()` 查询为准，不缓存布尔副本。该原型未进入应用，也不能证明多订单、所有退款分支、线程取消与池耗尽、Search/Fetch、资产团队或真实供应商安全。

`test_billing_refund_access_policy_matrix.py` 对 2304 组状态、渠道状态和证据代次组合验证退款 SQL 谓词及对象对账谓词；其中包括不可能或损坏的数据组合，不表示所有状态变更均被允许。该决策表与原退款服务测试联合运行 **95 项通过**，但尚不等于新互斥协议覆盖了所有事务分支。

正式实施前还必须证明发送与所有退款入口严格遵循同一顺序，尤其禁止发送端先持企业/钱包再等授权行、退款端先持授权行再等被发送端占有的反向锁；为新增企业和历史企业原子初始化授权行，不允许回退为未锁检查。还需复核公司群/私聊以外所有会同步等待这些锁的 ASGI 和 worker 路径、同 loop 的停止轮询、单调版本 ABA、超时/取消、幂等、未知账单、多进程迁移和恢复，并进行真实 MySQL 与普通浏览器多账号验收。只有完整证据具备后才可考虑解除门禁。
