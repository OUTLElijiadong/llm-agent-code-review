# 个人渗透终止证据与企业绑定

## 2026-11-09 最新本地门禁状态

虽然个人渗透持久执行 staging 仍关闭，企业项目绑定现在无条件调用 `project_execution_evidence`。有启动时间但没有持久执行代次/完整子活动和沙箱终态证据的旧委托返回 `unknown` 并拒绝绑定；正在授权或执行的委托由原状态检查拒绝。没有运行记录且 `started_at` 为空的草稿、待授权申请、取消或过期委托可继续绑定；已授权任务仍须先取消授权。测试先复现旧实现可绑定已启动的 `cancelled` 委托，再验证修复；个人渗透证据和绑定组合 86 项通过。

这只修复了绑定时的 fail-closed 判定，没有证明个人渗透旧/新执行已全部写入可靠终止回执，也没有建立管理员核查和历史恢复工作台；不能据此开放持久运行 staging 或声称这条执行链完整。

## 已复现的边界（2026-11-09）

个人委托取消会立即将数据库状态写成 `cancelled`，但并不等待在飞工作线程退出。企业绑定只检查 `authorized`、`running` 状态，因此取消后仍有线程活动时也可以绑定项目。隔离 SQLite 探针 `/tmp/test_prism_binding_live_cancel_probe.py` 使用真实绑定服务与 `_register_pipeline` 模拟仍存活的工作线程：预期绑定被拒，实际未抛 `ConflictError`。该测试证明绑定门禁没有检查该条件，不证明真实供应商或沙箱已在绑定后继续发生外部行为。

## 现有执行与恢复事实

- `PentestEngagement` 没有持久运行代际、工作进程租约、子任务终止回执或停止完成时间；`_PIPELINE_REGISTRY` 和 generation 仅属于本进程。
- `cancel_engagement` 立刻提交终态；`delete_engagement` 承认同进程线程可能仍在飞而检查进程内注册表。`start_engagement` 对 `failed/cancelled/expired/completed` 在授权窗口及规则满足时允许重跑，也只检查当前进程注册表。
- `_phase_detect` 的线程池使用 `shutdown(wait=False)`，父流水线退出并注销本地 registry 后，已经开始的子推演线程仍可能收尾；因此即使该注册表为空，也不是全部子任务终止的证据。
- `_run_sandbox_probe` 在取消时尽力调用停止；异常只记日志并依赖 TTL，停止请求或 TTL 时间到本身均不能证明实际环境已停止。
- `_pentest_billing_scope` 在新模型预占前复查状态、代际、项目权限与企业归属；它不能撤回已经发送的请求，也不能证明非模型沙箱已停止。已产生的真实用量仍需按原账本结算或冻结核对。
- `sweep_stale_engagements` 启动时把所有 `running` 置为 `failed`，`sweep_orphan_running_engagements` 按本进程注册表判断孤儿；两者不是其他进程工作已终止的证据。当前 Dockerfile 配置单 Uvicorn worker，但不能把配置当作迁移切换、其他进程或在飞外部任务的终止回执。
- 企业小菱已有持久 lease generation / execution token 及结果 fencing，可参考模式；该状态仅覆盖其自身运行，不能直接作为个人渗透任务的停止证明。

## 目标设计与兼容边界

1. 为每次个人渗透启动持久化唯一运行代际、所有者、范围、状态、租约与取消请求；运行、绑定及恢复在同一项目/运行锁序下复验。旧 worker 不得以新代际写入阶段、发现或报告。
2. 将可能在父线程之后继续运行的模型子调用和沙箱执行与所属代际关联，持久记录启动、发送、已确认完成/停止和未知状态。父 worker 退出、未来取消、租约到期、重启或发出 stop 都不能单独证明子调用已终止。
3. 发起外部请求前与结算/产物写入前持久校验当前代际和授权；结果到达后如用户取消或项目绑定发生变化，照实结算已产生费用但抑制不再有权发布的内容。沙箱须等待可信终态或通过受控对账/人工核实，无法证明时保持待核查。
4. 绑定项目时，在项目锁内检查该项目所有个人运行代际及关联子任务/沙箱没有未终止或未知执行。发现活动或证据不足时清晰显示待停止/待核查；已授权、running 的现有保护继续保留。
5. 旧记录没有可回填的终止证明时不能依据 `cancelled/failed/completed`、`completed_at`、本进程 registry 为空或一个超时推断已终止。历史数据必须先盘点；可提供有审计的、基于可信进程/供应商/沙箱状态证据的人工核查与释放路径，不伪造历史记录或自动发送请求。旧未运行的 draft 及可证明未启动的申请应继续可绑定。
6. 用户重跑必须以新持久代际、独立幂等键与预占发起，旧代迟到不得覆盖新代结果；若存在未解决的在飞/未知费用或不可确认的旧环境，则不自动重发。部署切换需清点并退出旧 worker，迁移与恢复演练不得把未验收的旧进程当成已停止。

## 为什么不能立即对历史记录一刀切

现有结构没有持久终止回执。简单拒绝所有 `started_at IS NOT NULL` 的终态记录会把正常完成的历史个人项目一并锁住；仅允许 `started_at IS NULL` 又无法证明所有旧空值都从未启动。只检查进程内 registry 或只设置数据库 `status=cancelled` 会漏掉跨进程、子推演及沙箱在途。生产中受影响记录数量和实际运行状态尚未读取，当前不能声称历史迁移兼容已解决。

### 供应商公开契约核对（2026-11-09）

- [DeepSeek Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/) 描述响应终态和 usage；本次未在所查接口页面找到按请求查询、取消并提供可验证远端停止回执的契约。这不证明供应商没有其他未公开或另行签约的能力，也不能将连接关闭当作终止证明。
- [DeepSeek Responses 指南](https://api-docs.deepseek.com/guides/responses_api/) 明确不支持 `store` 和 `background`，响应固定不存储；因此不能仅切换 API 格式，就认定断线后可以按请求恢复状态或获取停止凭证。
- [连接与限速说明](https://api-docs.deepseek.com/quick_start/rate_limit/) 中的 10 分钟断开仅针对请求尚未开始推理的情况，不能推广为已发推理终止的时间上限。需要供应商提供可绑定具体请求的权威状态、终止和费用凭据及查询合同，或获得经验证的等效证据；缺失时模型活动仍为 unknown，账单使用现有独立 C4 流程核查，不能据账务结果推断进程终止。

## 执行代际重复使用与实施拆分

隔离进程直接调用 `_register_pipeline`、`_unregister_pipeline`、再次 `_register_pipeline`，同一委托两次代际均为 `1`；旧代与新代比较会误认为一致。因为推演线程池允许父线程退出后子线程继续运行，这个 ABA 碰撞不能用当前进程 registry 避免。该探针只证明值会重复，尚未证明真实迟到子线程已经造成外呼或写入。永久递增的进程内变量也无法跨重启或多进程提供持久 fencing。

具体实施分阶段，但只有所有阶段及验收结束才能称为完整闭环：

1. **数据与兼容预演**：新增独立运行代次与子活动表，分别带不可重用随机 token、委托/项目/付款人、状态、开始/心跳/取消/终止证据、幂等键与唯一约束；为 sandbox 子活动持久关联已有 `SandboxEnvironment.id` 和该环境执行 token。以迁移对照验证旧委托和账本不变；不把空值批量写成已结束。先用生产副本统计旧终态中已启动/时间缺失/关联沙箱仍在途情况，再确定界面及核查容量。
2. **主代次与所有写入口 fencing**：创建运行时锁项目并原子持久申请新 token；线程、并行推演、每次 provider 发送前的账本 gate、阶段/发现/报告持久化、取消、恢复与删除都传递并校验 token。状态只能单向推进；同一委托并发启动由数据库约束和当前锁定读防重。退款/权限和项目归属在副作用前重新验证，已发 provider 的费用与输出分开处理。必须检查所有后台回调，不能只在主循环检查一次。
3. **子活动及明确排空**：子线程提交前持久声明活动；排空时只有确实已完成的子活动才能标明终态。网络超时、进程崩溃、未收到 worker 终止回执均为未知，不以租约过期或本地线程退出自动视为远端完成。沙箱优先复用现有 `stop_environment`/worker 的持久停止墓碑：停止失败保留 `stopping`；必须先新增可信的运行→环境关联，再按真实回执判断，不能按同项目任意沙箱或 TTL 猜测。
4. **绑定和恢复**：在企业、项目和运行锁序内，绑定只接受当前无未排空或未知子活动的项目；对当前运行显示停止中，对历史缺证据显示待核查。历史记录通过最小权限、双人或其他已对齐的人工审核流程登记可信证据，不复制源码/凭据，也不重置已有用量和运行状态；历史终态是否能自动判定需按真实数据验证，不能设计成默认全部冻结。已发结果到达后仍按账本原约定结算，不能再向已改变作用域写结果。
5. **上线验证**：隔离 MySQL 验证 110→新迁移、项目绑定/发起/取消/回调双向锁序；人为阻塞外呼和并发子线程、模拟独立进程、租约到期、进程崩溃、沙箱停止失败、恢复重跑与旧 token 晚返回。随后用生产脱敏副本核对历史分布、备份恢复和 worker 切换；真实渠道、用户界面及操作人员恢复流程单列验收。

同项目独立触发的沙箱或其他任务并不必然属于该个人委托；持久关联必须按真实来源创建，不能把所有同项目活动误认成该委托的子任务。相反，已发送外呼产生的上下文无法事后撤回，若项目归属变更政策要求在未知外部处理期间继续等待，需要以可信回执或人工核查来解除，而不能声称系统可以强制终止供应商的计算。

### 当前代际类型与传播缺口

当前 `_register_pipeline` 返回 `int`，`_run_pipeline`、`_advance_pipeline` 和 `_pentest_billing_scope` 接受该整数；`billing_scope` 将捕获的 `attempt_guard` 放入上下文，并通过 `copy_context().run` 传入并行推演线程。该 guard 在预占时将捕获的整数与进程内 `_pipeline_generation` 比较，商业计量未就绪时 `_pentest_billing_scope` 则直接返回 `nullcontext()`。`_pipeline_alive` 的 generation 参数可省略；现有阶段内部及并行线程有多处只传 engagement ID，`_run_detect_line` 的函数签名也没有代际参数。因此，仅替换 registry 中的值、或只调整主线程比较，不能覆盖子线程、未计量兼容路径或所有写入。

建议新表以数据库锁下生成的单调 `generation_no` 提供可审计顺序，并以随机、不可重用的 `execution_token`（例如 UUID4 的 32 位十六进制字符串）作为实际 worker fencing 身份；两者同事务持久化，数据库对 `(engagement_id, generation_no)` 和 token 分别唯一。`generation_no` 必须在数据库中递增且不因注销或进程重启重置，token 不能由客户端指定。代次创建与项目绑定/启动状态共同锁定，避免并发启动各自获得有效代次。

执行期采用不可变上下文对象携带 `execution_id + token + project_id + payer`，显式传入 `_run_pipeline`、所有阶段、`_run_detect_line`、分片及沙箱执行；将 worker 路径的 `_pipeline_alive` 改为必须持代次（或提供单独的强制检查函数），不能把 `None` 解释为允许。原仅供读取/展示的非 worker 调用应单独保留 API，而不是制造一个省略 token 的隐式豁免。计费 `attempt_guard` 以数据库当前锁定读校验本代次、账号、项目和取消状态，响应结算与产物写入另行 fence；上下文丢失或绕过计量的兼容路径也必须在实际外呼前失败关闭。请求键包含 execution ID/活动 ID，同时保留原供应商请求的结算和幂等历史，绝不能把旧未知调用改造成新代次请求。

回归应先复现：第一代注册/注销后第二代获得相同整数；旧 detect 子线程在第一代父线程退出后阻塞，第二代开始再放开；即使新委托状态为 running，旧代不能预占、发新请求、写阶段/发现/报告，也不能取消或修改新代。还需覆盖不同 OS 进程、进程重启、多 worker、后台线程缺上下文及计量开关状态；真实已经发出的外呼保留账本核对，不能声称 UUID 能撤回它。

## 实施任务与输入/输出契约

以下任务按依赖顺序执行；在未覆盖全部 worker 和真实终止证据前，任何局部代码不得作为“项目可安全迁移”的证明。

1. **持久运行与活动模型**：输入为既有 110 数据及锁序；输出为新运行表（委托、项目、付款人、递增代次、唯一 UUID token、状态、心跳/取消/可信终止字段）和子活动表（运行、活动 UUID、类型、状态、关联 reservation 或环境、可信回执），不回填旧已终止事实。验收：空库和历史库迁移、唯一性、双启动只能成功一个；旧空值保持未知。
2. **原子启动与绑定**：项目行、运行行按明确顺序锁定；启动时持久领代次并先记录活动再放行副作用；绑定时同事务检查未终止及未知活动。验收：绑定先提交则不得启动或发送；启动先提交则绑定拒绝并给出可操作状态；完成前不能因 worker 租约过期而放行。历史未开始与历史已启动但证据不足分开，并在发布前量化受影响项目，不能隐式把历史终态全部标成已终止或静默禁用全部项目。
3. **上下文传播与代次验证**：主线程、全部阶段、ThreadPoolExecutor 子线/分片、账单 scope、sandbox 调用和终态回调均携带不可变 execution token；无可信 token 时不得发起外呼或写结果。验收：旧代 A 父线程注销、B 启动后 A 的迟到子线程无法发送、预占、写阶段/发现/报告；B 的付款和输出不被 A 撤销或覆盖。分别覆盖计量开关、上下文丢失、多进程和进程重启。
4. **外呼、停止与结算**：网络发送前提交不可重复活动；仅在可信响应、明确无发送或可校验的外部终止回执后结束，超时、连接中断、worker 丢失仍为 unknown。取消不等于排空；sandbox 复用现有执行 token 和停止墓碑，但关联必须在创建前预登记，并检查实际终止回执。验收：阻塞模型/子线、停止失败、TTL 到期、执行中断后，绑定不因父线程退出/lease 到期而放行；迟到用量仍可结算但不可越权发布。
5. **异常恢复与用户界面**：进程退出后持久代次不重用；孤儿和 lease 到期只转未知/待核查，管理员最小权限人工核查必须有审计与可验证依据。为正常已确认排空、未开始、未知和仍活动分别提供清晰原因与恢复路径；不因修复静默改变旧项目权限或旧账本。
6. **验收**：SQLite 仅验证状态机；MySQL 8 在 performance_schema 实测绑定/取消/启动/完成的两种锁等待和跨进程旧代 fencing。完整迁移链及生产脱敏副本演练、原功能自动化、真实供应商/沙箱与浏览器的验收各自记录，未完成者明确待办。

## 111 基础层状态（未启用）

已先增加失败用例，再新增迁移 `111_pentest_execution`、`PentestExecution`/`PentestExecutionActivity` 和仅供后续集成的服务基础函数；SQLite 迁移与服务专项 5 项通过。它分配持久递增代次和随机 token，未知子活动和租约过期不会被该基础函数自动标成排空，迁移不伪造旧委托的终止证据。

### 本地 staging 进度与未闭环项

- 模型调用已在现有 agent 的每次实际 HTTP 尝试前提交独立活动标记；隔离测试使用真实 agent 内部重试流程，在 429 后取消，验证后续尝试不再发送。标记提交后、网络发送前仍有间隙：如果取消在此间隙提交，调用仍可能发送；已提交活动必须视为可能已发送，不能宣称取消后绝不会出网。
- 沙箱创建服务在环境首次 flush 后、提交和启动 worker 前，于同一事务关联精确环境 ID 与活动；关联异常会回滚创建，提交后进程退出仍可按活动定位环境。创建返回后的附加核验失败时，仅对持久化记录证实同一账号和项目的环境尽力发送停止请求，返回清理待核查；活动继续保留未排空。已经记录到 SandboxEvent 的 worker 停止回执包含经验证的具体 request ID、终态和清理确认，以及 worker 和执行令牌摘要，但不能单独证明沙箱父执行线程、后续子请求及个人渗透活动全部退出。停止状态字符串和 TTL 本身均不是回执。
- 沙箱停止顺序增加当前锁定读，避免 MySQL RR 的旧 `running` 快照把已停止记录重新推进 stopping；新 worker 请求快照的更新条件排除 stopping 和终态，停止状态提交后刷新已登记请求列表。并行 stop 中后返回失败的调用，只有在当前 stopped 行及同 worker、同令牌摘要、全部具体请求的清理回执均匹配时才认可另一调用的成功；缺失或不一致仍报错，且不回退终态。独立 MySQL 8.0.45 的两向锁等待、旧快照、并行 stop、错误回执及 worker 正常或异常响应期间并发停止等 15 项通过；这些证据均不能推断整个父任务已结束。
- 调用者持有数据库连接时，模型和沙箱活动登记另开 session；独立 SQLite 单连接池探针复现真实模型调用路径借第二个连接超时，未发出模拟外呼，不代表生产已发生事故。staging 现从 worker 会话建立时跟踪事务，仅对单 Engine 且可确认无写入的受限结构化查询释放读事务；待写对象、已执行写入、文本 SQL、SQL 函数和嵌套事务均拒绝自动释放。模型配置解析前也先检查，防止其密钥安全更新提交调用方待写业务数据。单池测试覆盖真实模型解析、模拟传输、商业预占/结算、用量日志及模拟沙箱创建关联，仍须验证真实 MySQL、并发和其他所有调用点。事务守卫仅服务于已审计的 worker，不是通用任意 SQL 只读证明。
- 模型活动与其预占已通过预占同事务的回调建立 request key 关联；已结算和超时未知均保留对应关联。完整读取并关闭的响应可在结算已核实后记录本机响应摘要；该摘要不是供应商签名，也不是远端工作终止回执，活动仍保持 dispatched，无法据此排空。detect 子线程在提交 Future 前持久登记活动，Future 回调记录实际返回或明确的排队取消；主线程退出时也单独记录父线程返回时间。**由于完整活动登记尚未证明，父子返回的自动排空门禁固定关闭**。调用 `Thread.start()` 后发生异常，不能仅凭 `ident` 为空和 `is_alive()` 为假认定未启动；隔离真实线程可在操作系统线程已启动但标识尚未登记时呈现这一状态，因此该情形也保持未决。父子归并的正向测试显式假设未来登记完整，不证明当前全链路可排空。进程崩溃、回调写入失败、未知模型、沙箱或矛盾的账本关联均保留未决。全链路子任务终止证明、所有阶段同事务写入 fencing、历史核查及删除留存均未完成。上述事项完成并经跨进程、MySQL、外部服务和浏览器验收前，不得开启 staging。
- worker 触发的终态报告发布已增加当前代次及账号、项目权限的同事务锁定校验，旧代和撤权的隔离用例不能写报告；用户本人直接取消仍沿用户授权路径发布。独立 MySQL 真实角色/报告服务覆盖旧代、账号停用、本人取消以及报告先行时停用和退款审核的实际锁等待，共 6 项通过。退款后降为普通用户仍有现有 `pentest:start` 权限，因此仍可发布自己的报告，不能误判为退款撤权失败。推演线结果、发现和阶段失败的旧代、撤权拒绝已覆盖 SQLite 隔离测试。该局部校验不等于所有阶段、失败清理、重启扫尾或多进程写点均已闭环。
- 当前本地结果：原渗透/项目策略等回归 153 项通过；持久基础、上下文和绑定门禁 65 项通过；staging worker 和沙箱 26 项通过。部分 MySQL 行锁专项另有隔离验证，但这些均不是供应商、完整跨进程链或生产验收。

## 删除、留存与未知账据（接入前门禁）

111 的执行及活动表对所属委托使用 `ON DELETE RESTRICT`，用于避免无意删除排空/对账证据。开启外键的隔离 SQLite 中曾复现旧清理路径对有关联执行的委托抛出 `IntegrityError`；该结果不是生产故障证明。

本地删除和留存现使用同一门禁：先锁项目及委托的当前记录，发现任何执行证据均拒绝删除并提示联系平台管理员，即使执行已标记排空也先保留；自动清理预先排除有执行证据和未到期记录，避免其占满批次，并在锁定后再次检查状态和期限。MySQL RR 的旧快照可能漏见先前提交的执行记录，最终由外键拒绝删除，整个事务回滚后转换为明确冲突；这依赖数据库外键真实启用。无执行行的旧委托仍维持原有删除行为，**没有执行行不代表历史工作已经终止**。

本地 SQLite 覆盖未知活动、已排空记录、原有删除、批次饥饿、自动清理及本人取消；隔离 MySQL 8.0.45 覆盖旧快照外键回滚、删除和创建执行的双向锁等待，以及其他项目创建执行不受该检查阻塞。测试不代表真实供应商、跨进程完整执行链或生产已验收。管理员只读核查界面现已实现；可信终止后的审计留存/脱敏删除协议和历史任务恢复入口尚未实现，不能据此宣称存在安全删除流程。

本地报告补发已调整为独立阶段：过期但有执行证据而被留存的委托仍可补发缺失报告；候选查询后的只读快照经事务守卫释放，再锁定项目和委托当前行，重查终态和报告并在同一事务中发布。调用者带有既存事务（包括已 flush 未提交的写入）时直接拒绝，不能代为提交或回滚；启动阶段先关闭前一清理会话，定时任务使用同一干净会话依次执行。隔离 MySQL RR 覆盖真实启动与补发双向锁竞争、回滚、旧快照后的新内容、过期留存、候选饥饿和定时入口单连接池；实际 `main.lifespan` 的单连接池补发测试也通过，但其他调度、支付、外网和恢复钩子使用替身，不能代表完整生产启动。详情见[流水线事务验证](个人渗透流水线事务验证.md)。生成终态报告不证明任何线程、模型调用或沙箱已退出。

- 对运行中、排空中、未知调用、未确认沙箱停止或未结算 reservation，明确拒绝删除并保留详情及恢复入口；自动留存清理同样跳过，不能吞掉数据库异常或删除半套数据。
- 对所有活动、资金状态和外部终止都有可信终态证据的记录，先决定经过授权的数据删除与审计保留协议：在同事务中保存最小、必要且不含提示词/源码/凭据的不可抵赖摘要/审计凭证，明确其项目、付款人与保留期如何处理，然后安全删除或脱敏；不得将“状态 finished”本身当成证据。协议和可用恢复入口落地前，对有证据记录的委托返回明确待处理错误，不能用未知异常伪装成功。
- 覆盖发起人手动删除、管理员操作、定时留存清扫、崩溃重试和跨进程晚回调；验证 unknown 账单/沙箱不丢失，已合法终结的数据按约定可删除，原有不涉及新执行的历史记录仍遵守既有删除契约。生产迁移前统计实际影响，不能仅凭空库测试承诺兼容。

## 管理员只读核查界面

运行与审计中心增加仅最高管理员可见的“渗透执行核查”，按委托编号读取代次和活动，游标分页展示已确认归属的账务或沙箱状态；历史证据缺失、关联无法确认和外部调用未知明确保留。账号、令牌或权限改变时界面立即清空，迟到响应不能回填；查询失败也清空现有详情。小菱导航对普通管理员隐藏该敏感分区，服务端权限校验与访问审计仍是最终依据。

本地 Vitest 的界面与导航组合 109 项通过，目标 ESLint、TypeScript 与 Vite 生产构建通过。未执行真实多账号浏览器或生产验收；此页仅提供只读核查，不提供解锁、删除或对外部终止的确认。

## 父线程退出观察与旧证据兼容（114，本地试验）

在真实本地线程的隔离测试中，原 `_run_pipeline` 在自己的 `finally` 写 `worker_exited_at` 时，该线程仍存活；该时间只能说明内部函数已返回，不能说明 OS 线程已退出。现在关闭的 staging 路径在 worker 成功启动后启动独立观察器，观察器在无数据库锁的情况下 join 实际 worker，确认其已结束后写入 `thread_join_v1` 来源和时间。观察器启动、join 或写库失败，以及进程在记录前退出，均不产生可信退出来源；调用 `start()` 后抛错仍不能证明没有启动。线程退出不证明其子任务、外部模型或沙箱已结束。

迁移 `114_pentest_parent_exit_proof` 在 `113_ent_proactive_chat` 之后新增可空 `worker_exit_evidence`，不回填历史值。隔离 MySQL 从 113 写入原 `drained` 与退出时间后升级到 114，原时间保留、来源为 NULL；即使仅在测试中假设活动登记完整，该历史记录仍不能证明项目可绑定或启动新代。父退出写入及子活动归并也检查当前委托与运行 owner/project 一致；排空还要求当前委托终态与 owner/project 一致；重跑和项目证据检查所有历史代次的来源、状态及未决活动，较早代不可信不能被较新代覆盖。超管界面对缺少 join 来源的历史时间显示“待核查”，`drained` 标签显示“排空待核查”。迁移必须在启动依赖新列的代码前完成。

实现者本地验证：一次性 MySQL 8.0.45 的迁移、两个取消先后顺序、旧代、阶段、锁序与历史安全组合 **70 项通过**；此后增加归属矛盾防线，MySQL 的失败关闭与超管核查组合另有 **22 项通过**。实际 worker 内部逻辑采用等待替身，未调用真实 provider。加入归属矛盾防线后的 SQLite/真实 JWT 定向组合 **155 项通过**，前端核查页专项 **12 项通过**，vue-tsc 与目标 lint 通过。人工设置 `thread_join_v1` 的测试只检验未来聚合算法，不证明对应运行实际 join；独立复核及生产浏览器验收未完成。

仍需持久接入全部实际 worker、子线程、外呼和写回，对跨进程退出和崩溃恢复提供可信证据，并实现可操作的历史核查/恢复与合规删除。现有 legacy 无 execution 的删除沿用原合同，本地 registry 无跨进程证明；不能宣称该历史删除已安全。当前完整性门禁与 staging 保持关闭。对于 DeepSeek，官方 [Responses API 文档](https://api-docs.deepseek.com/api/create-response/)说明该接口不保存响应；本次检索没有找到可验证请求终止/最终计费的取消和查询合同，不能据此断言服务商完全不存在其他合同。需供应商明确提供可与请求绑定的状态查询、终止确认、最终费用及验证方式；断流、超时、TTL、父线程退出和本地响应摘要都不能替代证明。
