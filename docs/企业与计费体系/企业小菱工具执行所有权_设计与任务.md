# 企业小菱工具执行所有权：设计与任务

## 状态和目标

本文是待实施的设计与验收任务，不代表功能已经实现、验证或发布。目标是在企业小菱执行 Search/Fetch 时，让同一工具调用的重复执行者不能打断正在执行的请求、篡改共享检查点或重复外呼，同时保留企业、小组、成员、审批和计费边界。公司群、企业私聊与小组群均需纳入，不改变用户的原始功能需求。

当前销售代码锁和企业跨会话计费锁保持原状；本设计不是解除锁的依据。真实供应商、商户、浏览器多角色、迁移与生产验收仍须独立完成。

## 已确认现状

- `EnterpriseAssistantRuntimeState` 保存运行代次和租约期限，检查点存取校验代次；`BillingReservation` 用请求键唯一约束预占并保存发送标记，`BillingToolExecutionResult` 保存已完成工具的结果。现有数据没有独立工具调用的执行者所有权。
- 正式队列及恢复路径在领取运行时通过数据库锁递增代次；`DeepSeekResponsesRuntime` 的进程内锁只属于该 runtime 实例，不能覆盖不同实例。
- 隔离 MySQL 测试构造了两个使用同一运行代次的真实 executor：第二个在发送标记前重放会使未发预占释放；在标记后重放会使正在外呼的账单转为 unknown。两类场景均未观察到重复外呼，但会中断首个调用或要求人工对账。
- **同代重入是否能经当前生产 HTTP 或队列路径自然产生，尚未证明。**上述是直接调用 executor 的防御性并发探针，不能称为已在线上发生。
- 仅让重放者不修改账本仍不充分：它若把失败写入同一运行检查点，仍可能使原执行者失去继续或结算资格。若把重复状态当作可重试失败，也可能导致后续调用或检查点写入。

## 拟采用的契约

### 运行和工具所有权

1. 在运行领取事务内签发新的运行所有者令牌，绑定现有代次；检查点创建、领取、保存、最终回复发布和异常收敛均校验当前代次及所有者。不同 runtime 实例各自的进程内锁不能作为跨进程所有权证据。
2. 为每个精确工具调用保存独立、持久的执行所有权：绑定运行、`call_id`、工具类型、规范化参数摘要、企业/会话/发起人、账单请求键、运行代次、随机执行令牌和租约状态。运行和调用令牌不得进入用户响应、日志、模型上下文或检查点正文；不得允许后来的执行者仅凭读取数据库得到的令牌冒充原持有者。
3. 不同执行者争用同一调用时，非持有者只获得受会话权限保护的“执行中”观察结果；不得释放/结算预占、改变调用或运行终态、保存失败检查点、发布答案、继续其余工具或调用模型。新的内部返回类型必须逐层贯穿至队列、HTTP 恢复和结果发布路径，不能被通用异常处理转换成可持久化失败。不得把两个被复制了相同运行令牌的 runtime 当作同一工具调用持有者：工具领取还须具有每次实例独有的令牌与唯一原子认领。
4. 任一调用键重放时必须验证工具名、参数摘要、企业、付款人与冻结小组及钱包；不一致时拒绝，不创建新预占。已结算且结果已原子保存时，可按原调用键重放持久结果，不再访问供应商或再次扣费。

### 发送、终止和恢复

1. 持有者在最终发送事务中重新锁定并核验运行、执行令牌、当前账号和会话权限、澄清结论、企业状态、冻结计费范围、费率/钱包及额度，然后原子记录现有供应商发送标记。只有成功提交该标记的持有者可以开始一次 HTTP 请求。
2. **已发送或可能已发送的请求绝不自动重发。**租约到期不能证明原进程已停，也不能证明供应商未收到请求；供应商发送标记与网络 I/O 不可能组成一个数据库原子操作。已有标记且结果不确定时冻结并进入人工对账，即使经事后发现没有响应也不能推断未收费。
3. 接管或隔离先在相同锁序中核实租约、递增运行代次并使旧令牌失效，再读取标记。只有在锁内证明尚无标记、旧执行者不能再提交标记的情况下，才可按已证未发送释放预占；恢复、释放及审计须复用既有账本与审批契约。若标记已提交或提交状态不能确认，一律保持冻结。
4. 供应商结果、账本结算和工具结果应在同一事务中验证并保存；发布检查点前发生崩溃时，只重放持久结果。撤员、取消、权限或澄清改变发生在已发请求之后时，禁止后续动作并按已知/未知结果正确结算或冻结，不承诺撤回网络请求。

### 数据模型和迁移候选

- 方案首选在迁移 `121_billing_model_evidence` 之后新增独立前向迁移，增加工具调用所有权表，并按最终实现所需为运行状态增加 owner 字段。迁移号须在合并前重新检查唯一 Alembic head 后确定，不预占版本号。
- 为新表设置调用和账本键唯一约束、范围索引、状态与令牌/租约一致性约束；MySQL 与 SQLite 均须检查约束实际行为。历史记录的 owner 保持未知，不推断发送状态，不合成结果或补写令牌。
- `BillingReservation` 仍是预占/发送标记/账本权威数据，不能以所有权表中的超时或状态覆盖财务事实。外部证据引用和复核事件继续沿已有对账记录保存。
- 把所有权塞进 `checkpoint_json` 而不改变检查点的并发更新协议不可取：一次旧 `save` 可覆盖其他执行者写入；若最终选择该替代方案，须先明确版本比较、原子领取及合并规则，并通过与独立表相同的验收。

### 锁序与授权边界

候选顺序为 **运行 → 运行状态 → 企业/会话/成员及澄清 → 工具执行记录 → 钱包 → 预占及其额度/批次**。这是设计目标，不是当前所有路径已遵循该顺序的证明。实施前必须逐一列出并验证 Search/Fetch 预占、最终发送、结算、重放、取消、租约接管、人工恢复、退款/订阅、组织变更与消息写入的实际锁序；如存在不同顺序，先解决反向锁或设计不持有冲突锁的安全阶段，不能仅调整一条路径。

归属和权限依旧以服务端当前账号、企业、资源、角色及冻结小组为准；默认计费小组不授予组长读取公司群或私聊的权限。额外的 owner 令牌只用于区分执行者，不授予新的业务权限。

## 接口与用户体验

- 现有工具或运行查询接口需明确区分“执行中”“结果待核对”“已完成/已停止”；重复执行者只能读取自己有权查看的运行状态，不得获得其他企业或私聊内容。
- UI 对正在处理的请求提供状态与刷新入口；未知账单提示等待对账，对已发请求不提供自动重试。取消说明已经发出的供应商请求不能撤回。
- 在工具预占/结果不确定时禁止把局部读取成功或健康接口包装成业务成功。对管理员显示必要对账记录，不展示令牌和供应商凭据。

## 依赖与分阶段任务

1. **梳理合同**：列出所有 `_build_runtime`、队列、HTTP 新运行/追问/澄清/重试、异常及 `_result_for_runtime` 路径，确认何处签发/传递/使运行 owner 失效；复现正式入口可能或不可能产生同代双 driver，保留直接重入探针。
2. **事务设计**：完成各 writer 的锁顺序图、请求键/参数摘要和状态迁移表，定义非持有者无写入返回与租约/超时处理；先用隔离 MySQL 证明无反向锁，再实现迁移。
3. **所有权实现**：完成运行 owner、工具精确领取和检查点写入 fencing；维持原有调用权限、审批和账本验价；旧记录默认只读或走明确的人工恢复。
4. **恢复与结果**：验证标记前未发送释放、标记后未知冻结、成功结果原子保存及幂等重放；不能因进程存活探测或超时就自动重发。
5. **交互与部署**：接入非持有者只读状态、取消和对账提示；完成部署/回滚兼容探针、备份恢复和真实多角色验收。任何销售或跨会话开关的开放独立于本任务实现，必须满足原有商业与安全门槛。

## 分阶段验收

- [ ] 使用隔离 MySQL 从生产兼容基线迁移到唯一新 head，验证历史记录、两种数据库约束、部分迁移和幂等约束；证明旧 pending/reserved/unknown 未被改写。
- [ ] 独立进程和独立数据库会话同时领取同一运行、同一调用及不同调用；非 owner 无账本、检查点、回复或模型副作用；不同调用/不同企业的合理并发不被错误串行化。
- [ ] 按预占前后、发送标记前后、供应商接收前后、响应返回前后、账本提交前后、检查点保存前逐点终止进程并恢复；验证供应商调用最多一次，已标记/不确定请求始终冻结，结果保存后重放不重复收费。
- [ ] 真实 MySQL 测试小组变更 ABA、撤员/重入、登录凭据失效、企业停用、澄清 allow→deny、后到高权限消息、取消、退款与订阅变动；测试当前/旧事务快照、所有入口和锁等待/死锁。
- [ ] 验证持锁发送、异步事件循环心跳、线程池和数据库连接池耗尽、慢上游/网络取消；不得根据租约超时推断上游未接收。
- [ ] 验证旧运行、旧 reservation、旧执行器和旧检查点：升级后不自动放款/重发；部署前后探针正确拒绝不兼容旧 worker/镜像，数据库备份校验并隔离恢复；回滚不等同数据库降级。
- [ ] 真实浏览器分别用个人账号、企业员工、组长、企业管理员和平台管理员核对权限与操作提示；验证真实供应商和账单的条件具备后再做受控业务验收。最终 CI、精确 SHA、生产发布和发布后业务证据分别记录。

## 当前未解决项

工具和运行双层 owner 的确切数据字段、领取/续租事务、重复执行的非写入返回协议、过期未标记预占的安全恢复方式及与现有审批/退款锁序的兼容，必须在代码实现前用实际调用路径和 MySQL 故障注入确认。上述方案是实施方向，不能视为这些安全性质已被证明。
