# 小菱唯一主控与 Agent 团队架构共识

## 明确需求

小菱是 Prism 唯一对用户负责的主 Agent。管理员面和普通用户面仍是不同的授权与会话边界，不再被表现为两套主 Agent。专业内置 Agent、已发布自定义 Agent 和按任务创建的临时 Agent 都是小菱调用的子 Agent；管理端旧 `manager` 与内部 `orchestrator` 保留为兼容/基础设施实现，但从子 Agent 可见目录和可寻址目标中排除。

小菱应在简单单域任务中选用一个合适 Agent；任务确有多个独立工作或用户明确要求并行时，创建可追踪任务图。并行工作任务互不依赖，验证/汇总任务必须覆盖所有叶任务。小菱负责复核证据、冲突、失败、覆盖范围和最终陈述。

## 固定 Agent 规划

保留已有 `code_reviewer`、`security_sentinel`、`review_orchestrator`、`test_verifier`、`reporter` 等内置职责；继续沿用仅超级管理员管理面可调用的只读 `operations`。通过当前审查员账号提交以下声明式审查 Agent 更新/新建版本，管理员分离审批后才可发布：

| 编码 | 固定职责 | 与其他 Agent 的边界 |
|---|---|---|
| `auth_boundary_reviewer` v2 | 身份、角色、对象归属、账号/会话隔离、审批目标和撤权后复核 | 不承担泛化业务缺陷或全项目扫描 |
| `backend_logic_reviewer` | API 状态机、业务不变量、权限检查顺序与异常分支 | 鉴权专项问题交由鉴权 Agent 独立复核 |
| `frontend_interaction_reviewer` | Vue 状态、响应式布局、焦点/键盘、交互状态与可访问性 | 不推断后端 API 成功或权限结果 |
| `data_integrity_reviewer` | 迁移兼容、事务边界、幂等、导入导出和报告数据一致性 | 不审查未提供的数据表或运行结果 |
| `agent_orchestration_reviewer` | Agent 发现、路由、会话上下文、团队 DAG、结果归并和压缩完整性 | 不声称模型具备未开放工具或能力 |
| `reliability_reviewer` | 重试、超时、租约、失败恢复、队列和可观测状态 | 不把静态测试结果说成生产通过 |

上述为审查 Agent，能力范围限于当前输入代码与固定 Issue 输出契约，不授予服务器运维或写权限。两个旧安全试验 Agent 仅显示 50% 历史成功率且当前生产 UI 未提供失败明细；本任务不复制其未知提示词或直接覆盖其发布版本，先用安全哨兵和新建职责清晰的 Agent 承担路由，原版本保持可回滚。

## 实现方案与约束

- 复用现有 Agent Studio、审批、目录、发布快照、运行服务、Mesh 和 Agent Team API。
- 团队创建服务拒绝公开 API 的直接建队；小菱内部工具使用单独受信入口并记录审计事件。
- Agent Mesh 消息任务要求受信调用且来源绑定当前账号、surface、会话；认领时重新检查目标权限和会话有效性。
- 隐藏 Agent 需在目标校验、团队成员校验和实际运行处理器三处分别封闭，不依赖目录隐藏。
- 自定义 Agent prompt 与小菱/内置审查提示词强调逐字源码证据、精确行号、来源/推断区分；服务端验证固定 Agent 引句与当前分片、行号的对应关系，并验证临时 Agent 原文/压缩引句。证据不足时省略发现并说明未覆盖边界。
- 运行结果截断、结构无效、分片不完整、团队节点失败时不能报成功；保留可核验的部分结果和账本状态。
- 逐字引文和行号校验能拦截编造引用或错位引用，但不能证明模型对真实代码的解释正确；不得承诺“零幻觉”或摘要语义绝对完整。

## 验收标准

1. 服务端负向测试证明公开建队、普通消息任务派发、跨 surface 隐藏目标与作者自审发布均拒绝且无副作用。
2. 正向测试证明小菱的团队工具仍能创建、调度已发布/内置/临时成员并保留审计，独立叶节点并行，汇总节点覆盖叶节点。
3. 后端与前端测试/构建、静态检查、差异检查通过；新增逻辑均有回归测试。
4. 生产 Agent 草稿由审查员真实点击建立；管理员分别查看实际 prompt、职责、静态测试声明与调用成本后审批。
5. 发布后以当前账号可访问的真实项目代码调用固定 Agent，并在真实小菱对话里调度至少一支混合团队；按返回的 release/version、调用账本、团队事件和最终摘要核实。
6. 报告生产角色、入口、对象和实际结果；未进行模型调用、未发布或未验收的事项标记未测/阻断，不写成通过。
7. 所有可达审查/审计 Agent 路径均须区分累计历史和单条超长当前输入；超过 1,000,000 token 的来源应先做可追溯压缩/分片，不能静默截断。验收要记录供应商实际 token usage，并用早/中/晚、互相冲突与后续更正的挑战事实做真实模型问答；模拟压缩器仅能证明结构覆盖，不能代替模型理解验收。模型上下文的单次硬上限与服务端成本上限仍须明确暴露。
8. 平台内部总分、漏洞条目技术等级、环境综合等级、CVSS 与国内漏洞库原始等级必须分开标示。声明使用最新 CNVD/CNNVD 数据前，必须有已授权的实时数据查询/同步、精确组件版本匹配、官方编号/记录链接和更新时间；否则明确提示未核验，不能冒称权威或最新。
9. 小菱应能按任务编排 `sandbox_deployer` 与 `test_verifier` 子 Agent：在隔离环境搭建项目后，对同一项目及固定源码快照执行白盒、黑盒或组合验证；结果记录项目/修订/源码 SHA-256、实际 worker 状态和失败证据。
10. 源码修复先由只读子 Agent 给出带原文锚点的补丁建议；小菱通过现有源码编辑与点击审批门实施，重新读取修改后的源码并创建/选择新快照，再由 TestVerifier 对新快照复跑原场景并增加样本。提示词合同不能代替真实模型端到端验收。
11. 远程黑盒请求逐目标确认并绑定当前调用参数；正式渗透测试使用独立项目/目标/时间窗授权与独立审批。未经授权不发起网络探测；黑盒 smoke 不得标成渗透测试。

## 监督 Agent 与风险审批补充（风险路由已确认）

- 用户新增明确要求：增加监督子 Agent，监控小菱和旗下子 Agent 的工作；低风险与中风险自动通过，高风险需询问当前用户。
- 用户已确认风险路由原则；具体动作风险由服务端固定能力登记表确定，不由模型自行选择等级。未登记动作及监督/审计不可用均按高风险处理并停止执行，显式拒绝始终优先。
- 低风险限定为已登记只读工具；中风险限定为可逆项目元数据变更、当前项目隔离测试和沙箱生命周期操作；高风险包括外部 MCP、浏览器黑盒/外部目标、生产/破坏性/权限操作、Agent 发布、管理运维和正式渗透。
- 监督服务不授予权限。每次执行仍须通过现有用户、项目、surface、审批和授权检查；人工批准绑定当前账号、运行、工具调用、完整参数及团队计划摘要。
- 监督结论需可持久化并在运行恢复时重现；持久化失败时不得继续执行副作用。
- 代码现状：`approval`/`policy` 治理画像已存在，但不能据此宣称所有对话、工具、团队节点和结果均被监督；本轮复现了未知动作默认低风险放行和显式高风险 `allow` 规则放行两处缺口。
- Agent Team 组合测试与修订路由已存在；REST 远程测试使用一次性服务端凭证，获批团队任务仍走内部布尔授权路径。正式渗透目前由小菱主控经独立授权链执行，子 Agent 没有可验证的正式渗透启动 Handler。
- 拟定门禁：低风险只读，中的风险仅限当前项目的隔离环境/不可变副本上的可回滚修复与测试；生产写入、删除、权限变更、Agent 发布、外部目标扫描/渗透、凭据动作要求人工确认；未知分类、监督失败和策略异常 fail-closed。此具体映射以用户答复为准，尚未作为最终共识。
