# A01 上下文预算修复范围与百万 token 验收计划

日期：2026-10-04。范围为候选工作树，不是生产验收。

## 已确认缺陷与修复

原 `estimate_tokens` 将 ASCII 字符数除以 4。官方 DeepSeek-V4.1-Flash 本地 tokenizer 对数字、英文片段、代码的计数可以显著高于这一平均估算。三份合法尺寸历史分别含 1,060,022 / 1,060,022 / 1,080,022 个本地内容 token，旧预算为 265,188 / 530,333 / 405,239，均错误地判断无需压缩。它们符合聊天请求的 100 条消息、每条 100,000 字符约束。此项是本地可复现的预算逻辑缺陷，未执行外部攻击，未声称已观察到生产 400。

第一阶段改 `deepseek_responses_runtime.py`：以序列化 UTF-8 字节作保守预算；标明预算计量类型；压缩请求在发送前计入完整 JSON Schema、角色和工具字段、实际重试说明以及 1,024 的协议余量；来源分批为协议留空间。原文、事实账本、来源引文校验、缓存、更正、输出状态拒绝、输出预算和 64 次压缩调用上限保持原契约。完整后端随后发现审查补充上下文重复除以 4 的单位适配缺陷，第二阶段仅改 `review_service.py` 的配额分配；两阶段均未改生产模型设置。

UTF-8 字节上界适用于相应 byte-fallback/byte-based 内容分词条件。它不是未知 tokenizer 或供应商特殊提示编码的数学保证，不是实际 tokenizer 统计，也不是计费 usage。应用用量仍以供应商返回的 usage 为准。

两次官方 tokenizer 重计量的冻结输入与工具散列相同，结果相同。实测时 Runtime SHA 为 `725797800eb527e574f79eed2b24521665ca30d5084ff37d1c6b8ee4559e6c06`；最终 `87fec56120f24e70daffcde19926a333275270e72a87f6dea0df0cb293e526af` 只增加未知 tokenizer 限定的 docstring。已保存旧快照并对去 docstring 的整个模块 AST 做相等核对。第三次实际重计量的公开文件下载发生 TLS EOF/连接超时，未计量通过；没有关闭 TLS 校验或调用付费模型。

修复后上述三份历史预算为 1,060,751 / 2,121,331 / 1,620,954，均触发投影，原文不变，投影预算为 159,384 / 159,384 / 180,384。该独立计量工具用固定本地摘要占位，仅证明分词数量与预算规划，不能证明模型摘要语义。工具只下载固定 revision 的公开 tokenizer JSON 与固定 SHA 的官方 PyPI wheel，使用独立临时环境并删除本进程创建的目录；未下载模型权重、未使用 trust_remote_code、未改候选依赖。

## 回归与 fixture 校准

首次新增用例 8 失败、2 对照通过；结构 Schema 漏预算单例先失败。重试说明单例另通过受控重放旧 commit 的单个 `_call_compactor` 方法复现失败，明确不是自然首次运行。第一阶段新预算测试 24 项、原 Runtime 测试 59 项，共 83 项通过；23 个关联文件连续三轮均 667 项通过。父代理完整后端后来出现 9 失败/5,768 通过/5 跳过，不能将上述局部结果写为完整后端通过。第二阶段修复与夹具校准后，原失败的 3 个文件扩至 42 项通过，26 个关联文件三轮均 709 项通过（11.88/11.76/11.66 秒）。这些是本地回归，覆盖 Responses、账本、账号隔离、公开代理、聊天、临时/已发布子 Agent、圆桌、来源与用量记录，不是供应商语义、生产浏览器或性能验收。最终完整后端由父代理另跑。

### 完整套件发现的审查单位适配与追加夹具

`_prepare_bounded_single_agent_prompts` 原先将可用输入**字节**预算再除以 4。新估算器已使用序列化 UTF-8 字节，这一转换会重复缩减正常压缩空间。产品只删除该除法并更新注释，最终完整消息的 `serialized_chat_input_bytes` 容量门、完整源码/规则、来源摘要和共用 32 次调用上限不变。三个语言/转义样本×两个窗口的配额回归，受控重放可信 HEAD 的旧单函数 6 项均失败，当前均通过；该重放没有调用真实模型。

原 32,768 窗口含 125,002/132,002 字节补充来源的用例，在仅修单位后依然拒绝：固定提示与输出留存后配额不足以容纳全部逐字来源账本。这是有效拒绝，未删负例或放宽限额。保留原背景和规则，用 40,000/65,536 窗口跑正常压缩，同时增加 32,768 窗口下较短但仍超窗的背景成功对照。所有失败前主审查均未执行；正常情形逐字源码、规则、来源 SHA 和最终完整消息容量均校验。精确入参、配额和最终成本见 `审查配额与固定契约-本地实参.json`。

| 追加文件 | 容量证据与原意保留 |
| --- | --- |
| C12 | 两份 CRLF 圆桌来源完整投影需 2,213/2,204 字节预算，旧 1,800 不足，正常目标校准至 2,250；另外保留 1,800 明确拒绝与记录不变样本。英文空白引文账本需 1,811，正常目标 1,850；fake 递归时复制已核验原始引文，继续拒绝虚构引文。没有放宽产品匹配。 |
| C13 | 原 5,000 窗口连压缩模型固定协议与输出空间都不足，保留原 21 条消息在该窗口明确失败/零模型请求/完整原文前缀；正常窗口 16,000 仍用相同历史与小触发阈值，检查中段权限、更正、user/assistant 角色与每次完整 payload 预算。 |
| 审查非源码上下文 | 两条保护规则和完整来源账本成本 1,118：正常目标 1,150，原 500 保留拒绝。11 段来源截断重试正常目标由 1,500 调为 4,000，继续断言 512→1,024 和 2,048→4,096、完整 SHA 与预算，不改 32 次上限。原 ASCII 误判对照在测试内明确冻结旧 ASCII/4 公式，分别对比新字节预算与 BaseAgent 最终门。 |

追加 42 项还包括 6 项字节配额样本与“摘要过大必须被最终组装门拒绝”样本。第一次只去除除法的测试日志文件名含 green 但实际为 1 失败，已归档为 `追加-单位修复后仍32k拒绝.log`，不能计绿；一次夹具校准误命中另一测试的相同参数行，随后改回并记录 `追加-夹具校准中间失败.log`，不计通过。第一阶段的 83/667 与第二阶段的 42/709 是不同范围，不能相加当作不重叠总用例数。

`rg` 核对本项目只存在一个 `estimate_tokens` 定义；审查配额的 `/4` 是已确认的旧单位转换。其余聊天/Responses/声明式/圆桌/论坛的 `/2`、`/4`、`/8` 同时用于输入或输出分配、二次 JSON 转义余量，并有完整请求预算门，本轮没有凭这些分数推断新缺陷，也没有扩大修改。

额外检查 48 份带多位来源索引、4 种服务端角色、ASCII/换行代码/转义/NUL/中英 emoji 的封装：最大 47,991≤48,000，原文重组相同。没有在这些场景复现“固定 64 来源封装余量不够”，因此没有据此修改产品或写成漏洞。

Runtime 构造器 fallback 输出为 32,768，生产 Settings 默认输出为 65,536，两种参数各有短/长固定提示及工具 Schema 成功对照。生产 Settings 的窗口/触发/近期保留默认分别为 1,000,000 / 850,000 / 200,000；它们不证明用户自定义模型也有同样真实窗口。

## 实际压缩架构与限制

各链路复用预算/来源工具，但不是所有 AI 调用都经过同一个压缩器。

| 入口/组件 | 现有策略与安全限额 | 百万 token 验收边界 |
| --- | --- | --- |
| 小菱主 Responses Runtime | 来源分批、受保护原文、词面召回、来源引文与缓存；每运行最多 64 次压缩请求，包含重试 | 可用内存 Store 和禁止副作用的 executor 先做真实模型语义测评；真实账户、持久账本与页面需分别验。超过限额应失败而非冒充完整。 |
| 公开 Responses 兼容服务 | 独立语义投影，最多 32 次压缩请求 | 命名空间按 Bearer key，不等于 Prism 登录账号隔离。较大的百万 token 样本可能达限额，不能套用主链路结论。 |
| 旧聊天与管理员兼容链路 | 各自历史压缩和事实保护，BaseAgent 另有请求容量拒绝 | 需独立测试；不能将主 Runtime 通过写成全部聊天入口通过。 |
| 已发布审查子 Agent | 全源码分片、来源 SHA/重组，最多 128 个审查分片，委派调用最多 8 次 | 按真实授权代码文件范围测试，不把完整源码直接替成摘要并声称逐行审查。 |
| 声明式子 Agent | 只读工具结果的来源摘要，最多 32 次压缩调用 | 确认工具结果、原文锚点与权限；入口单独验。 |
| 临时子 Agent | 单次最多 5 文件、60,000 字符工作集、32 个压缩片、每片摘要≤1,200 字符 | 当前有界接口不保证任意百万 token 源码都可单轮完成；明确拒绝/建议缩小正式审查范围是独立验收项。 |
| 圆桌 | 独立讨论历史三层摘要、每位发言最多 64 个源码窗口、共享会话模型调用限额 | 主持/发言/报告都需验来源覆盖；结束后 300 秒追问与页面恢复另验，不能由本地预算样本证明。 |
| 沙箱来源/报告 | 来源最多 32 片；报告证据最多 32×24,000 字符，知识压缩每报告最多 12 次调用 | 只用无害静态源码与已有授权证据验输入投影；不增加自动进攻、利用或反击流程。 |

## 真实供应商验收步骤（尚未执行）

1. 冻结实际 release、登录账号与 surface、解析后的主/子 Agent 模型 alias、已发布版本、供应商真实窗口、输出和所有调用限额。只记录非敏感配置摘要，不导出 key、私聊或生产源码。使用当前 [DeepSeek 模型与价格文档](https://api-docs.deepseek.com/quick_start/pricing/) 核验实际 alias；自定义模型不能套用 Flash tokenizer/容量。
2. 制作公开、无害的固定语料与答案 oracle：包含普通陈述、数字、否定、先后更正、时间与文件范围，分布于早/中/晚位置。语料至少三类、每类三次独立会话。每份原文用固定 tokenizer 计量超过 1,000,000 个**不同来源材料的内容 token 总和**，保存 revision、输入 SHA、消息数/字符数和计数；不能用多次请求累计 usage 证明原始历史百万 token。另保存完整序列化历史的本地计数，说明其不是供应商专用提示模板的精确计费数。
3. 初轮用实际 Native Responses transport、内存 checkpoint、禁止所有副作用的 executor；保留全部原文及有序摘要来源 ID。每次模型尝试的 on_round 原始 usage 分别记 input/output/cached/reasoning、状态、压缩或回答用途，不记录敏感正文到公共 Git。压缩失败、截断、缺引用、缺 usage、模型或价格变化均停止该样本，不填补虚构成功。
4. 预先设置本次样本和整批的费用/调用停止线。`guard_automatic_model_call` 明确只覆盖无人值守任务，交互调用不使用它，不能据此宣称本次付费压力验收已有硬费用门。费用按最新单价和实际 usage 计算，缓存与未缓存输入分开，reasoning 属于输出，失败尝试也计账；不能用应用保守预算代替账单。
5. 每次请求单独核查投影预算+指令+工具 Schema+协议余量+输出≤该模型窗口，保留被拒样本和拒绝前没有回答调用的证据。主链路 64 次及各子链路独立上限必须保留；有界未完成不能标为完整。
6. 对 oracle 的召回、更正覆盖、数值和否定逐项评分：询问中间不显眼事实与最新更正，不只问末尾事实；保留模型原答、原文位置与错误分类。来源 ID 与逐字引文仅证明片段存在，不能证明模型理解全部含义，任何固定通过率不能推导“永不幻觉/语义无损”。
7. 再在隔离、可恢复的数据库测试真实 Store：账本各行 checksum、来源顺序、旧消息前缀 SHA、账号/surface/session 拒绝、刷新恢复和发布版本绑定。原文账本与给模型的压缩投影分别核对，不覆盖旧原文；失败也保留原始材料。生产浏览器三角色与手机验收由父代理另列真实点击记录。
8. 对上表每一业务入口分别跑正常、超限拒绝、输出 length 重试、缓存复用、最新更正和权限撤回。永久/临时团队按实际授权项目来源运行，禁止将临时 5 文件/32 片限制绕成不受控工作集；审查结论仍要求原文证据与人工确认边界。

原生 Responses 的 stateless/上下文管理边界及 usage 字段以 [DeepSeek 官方 Responses 文档](https://api-docs.deepseek.com/guides/responses_api/) 为准。平台需自己持有历史和构造投影，不能依赖供应商 `previous_response_id` 自动完成压缩。

当前明确待办：真实供应商 oracle 的完整语义测评、实际每入口模型配置快照、交互付费测试硬停止线与持久可复跑真实模型验收入口；本轮新增工具只有本地 tokenizer/规划计量，不是付费验收 runner。历史报告中的“百万级估算 token”不能补齐这些待办。
