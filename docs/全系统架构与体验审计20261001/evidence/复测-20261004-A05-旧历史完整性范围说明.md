# 旧历史完整性补充闭环

## 实际发现与修改

候选工作树中的旧检查点首次转为会话账本时，`DatabaseCheckpointStore._merge_legacy_transcripts` 原先跳过非对象检查点、缺少 transcript 的检查点，并过滤 transcript 内非对象项。历史 API 的 `_stored_run_transcript` 与下一次聊天的 `_server_history_transcript` 也可能把损坏原文省略后继续返回。`load/claim` 的内嵌 transcript 仅检查列表类型，仍可直接装载损坏项。这是本地合成损坏数据可复现的恢复完整性缺陷，未证明生产存在损坏历史或外部利用。

本次只修改这四个直接相关函数：

- 旧合并拒绝非对象检查点、缺历史、非列表历史和非对象消息。合法 `_transcript_ref` 通过既有账本校验路径恢复，合法空游标也兼容；内嵌历史和非空引用并存时拒绝冲突。
- `_checkpoint_from_payload` 增加列表内逐项 Mapping 校验，使直接恢复旧运行的 `load/claim` 与入账采用同一要求，不收紧其它 metadata 契约。
- 历史 API 只提取 transcript/引用字段并复用存储验证器，不通过过滤删除原文；下一次聊天的旧运行合并复用同一个合并函数。存储错误转为现有 HTTP 409、业务码 40931；已经开始的 SSE 以现有 error/response.failed 事件呈现。
- 不改写或删除旧 checkpoint JSON，不重新解释用户/工具内容，不增加模型请求，也没有生产写入。

其它同链过滤点经过只读核对：新建/延展运行的源列表过滤之后有账本游标与原消息数量校验，损坏输入不能按删项后的数量提交；面向 UI 的工具/角色筛选是可见消息投影，不等于删改持久化原文。本次没有修改这些分支。

## 先红后绿与扩大样本

首轮新测试因合成会话漏填必填 `last_seen_at` 产生 fixture 错误，单独保留日志，不能计作产品缺陷。纠正 fixture 后、修改产品代码前，41 样本为 **32 failed / 9 passed**，失败包括损坏形状被静默接收，以及合法空/非空引用被旧合并拒绝。产品修改后相同 41 样本全部通过。

随后增加 8 样本，最终 **49 passed**：合法空账本引用首次追加；游标跨账号及跨 user/admin 入口拒绝；前一旧运行合法而后一损坏时不部分入账；空字符串及两类 JSON 语法损坏；工具调用/结果、附加证据字段及图片资产引用保持原样。原有正常/空历史对照同时验证原 JSON 未改、消息次序正确、消息无重复及另一账号历史为空。损坏输入的 `create` 和失败 `claim` 不提交新运行、账本或版本变更。

实际路由函数 `get_agent_response_session_messages`、下一次聊天真实 SSE 处理函数，以及数据库存储方法在隔离 SQLite 中运行。SSE 的模型启动使用本地拒绝桩；损坏历史在启动桩之前失败，没有外部模型调用。这不是生产 HTTP、真实浏览器或供应商模型验收。

13 个目标文件整合首次为 **470 passed**；增加 8 样本后重跑为 **478 passed**，覆盖旧历史完整性、事实召回、压缩、Responses 运行/审批/API、团队服务/调度、发布依赖绑定及 AI 用量归属。只有既有 passlib/crypt 弃用警告。目标 Ruff 和 `git diff --check` 通过。
