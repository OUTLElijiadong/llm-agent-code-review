# 沙箱精确 HTTP 白名单需求共识

## 明确需求

为本地代码沙箱黑盒测试增加可强制执行的精确 HTTP 请求白名单。受限模式只访问容器内应用的 loopback 服务，允许 GET 方法、精确路径和精确查询参数；至少 1 项、最多 20 项，`GET /` 可选。就绪检查只建立 TCP 连接，不产生隐藏 HTTP 请求。可选预期状态码用于精确断言。该模式跳过所有 AI 生成且会在容器内执行的补丁、PoC、测试脚本和语法修复。组合测试运行项目测试脚本，不开放白名单模式。

生产验收发现根路径并非所有应用的有效入口；白名单摘要在包含无查询 `GET /` 时继续以它为主，否则指向第一条实际请求。该修订不改变每条白名单必须逐项成功的判定。

## 技术约束

- 后端 schema 与 service 校验、Worker 协议校验、可信 shell runner 执行三层闭环。
- Runner 修改需同步 `docker-compose.build.yml` 中五种运行时镜像的固定 SHA-256。
- 远程 HTTP(S) 黑盒保持现有逐目标授权；其请求不使用本地白名单。
- 响应正文不得进入日志、回执或报告；只保留有限响应字节计数。查询参数只接受未编码 ASCII 安全字符；日志被截断时回执不可信，必须失败关闭。
- 报告如实标注未配置断言及未运行 AI 动态用例，不把 HTTP 可达性等同于安全验证完成。

## 验收

- 针对非法输入、协议篡改、runner 越权路径、注入脚本跳过、回执不一致、报告证据和前端表单分别测试；根路径可选修订需在生产部署后通过真实产品链路验收。
- 遵循用户要求，不在本机执行功能测试；可在本机执行不运行产品逻辑的语法、类型和格式静态检查，功能验证使用正式网站。
- 4.1.11 原始实现此前已部署，并按用户一次性授权运行过指定靶场，结果失败。当前根路径可选修订尚未发布；本次发布必须走精确 SHA、备份/恢复验证、镜像构建及生产健康/业务冒烟门禁，不把 4.1.11 的历史运行当作修订版验收。

## 实施方案

后端规范化白名单并持久化；Worker 再次独立验证并将规范请求计划编码给固定 runner；runner 在目标代码启动前以权限为 0600 的临时文件接管计划、exec 替换进程并清除编码环境变量，再只启动应用、以 TCP 连接检查就绪，按计划发出 GET 并生成结构化回执。后端将持久化计划与 runner 回执精确比对后写入结果及报告。前端仅为本地黑盒模式提供条目编辑器和证据展示。
