# 对齐：部署诊断与历史终态兼容

## 原始需求

“帮我部署，你看看什么原因。”结合当前 Prism 黑白盒验收，先核对生产部署状态和阻断原因；如确认历史任务仍存在模式文案矛盾，则在不改写审计历史的前提下修复展示并完成发布验收。

## 项目与当前基线

- 生产 `/healthz`、`/readyz` 返回 v4.0.85，release 为 `727d636c22e5ff7e8d7fe887f934867ce591e1f3`。
- 当前主工作区分支为 v4.0.2，且 `backend/`、`frontend/` 有未提交变更；`deploy.sh` 明确拒绝脏构建上下文。
- 已有干净 v4.0.85 发布工作树可用于基于生产源码修复。
- 生产旧沙箱任务时间线出现“白盒测试失败”，但任务模式为黑盒。新 Worker 已按模式写入终态文案；旧数据库事件由 API 原样序列化、前端原样展示。

## 范围与边界

- 核验生产版本、健康、候选 SHA、发布流水线与部署门禁，定位本次发布的真实阻断点。
- 仅修正黑盒/组合模式下精确匹配的旧白盒终态事件文案；不改写数据库事件、报告、审计记录或执行结果。
- 用回归测试证明历史终态映射、白盒原样保留、非终态与非精确文案不被改写。
- 发布必须来自干净、已通过精确 SHA CI 的提交，并按正式脚本完成备份、迁移、运行 SHA、HTTPS 和前端资源核验。

## 未确定事项

- 发布脚本是否可从配置的生产 SSH 身份访问服务器，以实际只读探测和发布回执为准。
- 历史事件的完整文案集合尚未确认；只兼容可由已提交旧 Worker 源码或生产证据精确证明的字符串。
