# 02 · 需求规格说明书(SRS)

> 本文从用户视角描述系统应具备的功能与质量属性,作为后续设计、开发、测试的依据。每条需求带唯一编号,便于追溯。

## 1. 用户角色与权限

| 角色 | 编号 | 权限说明 |
| --- | --- | --- |
| 管理员 admin | R-ADMIN | 管理所有用户、项目;查看全平台数据统计;管理审查规则 |
| 普通用户 user | R-USER | 管理自己的项目、代码、版本、审查任务、报告 |
| 审查员 reviewer | R-REVIEWER | 只读自己被授权项目;可标记问题状态;不能改代码 |

> 一期仅实现 admin / user 两种角色;reviewer 在权限模型中预留,UI 不暴露。

### 1.1 权限矩阵

| 资源 / 动作 | admin | user(本人) | user(他人) | reviewer |
| --- | :---: | :---: | :---: | :---: |
| 用户管理 | RW | R(自己) | × | × |
| 项目 CRUD | RW | RW | × | R(授权) |

| 启动审查 | RW | RW | × | × |
| 查看问题 / 报告 | R | RW | × | RW(状态) |

| 仪表盘(个人) | × | R | × | R |

## 2. 功能性需求(Functional Requirements)

### FR-01 用户登录注册模块

| 编号 | 名称 | 描述 | 优先级 |
| --- | --- | --- | --- |
| FR-01-01 | 用户注册 | 用户名(3-50 字符,唯一)+ 密码(6-32 字符)+ 邮箱(选填,格式校验)注册;密码 bcrypt 加密入库 | P0 |
| FR-01-02 | 用户登录 | 用户名 + 密码登录,成功返回 JWT(access_token,有效期 7 天) | P0 |
| FR-01-03 | 退出登录 | 前端清除 token,跳登录页;后端无状态 | P0 |
| FR-01-04 | 修改密码 | 登录后修改密码,需输入旧密码校验 | P1 |
| FR-01-05 | 获取当前用户信息 | 前端首次进入获取用户基本信息和角色 | P0 |
| FR-01-06 | 管理员重置密码 | 管理员可强制重置任意用户密码,默认密码 `123456` | P1 |
| FR-01-07 | 管理员禁用/启用账号 | `status=0` 禁用,登录被拒;`status=1` 启用 | P2 |

**异常处理**

- 用户名重复:返回 409,提示"用户名已存在"
- 用户名/密码错误:返回 401,统一提示"用户名或密码错误"(不暴露具体哪个错)

- token 过期:返回 401,前端跳登录页

## 3. 非功能性需求(Non-Functional Requirements)

### NFR-01 性能

- **N-01-01**:单文件审查端到端耗时 ≤ 30 秒(95 分位),含网络与解析。
- **N-01-02**:列表页接口响应 ≤ 500ms(本地环境),数据量 1000 条以内。
- **N-01-03**:仪表盘首屏加载 ≤ 2 秒。

### NFR-02 安全

- **N-02-01**:密码 bcrypt 加密,salt 自动生成,cost=12。
- **N-02-02**:JWT 使用 HS256,密钥从环境变量读取,长度 ≥ 32 字节。
- **N-02-03**:所有 API(除登录/注册)需 Bearer Token 鉴权。
- **N-02-04**:用户只能访问自己的资源,服务层强制 `user_id` 过滤;管理员可越权。
- **N-02-05**:文件上传白名单扩展名,黑名单 `.exe/.dll/.so/.bin` 等。
- **N-02-06**:SQL 全部走 ORM 参数化,禁止字符串拼接。
- **N-02-07**:DeepSeek API Key 仅存后端环境变量,前端无感知。
- **N-02-08**:开启 CORS 白名单,生产环境只允许指定域名。

### NFR-03 可用性

- **N-03-01**:DeepSeek 调用失败重试 2 次,失败后单文件标记失败,任务继续。
- **N-03-02**:前端关键操作(删除、回滚)二次确认。
- **N-03-03**:长操作(审查)显示 Loading;进度轮询和中途取消为后续预留能力。

### NFR-04 兼容性

- 浏览器:Chrome 120+ / Edge 120+ / Safari 16+
- 分辨率:≥ 1280×800
- 后端:Python 3.9+
- 数据库:MySQL 8.0+

### NFR-05 可维护性

- **N-05-01**:后端代码分四层(api/services/models/schemas),每层职责单一。
- **N-05-02**:函数 ≤ 50 行,文件 ≤ 400 行(指导值)。
- **N-05-03**:日志使用 `loguru`,关键流程 INFO,异常 ERROR + traceback。
- **N-05-04**:配置全部走环境变量,通过 `pydantic-settings` 管理。

### NFR-06 可观测性

- 后端日志按天滚动,保留 30 天。
- `ai_call_log` 表记录每次大模型调用,可在管理员页查看。

## 4. 用例(Use Case)

### UC-01 注册并登录

```
主成功场景:
  1. 访客打开 /register
  2. 输入用户名、密码、邮箱
  3. 系统校验唯一性
  4. 系统 bcrypt 加密密码并入库
  5. 跳转登录页
  6. 输入用户名、密码
  7. 系统校验,返回 access_token
  8. 前端保存 token 跳首页

扩展:
  3a. 用户名重复 → 提示并停留
  7a. 密码错误 → 提示"用户名或密码错误"
```

### UC-02 上传代码并发起审查

```
前置条件: 已登录,已创建项目

主成功场景:
  1. 进入项目详情页
  2. 点击"上传代码文件"
  3. 选择本地文件(< 20MB)
  4. 系统识别语言,展示预览
  5. 用户确认,保存
  6. 文件入库,version_no=1,生成版本记录
  7. 用户勾选文件,点击"开始审查"
  8. 系统创建 review_task,状态 pending
  9. 后端循环:取代码 → 调 DeepSeek → 解析 → 入库
  10. 任务完成,状态 success,前端跳转审查详情页
  11. 前端展示问题列表 + 报告入口

扩展:
  3a. 文件 > 20MB → 拒绝,提示
  9a. DeepSeek 失败 → 重试 2 次仍失败 → 单文件标记失败,任务继续
  9b. 返回非 JSON → 二次清洗 → 仍失败标记该文件失败
```

### UC-03 查看问题并标记修复

```
前置条件: 审查任务已完成

主成功场景:
  1. 用户在审查详情页查看问题表格
  2. 点击某条问题打开抽屉
  3. 查看描述、建议、修复代码
  4. 复制修复代码到代码编辑器
  5. 修改并保存代码(生成新版本)
  6. 回到问题列表,标记该问题为"已修复"
  7. 系统更新 review_issue.status,刷新统计
```

### UC-04 生成并导出报告

```
前置条件: 审查任务已完成

主成功场景:
  1. 用户在审查详情页点击"查看报告"
  2. 前端跳转报告页,展示 HTML 报告
  3. 用户点击"导出 Word"
  4. 后端用 python-docx 渲染,流式返回 .docx
  5. 浏览器下载文件
```

## 5. 数据流(高层)

```
[用户浏览器]
   │ ① 登录,拿到 JWT
   ▼
[Vue3 前端 SPA]
   │ ② 创建项目 / 上传代码(REST)
   ▼
[FastAPI 后端]
   │ ③ 持久化
   ▼
[MySQL]
   ▲
   │ ⑤ 写入问题与报告
[Review Service] ◄── ④ 调用 ──┐
                              ▼
                       [DeepSeek API]
```

详细时序见 [03-系统设计文档](./03-系统设计文档.md) 第 4 章。
