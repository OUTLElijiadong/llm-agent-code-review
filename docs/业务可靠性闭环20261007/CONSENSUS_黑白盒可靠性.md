# 黑白盒业务可靠性共识

1. Worker 严格字段白名单保持不变；Backend 只投影已允许的 wire 字段，来源版本和修复轮次留在后端审计账本。
2. 沙箱测试只有在 Worker 终态成功、目标状态 succeeded、exit code 为整数 0，且黑盒/动态测试需要的子步骤回执齐全时才可通过。未知字段、缺失或重复回执、无效状态、失败阶段均不可汇总为通过。
3. 黑盒路由只有 2xx 能证明该次固定路由检查通过。3xx 只证明返回重定向；401/403 只证明遇到认证边界，均显示部分/未完成；404、5xx 和动态断言失败显示失败。回环根路径 `/` 是合法路由。
4. 白盒确定性静态检查可单独形成已完成范围；AI 动态生成失败或未执行必须披露为部分覆盖，不伪装为 AI 测试通过。未生成/未执行的动态断言字段为 null，只有真实执行并通过才为 true，且必须有唯一、可信的执行回执。
5. Python 黑盒/白盒 AI 用例的导入和模块属性引用必须与对应源码模块的真实顶层导出对应；不能用另一文件里的同名符号证明当前模块存在该 API。没有明确路由、参数、数据库或身份依据时不能虚构业务探测。
6. 动态端口仅接受实际运行环境的 `PRISM_PREVIEW_PORT` 来源；固定端口、非回环地址，以及改写 `os.environ`/`os.getenv` 后的伪动态来源必须在执行前拒绝，包括环境项删除、`operator` 别名及 `methodcaller` 间接调用。
7. 压缩保留来源 ID、顺序、哈希、可核引文与受保护事实；调用、时间或预算不足时明确失败。有限重试不得重复相同无效请求，也不得静默丢弃尾部。
8. 模型截断、调用失败、超时、输入预算、结构/schema、grounding 拒绝和执行契约拒绝分别报告；重试耗尽后允许确定性回退，但用户可见结果需同时写清动态测试未运行。仅路由探活回执使用 `route_smoke`；只有动态断言实际执行才使用 `route_and_agent_assertions`。
9. UI 区分完整通过、部分未完成、结果未知和确定失败；权限不足时隐藏 coverage 细节。
10. 生产验证按白盒后黑盒串行执行；每项核对原始任务事件、Worker 回执、代码来源、制品、终态和资源清理。旧失败记录留档。
11. Node 新生成 harness 固定 `.mjs`/ESM，不依赖项目包的 `type`；runner 实际发现并执行 `blackbox.mjs`，同时保持历史 CommonJS `.js` 白盒兼容。
12. Java AI 测试编译与运行时 classpath 都必须包含可用项目类输出；依赖不在离线缓存时明确失败/未完成，不以生成测试自身可编译取代项目行为覆盖。
13. 普通白盒与黑盒应用启动都必须先尝试准备隔离缓存中的依赖；依赖准备状态及应用/测试执行结果要分辨，禁止以跳过依赖或空测报告业务通过。
14. 大源码压缩在截断或来源引文连续校验失败后可确定性无损拆分重试，但不可绕过哈希、来源覆盖、逐字引文和预算门禁。

## 明确未作出的保证

当前只有 Python 有源码级模块导出 grounding；Node `.mjs`、Java classpath 修复及各语言 Runner 行为测试并未补齐 Node/PHP/Go/Java 的等价源码语义 grounding。此轮百万级输入由模拟模型验证压缩分片、完整性和锚点保留；不证明真实供应商能接收或理解超过 1,000,000 个真实 token。实际 Worker、PHP/JDK 环境、三方依赖缓存和生产供应商语义验收仍需独立证据。通过当前发布门禁不等于任意真实项目和依赖环境都绝不失败。
