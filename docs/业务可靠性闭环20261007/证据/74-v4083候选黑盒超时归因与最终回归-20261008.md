# v4.0.83 候选：黑盒超时归因与最终回归（2026-10-08）

## 故障原因与证据边界

- 生产历史任务 `sbx_3b317e05c0fa45128c20e31d` 运行约 120 秒后以 `exit_code=124` 结束，`timed_out=true`、`oom_killed=false`。旧 Python profile 的 `test_timeout_seconds=120` 与执行器到期后强制终止的路径确认了该终态直接原因：profile 硬超时。
- 该任务使用的唯一项目只有 `review_sample.py`，没有可运行 Web 入口。`/health`、`/healthz`、`/api/health`、`/api/healthz`、`/api`、`/openapi.json`、`/docs`、`/login` 返回 404；根路径 200 仅是进程就绪，不是业务路由通过。因此历史路由失败符合该样本，并非生产站点 Web 路由故障证据。
- 日志在启动约 5 秒时已记录路由失败，之后容器仍运行至 profile 时限。原始日志没有结束前阶段尾迹、进程树或停止信号证据，故无法从历史记录确定延迟具体发生在 Agent 黑盒断言、应用清理或其他阶段；本报告不把候选中的推测写成已证实的历史根因。
- 独立复核在候选中发现并实弹复现文本扫描的另一个缺陷：源码仅含 `ROUTE_DOC = "route('/healthz')"`，没有注册路由，通配 WSGI 应用却对所有路径回 200，候选旧扫描器仍错误给出 `route_smoke passed`。先复现后改为词法扫描，并新增普通字符串、Python 多行字符串负例及对应嵌入 runner 测试；真实 Node `req.url === '/healthz'` 正例验证严格相等路径仍可发现。

## 候选修复

- runner 总预算提前于执行器 profile 截止，并保留回执写入窗口；所有耗时子进程经 GNU `timeout` 限制，动态 Agent 单文件编译/运行、依赖准备、PoC、应用就绪、路由探测都有界限。
- 应用启动失败、就绪超时、断言超时和总预算耗尽产生不同结构化回执；状态解析器按 fail-closed 规则校验。
- Runner 捕获 SIGINT/SIGTERM 并回收被测应用及子进程；修正非交互 shell 忽略 SIGINT 时的监督器转发问题。
- 部署 Worker executor 将 profile 的启动时限注入 runner；五种语言镜像确保 `/bin/bash` 与 GNU `timeout` 可用。
- 路由扫描忽略注释、普通字符串及多行字符串，只从代码 token 中识别已支持的路由调用或路径比较；该启发式不等同完整语言 AST/框架语义证明，真实业务审查仍须由动态断言和实际样本补足。
