## 异常对应的源码核验

生产 `sandbox.log` 记录了 `'Name' object has no attribute 'func'`。对生产基线 v4.0.78（commit `957a6588fc59b924ed1ebae81446a361b37c28bf`）源码核验发现一条结构吻合的崩溃路径：旧分支先确认外层 `node.func` 是 `ast.Call`，随后调用 `call_name(node.func.func)`；当表达式为 `methodcaller('__setitem__', ...)(os.environ)` 时，内层 `node.func.func` 是 `ast.Name`，而 `call_name` 直接读取传入对象的 `.func`，会产生同样的 AttributeError。最小复现确认这段 AST/访问契约产生精确错误文本。

候选改为将 `node.func` 交给 `methodcaller_mutator_spec(ast.AST)`，在分派中显式区分 `ast.Name` 与 `ast.Call`；相同模式也包含在 `test_nested_call_ast_contract_does_not_crash_and_keeps_environment_guard` 的参数化样例中（`nested-name-mutator`）。因此源码级证据强烈支持候选修复了这一已识别的崩溃路径。但生产生成用例原文及完整模型栈追踪不可得，不能证明生产那次异常必由该表达式触发，也不能把它与 Worker 未检测到支持入口后的启动失败合并为一个根因。

## 结论边界

- 候选静态检查器在这三轮固定测试样本中没有崩溃，相关端口约束回归稳定。
- 生产 `sandbox.log` 记录 Worker 未检测到支持的 Python 部署入口并报告应用启动失败；`'Name' object has no attribute 'func'` 出现在动态用例生成步骤。基线源码存在可产生相同异常的 AST 路径，候选及其回归测试覆盖了该路径；但由于未取得生产生成用例原文和完整模型栈追踪，不能证明这就是生产那次异常的确切触发点，更不能证明它导致了 Worker 的入口检测结果或启动失败。
- 发布后仍需在普通 Safari 对安全的可运行样本执行白盒/黑盒正例与无入口负例，核验原始事件、任务结果和资源回收；关键场景各重复三轮。
