# v4.0.82 生产部署、Worker 补齐与故障原因（2026-10-08）

## 已确认的原因与证据边界

- 生产黑盒失败任务 `sbx_3b317e05c0fa45128c20e31d` 使用的唯一可选项目 `V4验收样本20260920` 只有 `review_sample.py`，没有可运行 Web 入口和业务路由。`/health`、`/healthz`、`/api/health`、`/api/healthz`、`/api`、`/openapi.json`、`/docs`、`/login` 均返回 404；根路径 `/` 的 200 只能作为进程就绪信号，不能证明业务路由通过。因此这次黑盒路由失败符合该样本的事实，不足以证明 Prism 生产业务路由故障。
- Agent 子用例输出 `blackbox probe ok: status=200`，但报告没有保存脚本、目标 URL 和端口，不能作为独立 HTTP 成功证据。聚合任务仍正确失败。
- 同一任务约 120 秒后以 `exit_code=124` 结束，`timed_out=true`、`oom_killed=false`。生产旧 Python profile 明确配置 `test_timeout_seconds=120`；执行器在该预算内 `docker wait` 超时后会发送 KILL 并写入退出码 124。因此已能确认这次 124 是触发固定 120 秒预算，不是 OOM。日志约在启动 5 秒后已记下黑盒路由失败，容器随后仍运行到预算耗尽；现有记录没有进程树、停止信号之前的阶段状态或完整收尾证据，故“失败后为什么 runner 未及时退出”的根因仍未确定。v4.0.82 没有修改超时或回收逻辑。
- 发布前独立检查发现主站与独立 systemd Sandbox Worker 漂移：主站 v4.0.81，Worker 执行器与五个 runner 镜像仍为 v4.0.78，profile 也指向旧镜像。主站发布流程没有自动更新独立 Worker；必须另行运行 `deploy/sandbox/install.sh`。这属于实际部署遗漏，不是黑盒业务代码故障。
- Java runner 镜像初次构建在生产主机下载锁定的 JADX 官方 release 时出现 `curl (56) ... unexpected eof`；生产主机重试又遇连接超时。本机下载官方 `jadx-1.5.6.zip` 后以锁定 SHA-256 校验通过，再传入主机复验同一哈希，并在临时构建上下文中再次校验后构建。没有放宽摘要门禁，也没有改用未校验制品。
