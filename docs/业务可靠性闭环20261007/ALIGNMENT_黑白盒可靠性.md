# 黑白盒业务可靠性对齐

## 原始需求
确保正常业务可以落实，补齐正常、边界和异常测试；重点解决黑盒、白盒真实任务反复失败，先复现、再修复、按原场景复测并增加样本。测试须区分候选、生产、模拟和真实执行证据，不能将未测风险写成已发现漏洞，也不能将局部通过写成全量通过。

## 已核实基线
- 本轮发布前生产为 v4.0.78，release SHA 957a6588fc59b924ed1ebae81446a361b37c28bf；候选 v4.0.79 从生产精确提交的相同 Git tree 构建。
- 生产历史失败任务保留，包含白盒源码上下文拒绝和黑盒动态断言回执矛盾；未改写旧任务。
- 定位到多文件源码 JSON 转义导致引文无法精确核验、递归拆分重复携带完整文件元数据、AST 深层调用类型不一致，以及 methodcaller 赋值别名间接改写预览端口来源等故障。
- 生产已有函数级样本没有可运行服务入口，只能验黑盒启动失败诊断，不能作为成功黑盒样本。

## 本轮范围
修复源码 grounding、递归模型输入和 Python AST 动态端口别名检查；执行修复前红测、修复后同场景与新增变体；运行后端/前端完整回归、发布门禁、隔离 Redis；发布后以普通 Safari 实测白盒、黑盒负例和 loopback runnable service 正例，并核验任务及资源清理。

## 边界
候选自动化、生产 Worker、供应商模型分别留证。Node/PHP/Go/Java 尚无与 Python 等价的语义源码 grounding；模拟压缩不证明真实供应商端到端理解超过 100 万 token。目标是针对已复现故障修复并防止假通过，不承诺任意项目、模型、依赖或网络条件下零失败。
