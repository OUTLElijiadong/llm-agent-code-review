# 独立临时团队安全审查

日期：2026-09-20。基线功能提交为 `e153e938cee413298220a1aa30f838aac36cd015`，文档提交为 `42d9ddd`。本审查只读取代码、在内存 SQLite 复现和新增独立测试，未连接生产数据库、未部署、未运行真实模型或读取凭据。

## 结论与最小方案

现有团队已具备成员快照、依赖图、并行队列、独占租约、失败恢复、汇总及账户归因，可直接承载临时成员。当前只能引用 `agent:<code>` 或已发布 `custom:<code>`，不能生成新临时职责；整个代码树未找到名为 `generate_agent_template` 的实现或注册。不能把临时成员实例与动态生成 Agent 职责混为一谈。

用户最新确认的生命周期是：仅当前账号、当前任务可用；任务结束保留审计记录，不加入永久 Agent 库。最小实现应将经过严格校验的临时职责定义保存在既有 `AgentTeamMember` 快照中，复用调度与审计，避免调用 `agent_studio_service.create_agent`。后者会创建永久 `CustomAgent` 与 `CustomAgentVersion` 草稿，并进入测试、发布审批流程，语义不符。

临时定义可包含展示名、审查专长、任务指令、基础执行能力地址、固定字段校验和；外部不能选择 owner、team、原始工具权限、数据库连接或宿主路径。对临时成员的有效能力取“基础执行能力 ∩ 当前账号权限 ∩ 当前任务资源范围”。基础地址解析必须先于操作规范化、权限验证、资源验证和运行时路由，防止用临时别名绕过原检查。

`BaseAgent` 已支持单次 `system_prompt` 参数，`ReviewAgentProfile` 是不可变职责画像，适合复用。不可修改注册全局 Agent 的提示词或权限。`DeclarativeReviewAgentFactory._compile_skill_version` 中 `agent_delegate` 当前主要把目标职责编入提示文本，不代表真实并行执行；真实团队调度必须使用既有 team dispatcher。

## 已准确复现的问题

### 问题一：管理员可越过新约定的账号私有团队边界

严重性：高。管理员可以通过普通聊天团队接口读取其他账户的目标、成员、任务指令、事件与消息；如果临时职责保存于成员快照，内容也会被一并披露。

基线位置：`backend/app/services/agent_team_service.py:1025` 的 `_team_or_raise` 对管理员不加 `user_id` 条件；`:1345` 的 `list_teams` 在管理员未传 `session_id` 时同样不加该条件。`backend/app/api/v1/agent_teams.py` 的列表、详情、事件和消息接口使用这些公共服务，仅要求 `agent:chat`。这不是未授权普通用户读取全站的漏洞，而是旧管理员例外与本次明确“每个账号聊天严格隔离”合同冲突，必须修正。

复现：真实 ORM 管理员 803 读取所有者 801 的合成团队，列表返回该团队，详情、事件、消息均未拒绝；普通用户 802 对照测试正常拒绝。4 个预期拒绝的安全断言失败，1 个普通用户对照通过。

建议：所有聊天团队读写路径严格限定 `AgentTeam.user_id == current_user.id`，包含详情、增量事件、消息分页、取消、重试及归档。若业务仍需管理审计，应在另一个显式、最小化的管理审计合同中处理，不能复用私人聊天内容接口的管理员绕过。

### 问题二：安全扫描权限可被团队消息路径绕过

严重性：高。仅有 `agent:chat` 的账号可以经团队消息进入受 `security:scan` 保护的扫描实现，临时能力别名若直接继承该处理器会继承同一缺口。

基线位置：`backend/app/services/agent_mesh_dispatcher.py:777` 直接调用 `orch.security_sentinel.scan_file/scan_task/scan_project`，跳过 `backend/app/agents/orchestrator.py:524`、`:534`、`:544` 的 `audit_security_for_*` 功能权限检查。`backend/app/services/agent_team_service.py:540` 创建时检查项目可见性，但未检查安全扫描功能权限。

复现：真实 RBAC 账号 801 只有 `agent:chat`、明确没有 `security:scan`。三个主小菱审计方法均正确拒绝，扫描叶方法调用次数为 0；相同账号进入 mesh 后，三个扫描叶方法分别被调用。另一个测试证明该账号能为自己的项目成功创建安全扫描团队。3 个执行拒绝断言与 1 个创建拒绝断言失败。

为避免对外调用，只将扫描叶方法替换成记录调用的测试替身；账号、权限表、权限判断、Orchestrator 和 mesh 路由保持真实实现。该证据证明功能授权旁路，不声称读取了他人项目或运行了真实模型。

建议：创建时和执行时都校验当前账号权限，运行时复用现有 `audit_security_for_*` 包装器。不能仅在前端隐藏工具，不能仅信任已冻结的创建时权限。其余基础执行能力也应统一对应现有权限契约，尤其文件、报告、审查结果、仪表盘查询与受治理动作。

## 临时执行必须保持的边界

- 临时地址不注册全局目录，不加入永久资产表，不接受普通跨会话 `send_message` 直接调用。
- 仅服务端确认的当前账号、团队、任务、成员和有效租约组合能够解析临时定义；结束、取消、过期后只读保留审计快照，不能在另一团队复用该地址。
- 每次执行重新核对账号状态、功能权限、项目可见性、基础 Agent 是否停用。临时提示文本不能解除任何检查。
- 保留现有任务图、并发上限、重试与截止时间；最终汇总要披露动态成员的实际执行、失败与覆盖，不能只新建名字就称已执行。
- 模型输出的图标或展示内容不得成为可执行 HTML、脚本或任意外链；优先映射到已有图标枚举。具体可爱风格由前端代理处理。
