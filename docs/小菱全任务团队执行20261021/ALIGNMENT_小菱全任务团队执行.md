# 小菱全任务团队执行对齐

## 原始需求

小菱只负责规划、组队、派发、跟踪、核验和汇总；所有请求包括普通问答都由 Agent 团队成员执行。若没有适配成员或执行合同，必须明确阻塞，不得由小菱直接代做；可由小菱创建当前任务专属临时成员组队。常用临时成员可由小菱按实际使用表现判断是否保留。实施前先核实当前版本完整部署到生产，并复现历史问题，再继续修改。

- 修改工作基于该 SHA 的独立干净 worktree；主工作区有大量其他未提交改动，不得直接部署。

## 范围

1. 生产 4.1.15 发布完整性与历史行为复现；2. 全任务强制团队派发与失败关闭；3. 团队计划、成员、真实派发内容和执行状态的前端可见性；4. 临时成员的任务隔离与可审计保留判断；5. 与既有评分、圆桌停止/恢复、报告权限验收的交叉检查。

不把本次部署扩大为主机任意 root 运维；不删除历史业务记录；不直接修改 GitHub；生产部署前保留可恢复回滚版本并检查迁移兼容性。

## 已确定的实现约束

- 对普通文字问答使用受限通用 worker；读取页面数据必须匹配固定页面能力与当前账号权限；领域任务优先使用专用 Agent。
- 临时 Agent 只能在当前团队中执行其明确的无工具/已注册能力合同，不能自行获得网络、命令、数据库或写入权限。
- 所有业务完成声明必须绑定真实团队、成员结果、必要核验与服务端终态；运行中只能报告已派发/进行中，失败、取消或无合同必须如实阻塞。
- 运行时服务端拒绝小菱主会话直接调用业务工具；提示词仅作补充，不能充当唯一控制。
- 团队跟踪卡展示服务端保存的目标、成员与派发 instructions；恢复历史会话时不得伪造新团队或隐藏失败节点。

## 待验证事项

- 候选发布后的发布树/当前与上一版本账本/运行镜像 digest/Alembic current 与 head 是否一致。
- 浏览器目标账号中，评分、报告可见性、圆桌强停与断线恢复的实际生产行为。
- 现有临时 Agent 是否有安全的“常用保留”治理流程；若无，先生成可审计保留建议，不绕过发布/审批流程。
