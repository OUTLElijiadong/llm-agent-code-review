## 5. 如何判定"这条失败是不是安全中心引入的"

```bash
cd backend
.venv/bin/python - <<'PY'
import sys; sys.path.insert(0, '.')
from app.services import copilot_security_service as svc, tool_gateway
svc.tighten_tool_decision = lambda db, *, decision, **kw: decision  # 关掉闸门
tool_gateway.copilot_security_service = svc
import pytest
print(pytest.main(["tests/unit/services/<目标用例>", "-q", "--no-cov", "--tb=line"]))
PY
```

关掉闸门仍失败 = 与安全中心无关。本次用这个方法确认了
`test_agent_team_dispatcher::test_operations_team_rejects_write_action_without_executing`
与 `test_agent_responses_admin_tools::test_roundtable_stop_tool_waits_until_local_request_is_cancelled`
是既有失败。

## 6. ⚠ 需要补一步（MySQL 在收尾时下线）

配置写入成功后，收尾阶段本机 MySQL（`127.0.0.1:3307`）已停止。收尾时我又把默认策略改成
"只检测不硬拦"，并把受管控 Agent 名单补齐为
`["admin_copilot","chat_assistant","manager","operations","orchestrator"]`
（小菱在网关上的真实身份是 `chat_assistant`，运维动作是 `operations`）。

**数据库里现存的策略仍是旧名单（3 个），需要重新落一次**：

```bash
cd backend
.venv/bin/python scripts/apply_copilot_security_preset.py --preset max \
  --allow 127.0.0.1/32 --allow ::1/128 \
  --allow 10.0.0.0/8 --allow 172.16.0.0/12 --allow 192.168.0.0/16
```

不补这一步的后果：注入拦截、IP 白名单、超时、预算对 `chat_assistant`（小菱本人）仍然生效，
但对 `operations`（服务器运维工具）不生效——**这是唯一仍然开着的口子**。
补完后 `--show` 应显示 `governed_agents` 含 `operations`。

## 7. 待办（需要管理员决策，不由代码替决定）

1. **补齐 `tool_allowlist`**：按第 5 节清单粘贴，评分 95 → 100。
