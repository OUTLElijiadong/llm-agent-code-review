# 多 Agent 圆桌讨论审(讨论审)功能文档

> 版本:v2.5 · 最近更新:2026-07-15
> 关键词:圆桌讨论、聊天室、WebSocket、实时多 Agent、用户插话

## 1. 功能概述

「圆桌讨论审」是在原有「多 Agent 并行审查」之外新增的一种**实时、对话式**审查模式。它把通用质量、安全、可靠性、性能、可维护性五个审查子 Agent 放进一个**共享聊天室**:

- 每个 Agent 依次读取此前所有人(含其他 Agent 和用户)的完整记录,并自主选择**发言或静音**;
- 发言时通过结构化决策明确选择**提出/赞同/否认/质疑/补充/中立**立场和可选回应对象,形成可验证的真正交锋;
- **用户可以随时插话**,发言会被广播给所有 Agent,并影响后续讨论与最终共识;
- 讨论结束时由**主持人**汇总各方共识,给出结论性小结;
- **讨论结束自动沉淀为一份审查报告**(ReviewTask + 抽取的结构化 ReviewIssue),可在「报告列表 / 审查任务」中查询,报告详情含评分、严重度分布、问题清单与共识小结;
- **全程调用真实可溯**:每次 LLM 发言写入 `AiCallLog`,并广播 AgentEvent,使「Agent 调用日志」与「Agent 中心」统计反映真实讨论活动;
- 全程通过 WebSocket 实时推送,前端以聊天气泡逐条渲染,带「正在发言」打字指示。

与并行审查的区别:

| 维度 | 并行审查(full) | 圆桌讨论审(discuss) |
| --- | --- | --- |
| 交互形态 | 一次性出结果 | 实时逐条发言,可观察思考过程 |
| Agent 之间 | 互不可见 | 后者可见前者全部发言,可反驳 |
| 用户参与 | 不可 | 可随时插话,所有 Agent 可见 |
| 传输方式 | HTTP 请求/响应 | WebSocket 双向实时 |
| 产物 | 结构化问题清单 + 报告 | 对话记录 + 共识小结 + **同样沉淀为审查报告** |

## 3. 后端协议

### 3.1 REST 预检:`GET /api/discuss/start`

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `project_id` | int | 是 | 项目 ID(校验存在) |
| `file_id` | int | 是 | 文件 ID(校验属于该项目且 active) |
| `review_type` | string | 否 | 默认 `full`,决定参会 Agent 组合 |

成功返回:

```json
{
  "code": 0,
  "data": {
    "session_id": "disc_xxxxxxxxxx",
    "ws_url": "/api/ws/discuss/disc_xxxxxxxxxx",
    "file_name": "README.md",
    "language": "markdown",
    "review_type": "full",
    "agents": [
      {"code": "general", "name": "通用质量代理", "focus": "..."},
      {"code": "security", "name": "安全审查代理", "focus": "..."},
      {"code": "reliability", "name": "可靠性代理", "focus": "..."},
      {"code": "performance", "name": "性能审查代理", "focus": "..."},
      {"code": "maintainability", "name": "可维护性代理", "focus": "..."}
    ],
    "rules_count": 12
  }
}
```

> 预检只创建会话和暂存上下文(`register_pending`),**真正的讨论在 WebSocket 连接建立后才启动**,避免无人连接时空跑 LLM。默认 `rounds = 2` 轮。

### 3.2 WebSocket:`/api/ws/discuss/{session_id}?token=<JWT>`

鉴权:token 通过 query string 传入,服务端用 `jwt.decode` 校验;缺失或非法时以 `4001` 关闭连接。

**服务端 → 客户端**(JSON 文本帧):

| type | 字段 | 说明 |
| --- | --- | --- |
| `discuss` | `turn` | 一条发言(见 `DiscussionTurn`) |
| `control` | `action`,`payload` | 流程控制信号 |
| `session_end` | — | 会话结束(队列收尾) |

`control` 的 `action` 取值:

| action | payload | 触发时机 |
| --- | --- | --- |
| `round_start` | `{round, total_rounds}` | 每一轮讨论开始 |
| `speaker` | `{speaker_code, speaker_name, speaker_index, total_speakers}` | 轮到某 Agent 发言 |
| `paused` | `{}` | 已暂停 |
| `resumed` | `{}` | 已恢复 |
| `stopping` | `{}` | 收到终止请求,主持人即将给出小结 |
| `done` | `{}` | 讨论结束 |
| `info` | `{message}` | 提示信息(如「讨论尚未启动或已结束」) |

**客户端 → 服务端**(JSON 文本帧):

| action | 字段 | 说明 |
| --- | --- | --- |
| `user_input` | `content` | 用户插话(先广播为一条 `role:user` 发言,再通知编排器) |
| `pause` | — | 暂停讨论(回合间生效) |
| `resume` | — | 恢复讨论 |
| `stop` | — | 终止讨论(标记会话 concluded,编排循环下次检查时退出) |
| `ping` | — | 心跳,服务端回 `{"type":"pong"}` |

### 3.3 DiscussionTurn 结构

```ts
interface DiscussionTurn {
  turn_id: number       // 序号;用户插话为 -1
  agent_code: string    // security/reliability/performance/maintainability/orchestrator/user
  agent_name: string    // 「安全审查代理」「主持人」「你」…
  role: 'agent' | 'user'
  content: string       // Markdown 文本
  action: 'speak' | 'silent'
  stance: 'propose' | 'agree' | 'oppose' | 'question' | 'supplement' | 'neutral'
  reply_to?: string | null
  round_index: number
  timestamp: string     // ISO-8601
}
```

### 3.4 编排流程(DiscussionOrchestrator)

1. **开场**:主持人发布欢迎语(文件名、参会 Agent、轮数);
2. **逐轮**:`for round in range(max_rounds)`,每轮发 `round_start`;
   - **逐人**:`for profile in profiles`,发 `speaker` → 调用 `DeepSeekAgent.call_raw(..., json_mode=True)` 生成结构化**发言/静音决策** → 发布 `discuss` 帧;
   - 发言时通过 `_build_history()` 把**之前全部发言**(含用户)拼入 prompt,实现「后者可见前者」;
   - 每轮结束清空 `_user_inputs`(用户指示只对下一位发言者强提示一次)。
3. **汇总**:全部轮次结束(或被终止)后,主持人在线程池中调用 LLM 生成**自然语言共识小结**(失败时回退为按 Agent 分组的统计);
4. **收尾**:`finally` 中发布 `done` 并 `close_session`。

暂停/恢复/终止通过 `set_controller` 注册的回调 `_handle_control` 处理:
- `pause` → 置 `_paused=True` + 新建 `asyncio.Event`,编排循环在 `_wait_if_paused` 处阻塞;
- `resume` → 置 `_paused=False` 并唤醒事件;
- `stop` → `request_stop`(置会话 concluded)+ 发 `stopping`,即使在暂停中也会被唤醒并走向汇总。

## 4. 前端聊天室(AgentDiscussionPanel.vue)

### 4.1 布局

- **顶部头条**:🗣️ 标题 + 文件标签 + 状态徽标(连接中/进行中/已暂停/已结束)+ 「第 X / Y 轮」+「XX 发言中」;右侧三枚圆形按钮:暂停/继续、终止、关闭。
- **参会者条**:🎤 主持人 + 五个 Agent 彩色标签 + 🙋 你;每个 Agent 显示决策中/已发言/静音状态。
- **消息区**:发言气泡显示立场和回应对象;静音使用紧凑状态气泡;按角色着色并支持 Markdown 渲染;底部显示“决策中”指示。
- **回到底部**:向上滚动时浮现「↓ 最新」按钮。
- **输入区**:4 个快捷提问按钮 + 多行输入框 + 发送按钮。

### 4.2 状态机

```
connecting ──onStatus('connected')──▶ connected(live) ──session_end/done──▶ concluded
                                          │  ▲
                                    pause │  │ resume         (phase 始终为 live)
                                          ▼  │
                                       isPaused(仍 live)
```

- `canSend = canControl = (status==='connected' && phase==='live')`;
- **暂停态 phase 仍为 live**,因此暂停时仍可发言、点击快捷提问、终止;
- **结束态**(concluded):暂停/终止/快捷/发送/输入框全部禁用,输入框占位符变为「讨论已结束,无法发言」,仅「关闭」可用。

### 4.3 按钮与交互一览

| 控件 | 行为 | 反馈 |
| --- | --- | --- |
| ⏸ 暂停 / ▶ 继续 | 发送 `pause`/`resume` | 状态徽标切换「进行中 ↔ 已暂停」,图标切换 |
| ⏹ 终止 | 弹确认框「确定终止本次讨论吗?」→ 发送 `stop` | 主持人给出小结,状态转「已结束」 |
| ✕ 关闭 | 进行中且有发言时弹「讨论仍在进行…」二次确认;已结束直接关 | 断开 WS,移除面板 |
| 🔒安全 / ⚡性能 / 🔧可维护性 / ✅请汇总 | 直接把预设话术作为用户发言发送给讨论组 | 出现一条「你」的发言气泡 |
| 发送 | 把输入框内容发送(空内容禁用) | 立即出现「你」气泡,输入框清空,所有 Agent 可见 |
| Enter / Shift+Enter | Enter 发送、Shift+Enter 换行(正确处理中文输入法合成) | — |
| ↓ 最新 | 滚动到底部 | 按钮自动隐藏 |
| 重新连接 | 仅在 WS 错误条出现;重置状态并重连 | — |

## 5. 端到端使用流程

1. 进入「发起审查」页,选择项目、勾选一个文件;
2. 审查类型选择「💬 多Agent圆桌讨论(实时可见每个Agent的思考)」,按钮变为「💬 启动讨论审」;
3. 点击启动 → 前端调用 `GET /discuss/start` → 携带 `session_id` 跳转到 `/agents`;
4. AgentCenter 读取路由参数,弹出讨论面板并建立 WebSocket;
5. 主持人开场,各 Agent 逐条发言,可观察「正在发言」指示;
6. 期间可暂停、插话、用快捷提问引导方向;
7. 讨论自然结束或手动终止后,主持人给出共识小结;
8. 讨论结束后,面板出现「📄 查看报告」按钮,可直达本次讨论生成的审查报告;
9. 点「关闭」结束。

## 6. 讨论沉淀为审查报告与真实数据(v2.3.1)

讨论不再只是「聊完即止」,而是和并行审查一样产出**可查询、可导出的审查报告**,并把全过程的 LLM 调用沉淀为真实日志。

### 6.1 报告生成流水线

`DiscussionOrchestrator.start_discussion` 现接收 `user_id / project_id / file_id / review_type`,并:

1. **讨论开始**:经 `SessionLocal` 创建 `ReviewTask(review_type="discuss", status="running", task_name="<文件> · 圆桌讨论审")`,拿到 `task_id`;
2. **讨论过程**:每位 Agent 的发言、主持人汇总都把 `call_raw()` 返回的 `meta` 收集起来;
3. **讨论结束(`finally`,自然结束或终止都会执行)**:
   - 用 `log_deferred()` 把收集到的全部调用补写入 `AiCallLog`(带 `task_id/user_id/file_id`,`model_name` 带 `/<code>-agent` 后缀);
   - 调 `_extract_issues()` 用一次 LLM(`json_mode=True`)把讨论共识抽取为结构化问题,经 `result_parser.parse()` 解析后写入 `ReviewIssue`;
   - 用 `compute_score()` 按严重度计算评分,回填 `ReviewTask` 的严重度计数、`score`、`summary`(主持人共识原文),置 `status="success"`;
   - 通过 `done` 控制帧把 `task_id` 推给前端,面板显示「📄 查看报告」。

> 报告列表的本质是 `ReviewTask.status == "success"` 的记录,因此讨论报告天然出现在「报告列表 / 审查任务 / 仪表盘」中,报告详情复用既有 `report_service`(评分、严重度分布、`by_type`、问题清单)。

### 6.2 真实数据(Agent 中心 / 调用日志)

- 讨论的每次 LLM 调用都写入 `AiCallLog`,`model_name` 形如 `deepseek-v4-flash/security-agent`,经 `agent_service` 归因到对应注册中心 Agent,使「Agent 中心」的调用统计与「Agent 调用日志」反映真实讨论活动;
- 编排器通过 `AgentEventBus` 广播 `dispatch/thinking/complete` 事件,讨论进行时 Agent 办公室对应工位卡实时点亮;
- 经实测:一次「full」讨论(2 轮 × 4 Agent)新增 10 条 `AiCallLog`(8 条发言 + 1 条共识 + 1 条问题抽取),Agent 中心总调用数同步增长。

### 6.3 反驳式讨论

发言 system prompt 显式要求:有他人发言时**必须先表态**(同意 / 补充 / 质疑 / 反驳并给理由),鼓励指出严重度评估偏差、定位不准等并据理力争,而非一味附和,使圆桌讨论形成真正交锋。

### 7.1 路由重挂载导致面板弹不出(根因与修复)

**现象**:点击「启动讨论审」后成功跳转到 `/agents` 且 URL 携带了正确的 `discuss_session` 等参数,但讨论面板从不出现。

**根因**:布局组件的 `<router-view>` 以 `fullPath` 作为 `key`。`AgentCenter` 在 `onMounted → initDiscussionFromRoute()` 中读取查询参数、设置讨论状态后,调用 `router.replace({ query: {} })` 清理地址栏。由于 `key` 绑定 `fullPath`,**任何 query 变化都会让 `<router-view>` 整体重挂载 `AgentCenter`**,刚设置的 `discussVisible`、`discussSessionId` 等 ref 全部被重置为初始值,面板自然弹不出来。

**修复**(`frontend/src/views/agent/AgentCenter.vue`):用 History API 清理地址栏,而不触发路由导航,从而避免重挂载:

```js
// 仅清理地址栏查询串,不能用 router.replace:布局的 <router-view> 以
// fullPath 为 key,任何 query 变化都会重挂载 AgentCenter,导致刚设置的
// 讨论状态被重置、面板无法弹出。history API 不触发路由导航,故无重挂载。
window.history.replaceState(window.history.state, '', route.path)
```

| 结束态禁用 | ✅ 暂停/终止/快捷/发送/输入框全部禁用,占位符提示「讨论已结束,无法发言」 |
| **讨论生成审查报告** | ✅ 报告总数 6→7→8;报告 `review_type=discuss`,含 10/7 条结构化问题、评分、严重度分布、共识小结 |
| **报告列表/详情可查** | ✅ 「📄 查看报告」按钮跳转 `/reports/{id}`,详情页正常渲染评分与共识小结 |

## 9. 已知限制

- **会话存储为内存**:`DiscussionBus` 单例 + 内存字典存储会话,进程重启后丢失,且不支持多实例横向扩展(报告本身已落库,不受影响)。
- **轮数固定**:当前 `rounds = 2` 写死在 `discussion.py`,如需可配置应下沉到请求参数或系统设置。
- **问题行号精度**:讨论报告的问题由 LLM 从自然语言讨论中抽取,行号准确度略低于并行审查的逐分片定位,适合作为「讨论结论存档」而非精确定位。
- **断连后编排不强制收尾**:用户直接关闭面板(WS 断开)时后端编排仍会跑完并生成报告;若处于暂停态可能短时挂起,依赖会话生命周期自然结束。

## 10. v2.5 共享群聊与自主决策升级(2026-07-15)

- 圆桌不再复用普通 `full` 的四画像组合,而是通过 `get_discussion_agent_profiles()` 固定邀请全部五个代码审查子 Agent,不改变普通并行审查的调用成本。
- 每个 Agent 返回 `action/stance/reply_to/content` JSON 决策。解析器支持中英文枚举、Markdown 围栏和旧纯文本响应降级。
- `silent` 是成功的自主决策而非调用失败:会进入共享时间线和 WebSocket 回放,但不会被主持人或问题抽取器当成有效问题。
- 用户插话同步进入编排器 `all_turns`,后续 Agent、主持总结与报告问题抽取均能读取用户原话。
- 主持 Agent 的最终输出明确区分共识、未解决分歧、用户关注点和修复优先级。
- 前端参会者条显示每个 Agent 最近状态,消息元数据展示立场与回应对象,并兼容缺少新字段的历史帧。
