# 小菱与全栈优化：执行共识

## 已确认范围

1. 完成旧修复的本地 Git 提交和独立生产发布，保留备份及回滚证据。
2. 基于现有项目、知识库和代码证据审视小菱、后端状态机、Agent 调用、SOP、团队协作和前端反馈。
3. 准备用户指定动效库的独立本地预览，选择前不把第三方动效源码接入产品。
4. 形成按风险与依赖排序的可实施方案，并明确哪些能力已有、哪些是缺陷、哪些只是建议。
5. 对关键统计、生产版本和交付覆盖进行子代理独立复核。

## 技术与数据约束

- 继续使用当前 Vue、FastAPI、SQLAlchemy、MySQL、既有模型路由和部署体系。
- 修复保持向后兼容；数据库变更使用可验证迁移，不启动全库危险重建。
- 每次操作必须表达真实阶段、执行结果、失败原因和下一步；无法确定百分比时使用不定进度，而不是自动爬升的假百分比。
- 权限、审批、预算和数据完整性失败时拒绝执行；非关键能力失败可以降级，但必须保留已完成结果与明确缺口。
- 业务入口、异步任务、数据库持久化、事件流、报告和页面必须按同一任务标识核对。
- 发布成功仅表示该版本通过已执行门禁；只有真实账号和模型闭环执行过的项目才可记为业务验收通过。

## 尚待用户选择的内容

动效风格、具体应用位置及可能涉及的第三方商业授权等待预览后确认；真实生产浏览器需登录。除此之外，已确认的修复发布不重复询问。

## 本次继续授权的有界修复

用户再次明确“继续”，沿用先复现再修复、通过门禁后分批发布的授权。本批新增成员仪表盘读取状态修复与团队父失败后的未启动子任务收尾，不引入新的失败分支策略、预算、模型或动效选型。仪表盘复用五个真实接口，区分未知、成功、空数据和读取失败；团队保持现有fail-fast，不把未执行任务写成成功，不自动回填历史记录。新的本地测试结果与已运行的3.8.4分别记录，只有实际发布后的精确SHA才记为生产版本。
