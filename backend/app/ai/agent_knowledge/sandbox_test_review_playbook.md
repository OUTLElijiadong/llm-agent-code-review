# 沙箱测试审查知识库（test_review 手册）

本手册是 `test_reviewer` Agent 生成"黑白盒测试审查报告"时的方法论依据。
适用对象：沙箱白盒（编译/静态检查/单元测试）、黑盒（运行态 HTTP 探测/预览冒烟）与部署自动测试链的结论审查。

## 一、审查立场

1. 无可用证据 ≠ 通过。任何"通过"结论必须有可复核证据（退出码、HTTP 状态码、测试输出、日志摘录）。
2. 通过 ≠ 安全。白盒编译通过、黑盒 200 只说明"能编译、能响应"，不代表无缺陷、无漏洞。
3. 测试失败 = 用户的项目问题，要给出可执行的修复方向，不要只说"失败了"。
4. 信息分级：
   - 编译错误、测试断言失败、HTTP 5xx = 高优先级问题。
   - 跳过（skip）、警告（warning）、HTTP 3xx 重定向链异常 = 中优先级。
   - 性能/耗时过长、覆盖率缺失 = 提示级。

## 二、漏洞认定标准（认定门禁）

| 标准 | 内容 |
|------|------|
| 可复现 | 结论需有证据支撑；日志/响应可复现才写入报告"已确认"段 |
| 证据要求 | 堆栈跟踪/版本号/Server 头单独 ≠ 漏洞，只是侦察信息 |
| 影响门禁 | 只影响自身环境、不造成实质危害、纯猜测的问题 ≠ 漏洞，最多列入"风险观察" |
| 误报熔断 | 同一类问题重复出现但无证据升级时，降级为"待人工复核"，不重复报警 |

## 三、审查顺序（队列驱动，不靠记忆）

按固定顺序逐项核对，每项给出 结论 + 证据 + 建议：

1. **白盒编译/静态检查**：退出码是否为 0；编译错误是否阻断运行；静态告警是否集中在入口/鉴权/IO 文件。
2. **单元/集成测试**：是否发现测试文件；是否实际执行（而非因缺 pytest 静默跳过）；失败用例的断言含义。
3. **黑盒冒烟**：首屏状态码、响应时延、重定向链、错误页是否泄露堆栈/版本指纹。
4. **部署就绪度**：健康检查是否通过；预览路径是否可达；进程是否监听预期端口。
5. **交叉比对**：白盒过而黑盒挂（编译正常但运行即崩）→ 多半是运行时配置/依赖/环境问题；黑盒过而白盒挂 → 代码能跑但质量债高，提示补齐测试。

## 四、攻击面快速清单（黑盒通过后的必查项）

黑盒冒烟通过后，报告必须提示用户后续可做的人工/深度验证项：

- 鉴权端点是否未授权可访问（不带 token 直接请求）。
- 错误响应是否泄露内部路径、堆栈、SQL 片段、框架版本。
- 敏感路径探测：`.git/`、`.env`、`/actuator`、`/metrics`、`/swagger`、`/debug`。
- 响应头基线：`X-Powered-By`、`Server` 是否暴露精确版本；安全头（CSP/X-Frame-Options/X-Content-Type-Options）是否缺失。
- 文件上传/下载/导出端点是否存在路径穿越或任意文件读取迹象（参数名含 file/path/download/export）。
- 会话 Cookie 是否缺 HttpOnly/Secure/SameSite。

以上项只列"待验证清单"，没有实测证据一律标记为"建议验证"，不得写成"存在漏洞"。

## 五、报告结构（固定七段）

1. **总体结论**：通过/未通过/有条件通过 + 一句话概括。
2. **白盒结果**：证据 + 发现 + 建议。
3. **黑盒结果**：证据 + 发现 + 建议。
4. **问题清单**：按严重度排序，每条含 位置/证据/修复建议。
5. **攻击面待验证清单**：第四节的适用子集。
6. **下一步建议**：按优先级排列的可执行动作。
7. **证据附录**：关键日志摘录、状态码、耗时（原文引用，不加工）。

写作纪律：全程中文；每条发现必须挂证据；没有证据的只能进"建议验证"；禁止编造文件路径、行号、URL。


## 六、结构化安全发现与评分

对抗复检角色在原 JSON 中输出 `security_findings`；七段 Markdown 只负责展示，不是漏洞或 CVSS 数据来源。
每条包含 `title`、`description`、`severity`、`status`（confirmed/suspected/refuted）、`impact`、
`cvss_vector`（CVSS 3.1 八项基础向量，证据不充分则 null）、`cvss_rationale` 与 `evidence_refs`。
每个引用指定本次 `cvss_evidence` 的精确 `test_file` 和 `output` 中至少 24 字符的连续原文 `quote`。

只有 runner v2 已实际执行且经注入清单对账的用例输出可作为评分证据。编译错误、协议错误、
超时、缺失回执、HTTP 200、版本指纹、模型草稿和压缩摘要均不能单独确认漏洞。
复检必须解释原文如何证明漏洞机制与实际安全影响；原文锚点存在本身不证明模型的语义判断正确。
无证据的发现列入待复核，证伪项单独披露；两者均不参与已确认漏洞评分。

只有已确认且证据引用合法的发现进入 `conclusion.cvss_findings` 与报告快照 `findings`。
服务端仅由合法向量复算 CVSS，不接受裸分，不根据 Markdown、严重度或测试失败推导向量。
缺少合法向量的已确认发现仍保留，披露 CVSS 不可用；禁止为了凑足覆盖率补造向量。
领域综合分采用 CVSS 最高基础分 70% 和执行检查规则分 30%，并始终受执行质量分上限约束。
没有发现也保留执行质量实分；未覆盖范围不作安全结论。压缩报告的确认仍须回查原始执行证据。
